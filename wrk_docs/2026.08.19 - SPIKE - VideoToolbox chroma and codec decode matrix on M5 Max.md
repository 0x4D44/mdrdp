# SPIKE — what this Mac's VideoToolbox decodes in hardware, by codec × chroma × depth

2026-08-19 · Apple M5 Max, macOS 26.5.2 (25F84) · `tools/vt-caps-probe`

## Headline

**The M5 Max decodes H.264 4:4:4 and HEVC 4:4:4 (8- and 10-bit) in hardware, at native
5K.** That overturns the working assumption behind the AVC444 design and behind my own
earlier advice ("H.264 hardware decoders are 4:2:0-only") — at least for this client.
AV1 is hardware for 4:2:0 only; VideoToolbox has **no VP9 decoder at all**, hardware or
software. And the Mac-side H.264 decoder is not bounded by level 5.2: a 5120×2880
level-6.0 stream decodes fine — the 4096×2304 ceiling we clamp to lives in the Windows
server's encoder, not here.

So for rhydra, the 4:4:4 question is no longer "can the client decode it" — it can, for
HEVC and even for H.264 — it is purely "what can the host encode". The decision moves to
quench's Quick Sync generation.

## Method

`tools/vt-caps-probe/probe.swift` builds a `CMFormatDescription` for each stream (from
in-band SPS/PPS/VPS for H.264/HEVC; a hand-built `vpcC` / `av1C` atom for VP9/AV1),
creates a `VTDecompressionSession` with
`kVTVideoDecoderSpecification_RequireHardwareAcceleratedVideoDecoder = true`, feeds every
access unit length-prefixed, and counts decoded frames and their output pixel format. It
then repeats with hardware merely allowed, so "no session either way" means VideoToolbox
has no decoder for that format full stop. `VTIsHardwareDecodeSupported` is printed for
contrast — it answers per codec only and says nothing about chroma.

Streams are real encodes (ffmpeg testsrc2, 8 frames, GOP 4): libx264, libx265,
libvpx-vp9, SVT-AV1, and rav1e for the AV1 4:4:4 / 4:2:2 cases no installed encoder
produces. ffprobe confirmed each stream's profile before the run (High 4:4:4 Predictive,
HEVC RExt, VP9 profiles 0/1/2, AV1 Main/High/Professional).

## Results — 5120×2880, the cases that matter

Wall-clock per frame over 8 frames on a cold session, first frame included — an
order-of-magnitude figure, **not** a latency number to quote (n=8, warm-up included, no
distribution).

| Stream | Hardware decode | Output | ≈ ms/frame |
|---|---|---|---|
| H.264 4:2:0 8-bit, level 6.0 | yes, 8/8 | `420v` | 5.2 |
| **H.264 4:4:4 8-bit, level 6.0** | **yes, 8/8** | `444v` | 8.4 |
| HEVC 4:2:0 8-bit | yes, 8/8 | `420v` | 3.4 |
| **HEVC 4:4:4 8-bit** | **yes, 8/8** | `444v` | 6.4 |
| **HEVC 4:4:4 10-bit** | **yes, 8/8** | `p444` | 6.6 |
| AV1 4:2:0 8-bit | yes, 8/8 | `420v` | 4.0 |

Even with those caveats the shape is useful: 4:4:4 costs roughly 1.6–2× the 4:2:0 decode
time (it is twice the samples), and everything here is single-digit milliseconds at 5K.

## Encoders on this box (for a future Mac-hosted peer, not for the client)

`VTCopyVideoEncoderList` + `VTCopySupportedPropertyDictionaryForEncoder`:

- **Apple H.264 (HW)** — profile levels include `H264_High422_AutoLevel` and
  `H264_High444Predictive_AutoLevel`.
- **Apple HEVC (HW)** — `HEVC_Main`, `Main10`, **`Main444`, `Main44410`**, `Main42210`,
  Monochrome, MainStill.
- The software encoders offer 4:2:0 only. No VP9 or AV1 encoder of any kind.

## What this changes

1. **For rhydra the client is not the constraint.** HEVC 4:4:4 (8- or 10-bit) and even
   H.264 4:4:4 decode in hardware at 5K on this Mac. Whether rhydra can run true 4:4:4
   now depends entirely on the host encoder: Intel Gen11+/Arc and NVENC do HEVC 4:4:4;
   NVENC does H.264 4:4:4; AMD does neither. Next probe is therefore **quench's**: which
   Quick Sync generation it has and which encoder MFTs / input formats it exposes.
2. **AV1 is a 4:2:0 decision.** Hardware decode here is 4:2:0 only, and there is no
   software fallback inside VideoToolbox for 4:4:4 AV1 (that would be dav1d). Choosing
   AV1 means accepting 4:2:0 on the client for good.
3. **VP9 is software-only on the Mac**, whatever the silicon does for Safari. rvp9 or
   libvpx would be the decoder. That closes the "VP9 4:4:4 happy days" path for a
   hardware client.
4. **The H.264 5K ceiling is the Windows encoder's, not ours.** `clamp_to_encodable`
   stays — it protects the server — but a native H.264 path need not tile for the Mac
   decoder's sake.
5. **The M5 Max is not every Mac.** AV1 hardware decode starts at M3; the 4:4:4 results
   should be re-run on M1/M2 before anything assumes them. The probe is in the tree for
   exactly that.

## Caveats

- One machine, one OS build. The probe is cheap; run it, don't extrapolate.
- "Hardware" is VideoToolbox's own word (`UsingHardwareAcceleratedVideoDecoder` = true
  on a session that *required* hardware). I did not measure power or watch the media
  engine — if Apple were to satisfy "hardware required" with a GPU-shader decoder the
  probe would not know. The per-frame times are consistent with a fixed-function path.
- Timing is cold-session, n=8. Do not quote it. A proper decode-latency measurement
  belongs in the rhydra pipeline stats, where it would be warm and per-frame.
- Test content is a synthetic pattern; decoder *capability* does not depend on content,
  but decode time on real desktop frames will differ.
