# 2026.08.17 — HLD — Low-latency server exploration (hybrid video + text path)

Status: DRAFT (awaiting sign-off)
Author: Claude Fable 5, from a design discussion with Arthur 2026-08-17.
Revised same day after adversarial review (three lenses + cross-refutation); the
review materially restructured the plan — see the Review record at the end.

## Problem and goal

Interactive latency over RDP has a server-side floor we cannot remove from the
client: typing RTT to quench is ~34 ms p50 with the client spending ~4 ms (decode
p50 2.4 ms, present p50 6.4 ms). Two facts sharpen where that floor lives:
DWMFRAMEINTERVAL=15 halved *drag* RTT (23.3 → 12.3 ms) but left *typing* RTT
unmoved (33.0 → 34.3 ms), and typing frames already rode a ~16 ms tick before the
change — so the typing floor was never frame-rate-capped, and roughly ~18 ms of
server-side time (repaint? composite? encode? RDP pacing?) is **unattributed**
(`wrk_journals/2026.08.17 - JRN - DWMFRAMEINTERVAL experiment on quench.md`,
`… - JRN - frame cadence and transport findings.md`).

Arthur's hot path is remote terminal use (Windows Terminal / WezTerm). The
Hydra-era "send orders, render locally" idea is dead at the GDI layer (DWM
composites pixels from DX swapchains; there are no orders) but alive at the
VT/ConPTY layer, and WezTerm's mux client/server already ships it.

**Goal:** decide, with measurements, whether a custom server component — hybrid
H.264 video base layer plus a semantic text path — could cut interactive latency
well enough below RDP to justify building one. The deliverable is **numbers and a
go/no-go decision**, not a server. A server component is out of scope per
CLAUDE.md; this document is the sanctioned architectural-fork discussion, and only
its final gate can propose changing that.

Important calibration from the review: our ~34 ms figure is an *internal* metric —
`SessionStats::latency` stops at the paint (`src/stats.rs:385`) and excludes
present, the Mac compositor, and scanout. A glass-to-glass measurement of the same
session will read materially higher (plausibly ~45–55 ms). All comparisons in this
exploration are therefore glass-to-glass against glass-to-glass, measured by one
instrument; internal metrics are used only as cross-checks.

## Non-goals

- No product server, no protocol design, no auth/TLS design.
- No Indirect Display Driver. Note (review): DWMFRAMEINTERVAL=15 (~66 Hz) is NOT a
  substitute for the 120–360 Hz IDD trick — the deferred composition-interval
  delta is 2–6x — and the knob is a Terminal Server WinStation setting that only
  governs RDP-session desktops. Any "go" costing must carry the IDD as real work.
- No RAIL-style seamless windows, no changes to mdrdp's shipped session path.
- No code lifted from GPL projects (Sunshine/Moonlight). **Running** them for
  measurement is fine — GPL constrains distribution, not use — and P2b does.

## Method — one instrument, then phases with a gate after each

### P0 — the instrument: `probe glass`

A keypress-to-photon probe usable against *any* on-screen client: inject a
synthetic keystroke (CGEvent) into the target window, watch a screen region via
ScreenCaptureKit, report keystroke → pixel-change latency. Requirements that came
out of review, all load-bearing:

- **Timestamps from the frame's `CMSampleBuffer` presentation time**, never
  callback arrival (callback delivery adds 1–2 frames of pipeline lag).
- **Sampling resolution is the display refresh**: at 60 Hz the error is one-sided
  late, mean +8.3 ms, worst case +16.7 ms. The probe prints its capture rate and
  this uncertainty band with every result; run on the highest-refresh display
  available, **pinned to a fixed rate — ProMotion/VRR off** (a variable rate makes
  the quantization non-constant and invalidates the arithmetic).
- **Randomized inter-keystroke intervals** (jitter ≥ one full composition
  interval, recorded in the output) — a fixed period phase-locks against the ~16 ms
  grids on both ends and reports a spuriously tight distribution.
- **n ≥ 500 per row** (keystrokes are free; under a minute per row), report p50/p95
  with a **bootstrap CI on p50**. No p99 claims at these n.
- **Two event times per keystroke**: first-pixel-change and converged-glyph
  (H.264 quality ramps; local raster steps — reporting both keeps rows comparable
  and exposes threshold sensitivity).
- **Validation is against an oracle, not an expectation**: on a live mdrdp
  session, glass minus the internal RTT metric must equal present + ~half a
  refresh (both independently measured); and the answer must not move when the
  capture rate is changed. A "looks about right" number is not validation.
- Conditions block per run: Mac display refresh + VRR state, power state, host,
  resolution, codec, build profile, client versions, and who held quench.

Code: a `glass` subcommand beside the existing ones in `src/probe/` +
`src/bin/probe.rs`. This is shipped measurement-harness code on the normal
integration lane. The ScreenCaptureKit/CGEvent bindings are macOS-only and land in
the root manifest — they must sit under the existing `cfg(unix)`/target-gated
pattern so `scripts/check-windows.sh` (`cargo check --all-targets`, msvc target)
stays green.

### P1 — baselines, zero server code, then **Gate A**

Step zero: `probe rtt quench` baseline (the documented 3.31 ms LAN figure is
**temper's**; quench has no RTT baseline on record) and a short quench host
description (spec, GPU, OS, display topology) — CLAUDE.md documents only temper.

Then four rows, same workload (echo of a block glyph at a fixed cell in the same
terminal application for every remote row), same host, release builds, probe
conditions recorded:

| # | Path | What it establishes |
|---|---|---|
| 1 | mdrdp → quench RDP | our current glass floor — **this number anchors the gate** |
| 2 | Windows App 11.3.8 → quench | whether the reference client's floor differs |
| 3 | local WezTerm + ssh → quench | the semantic-path floor |
| 4 | `wezterm connect` (mux) → quench | the shipped VT-layer client/server split |

Expectations are deliberately left open until measured. (Review struck the
"~5 ms RTT-bound" claim for rows 3/4: ConPTY re-renders on its own tick and the
local terminal draws vsync-gated, so 15–25 ms glass is plausible — likely still a
large win over row 1, but that is the measurement's job to say.)

**Gate A (stop-and-report):** results go to Arthur before any P2 work. If the text
rows already deliver the win that matters for the hot path, the exploration can
end here at near-zero cost.

### P2 — video-floor attribution, without building a server, then **Gate B**

The originally-sketched bespoke spike (DXGI + Media Foundation encode + TCP +
custom viewer) died in review as a *first* step: it has no input path back to the
host (a one-way video stream cannot be measured keypress-to-photon), it must run
inside an attached RDP session whose encoder then runs concurrently with the thing
being compared, and its true cost is far above "~one file" (BGRA→NV12 conversion,
async hardware-MFT contract, this repo's first-ever linked Windows binary). Two
cheaper experiments answer the same question:

- **P2a — server-side composite probe.** A small on-quench tool: `SendInput` a
  keystroke, poll `IDXGIOutputDuplication::AcquireNextFrame`, timestamp the first
  frame containing the change; report the distribution. No network, no encoder, no
  viewer, no input channel. This directly attributes the unattributed ~18 ms: it
  measures repaint+composite in isolation. **If repaint+composite alone is
  ~25 ms, the video half is dead for an afternoon's work.** It also proves whether
  Desktop Duplication works in the session we can actually get on quench.
  (Prerequisite: producing a Windows binary — Rust toolchain on quench, or our
  first cross-link via the existing xwin splat. Contained, but real; budget it.)
- **P2b — measure the ceiling with someone else's tuned stack.** Install Sunshine
  on quench, Moonlight on the Mac, and measure it with `probe glass` — Moonlight
  already carries input back, so the measurement runs exactly like rows 1/2. A
  tuned reference implementation is an **upper bound** on what a first-cut custom
  path would achieve: if Sunshine/Moonlight cannot clear the bar on this hardware
  and LAN, ours will not, and the video half dies without our writing capture or
  encode code. It also exercises DDA viability on quench for free.

**Gate B (the go/no-go), pre-registered before P2 runs:** "go" toward a product
server requires the best measured alternative (row 3/4 for text, P2b for video)
to beat **row 1's measured glass p50 by ≥2x, with non-overlapping bootstrap
CIs** — a ratio against the same instrument's own anchor, never against an
internal metric. The DECISION doc records the numbers and the verdict either way.
Nothing beyond P2a/P2b is authorized by this HLD; a bespoke spike or product
server needs a new design signed off on the back of the DECISION doc.

### Deferred: notes for a bespoke spike, if Gate B ever wants one

Recorded so review findings aren't lost: it needs its own input channel (second
stream → `SendInput`); the capture-source dilemma (attached RDP session vs
console vs IDD) must be resolved explicitly; MF's encoder wants NV12 (D3D11
VideoProcessor conversion, async-MFT event pumping, `AVLowLatencyMode`, zero
B-frames); MF does not repeat SPS/PPS in-band by default while our decoder
requires in-band parameter sets (`src/h264.rs:742` errors without them); viewer
must reuse mdrdp's presenter or add a control row, or the client-side delta
confounds the server comparison; bind loopback + SSH forward, never a bare LAN
port; `--release` only; tear down binary and firewall rule as part of the phase.

## Acceptance criteria

1. `probe glass` passes its **oracle** checks: (a) on a live mdrdp session,
   glass − internal RTT ≈ present + ~half refresh, within the stated uncertainty
   band; (b) results stable across two capture rates. Output states capture rate,
   uncertainty band, and injection-jitter parameters.
2. Quench RTT baseline exists in `baseline/` and a quench host description is on
   record.
3. Baseline table: p50 (with bootstrap CI) and p95 for rows 1–4, n≥500 each, same
   remote terminal app for rows 1–2, full conditions block per row. Reported to
   Arthur at Gate A.
4. If P2 runs: P2a distribution of keystroke → first-changed-`AcquireNextFrame`
   on quench (release build, session type recorded); P2b Sunshine/Moonlight
   glass numbers under the same probe conditions, versions recorded.
5. A DECISION doc states go/park against the pre-registered Gate B ratio bar,
   with the numbers.

## Decision log

- **Measurement-first, product later** — every phase produces a number that can
  kill the idea cheaply, and a gate follows every phase (review: the original
  single end-gate pre-authorized the expensive phase).
- **Glass-to-glass as the one metric; internal metrics demoted to cross-checks**
  (review: the 34 ms anchor stops at the paint; comparing it to glass numbers
  mis-set the original gate).
- **Gate bar is a pre-registered ratio against the instrument's own row-1
  anchor**, not an absolute ms threshold derived from a different instrument.
- **Bespoke spike replaced by P2a (attribute the floor) + P2b (measure the
  ceiling with Sunshine/Moonlight)** (review: the spike had no input path, a
  capture-session confound, and understated cost; the two replacements are
  cheaper and more decisive).
- **Hydra orders are dead at GDI, alive at the VT layer** — terminals are grid
  state machines; ConPTY/VT is the seam; WezTerm mux already ships it. Measure
  before building.
- **No IDD in the exploration; no pretending DWMFRAMEINTERVAL substitutes for
  it** (review: TS-scoped knob, 2–6x interval delta remains, and the typing floor
  never was cap-bound).
- **GPL discipline** — run Sunshine/Moonlight and read them for technique; never
  copy code.
- **`tools/`, not a new `spike/` dir** — the repo already documents the
  out-of-workspace pattern there.

## Risks and open questions

- **The typing floor may live in the app/repaint layer** (the DWMFRAMEINTERVAL
  result points that way), in which case no capture-side server work helps and
  P2a will say so — that is a cheap, useful "park" outcome, not a failure.
- **Desktop Duplication session semantics on quench**: capture needs an attached,
  unlocked session; disconnect lands on the secure desktop
  (`DXGI_ERROR_ACCESS_LOST`; recoverable by re-creating the duplication once a
  desktop is back). P2a runs while a session is attached by construction; the
  product-viability question (headless capture ⇒ IDD) is recorded for the
  DECISION doc.
- **Producing a Windows binary is new for this repo** — check-windows.sh
  type-checks, it has never linked. P2a is deliberately tiny, but toolchain time
  on quench (or a first xwin cross-link) is a real prerequisite.
- **Sunshine on quench needs install + admin + possibly a display** — if quench
  is headless, Sunshine itself may need a virtual display, which is itself a
  finding (it prices the IDD into any custom path honestly).
- **Deployment/teardown**: binaries and any firewall change go on via the
  established autoinput/sudo route; loopback + SSH forward preferred over open
  ports; remove tool binaries and rules at phase end.
- **Single-session quench**: connects kick the holder; coordinate as with all
  live testing, disconnect gracefully, budget runs.
- **Probe portability of the pixel trigger**: caret blink and font smoothing can
  fire false first-change events; the block-glyph-at-fixed-cell workload plus the
  converged-glyph second timestamp are the mitigations — verify during P0
  validation.

## Review record

Process: three independent reviewers (measurement validity; Windows internals;
scope/process), then cross-refutation — each attacked the other two's findings
against the code and journals. 15 of 16 findings survived, several qualified;
one (an observer-effect claim) was downgraded to minor. All survivors are folded
into the body above. The three that most changed the design: the spike's missing
input path, the internal-RTT-vs-glass anchor mismatch (independently found by two
lenses and confirmed in `src/stats.rs`), and the Sunshine/Moonlight
measure-the-ceiling substitution. Residual risks are as listed; none is a design
unknown — each has a named phase that resolves it.
