# 2026.08.17 — HLD — Low-latency server exploration (hybrid video + text path)

Status: DRAFT (awaiting sign-off)
Author: Claude Fable 5, from a design discussion with Arthur 2026-08-17.
Revised twice same day: once after adversarial review (three lenses +
cross-refutation), once after Arthur's direction at the gate — see the Review
record and the decision log.

## Problem and goal

Interactive latency over RDP has a server-side floor we cannot remove from the
client: typing RTT to quench is ~34 ms p50 with the client spending ~4 ms (decode
p50 2.4 ms, present p50 6.4 ms). DWMFRAMEINTERVAL=15 halved *drag* RTT
(23.3 → 12.3 ms) but left *typing* unmoved (33.0 → 34.3 ms), so the typing floor
was never frame-rate-capped and ~18 ms of server-side time is unattributed
(`wrk_journals/2026.08.17 - JRN - DWMFRAMEINTERVAL experiment on quench.md`).
Arthur's read, which the numbers support: RDP against a 60 Hz-composited desktop
is at its ceiling — a keystroke crosses two vsync boundaries (repaint, composite)
at ~8.3 ms average each, ~16–17 ms expected floor before encode, worst-case phase
~33 ms. Client-side work cannot move this.

**Product intent (fixed by Arthur):** desktop sharing, not per-app remoting. The
candidate architecture is a custom server: H.264 video base layer + a semantic
text path for the terminal hot path (the Hydra "send orders, render locally"
insight — dead at GDI, alive at the VT/ConPTY layer).

**Goal:** measure, with our own instrumented code, the two numbers the decision
needs — (a) the floor of a VT-layer text channel, and (b) what a custom
capture/encode path achieves, including at high refresh (~240 Hz-class) — against
mdrdp/RDP as the anchor, then decide go/no-go on a product server. The
deliverable is numbers and a decision, not a product. A server component is out
of scope per CLAUDE.md; only this exploration's final gate can propose changing
that.

Calibration (from review): our ~34 ms is an *internal* metric — it stops at the
paint (`src/stats.rs:385`), excluding present/compositor/scanout. Glass-to-glass
will read higher (plausibly ~45–55 ms). All comparisons here are glass-to-glass
by one instrument; internal metrics serve as cross-checks only.

## Non-goals

- No product server, no protocol design, no auth/TLS design.
- No third-party remoting stacks (Sunshine/Moonlight/Parsec) as measurement
  proxies — their numbers need interpretation we cannot do, and effort spent on
  them survives no outcome (Arthur's call at the gate; reverses one review
  suggestion). Reading their source for technique remains fine; copying GPL code
  does not.
- No RAIL-style seamless windows; no changes to mdrdp's shipped session path.
- No Windows App comparison row — that loop has been run; it measures a client we
  cannot change.

## Method — one instrument, then phases with a gate after each

### P0 — the instrument: `probe glass`

Keypress-to-photon against *any* on-screen client: inject a synthetic keystroke
(CGEvent) into the target window, watch a screen region via ScreenCaptureKit,
report keystroke → pixel-change latency. Review-hardened requirements, all
load-bearing:

- Timestamps from the frame's `CMSampleBuffer` presentation time, never callback
  arrival.
- Sampling resolution = display refresh: one-sided late error, mean +8.3 ms at
  60 Hz, worst +16.7 ms. The probe prints capture rate and uncertainty band with
  every result; run on the highest **fixed** refresh available (ProMotion/VRR
  off — variable rate invalidates the arithmetic). This bounds how confidently
  small absolute numbers can be stated: ranking 10 vs 33 ms is safe; "8 vs 12"
  needs the band quoted honestly.
- Randomized inter-keystroke jitter ≥ one composition interval, recorded (fixed
  periods phase-lock against the ~16 ms grids on both ends).
- n ≥ 500 per row; p50 with bootstrap CI, p95; no p99 claims at these n.
- Two event times per keystroke: first-pixel-change and converged-glyph (H.264
  ramps quality; local raster steps).
- Oracle validation, not expectation: on a live mdrdp session, glass − internal
  RTT ≈ present + ~half a refresh (both independently measured); result stable
  across two capture rates.
- Conditions block per run: Mac display refresh + VRR state, power state, host,
  resolution, codec, build profile, client versions, quench session holder.

Code: a `glass` subcommand in `src/probe/` + `src/bin/probe.rs` — shipped
measurement-harness code, normal integration lane. ScreenCaptureKit/CGEvent
bindings are macOS-only root-manifest deps and must sit under the existing
target-gated pattern so `scripts/check-windows.sh` stays green.

### P1 — anchors, zero server code, then **Gate A (checkpoint)**

Step zero: `probe rtt quench` baseline (the 3.31 ms LAN figure is temper's;
quench has none on record) and a quench host description (spec, GPU, OS, display
topology).

| # | Path | What it answers |
|---|---|---|
| 1 | mdrdp → quench RDP, glass | **the anchor** every later ratio uses |
| 2 | `wezterm connect` (mux) → quench, glass | the floor of a VT-layer text channel — the hybrid's text half, measured for zero build cost |
| 3 | local terminal + ssh → quench, glass | free control for row 2 |

Row 2 is kept deliberately: it is not an alternative product, it is the mainline
"text capture on remote terminals" path (remote terminal state machine → grid
deltas → local rasterization) that the hybrid's text layer would use — a shipped,
tuned implementation of it, measured before we build anything. Expectations stay
open until measured (review struck the "~5 ms RTT-bound" claim; 15–25 ms glass is
plausible and would still be a large win).

**Gate A:** results reported to Arthur before spike work starts. A checkpoint,
not a kill — the product is desktop sharing, so text numbers inform the hybrid's
worth rather than replace the video question.

### P2 — the spike, stage 1: instrumented capture/encode path at current cadence

Our own minimal remoting path, built to be *decomposable* — every stage
timestamped, so the output is a budget, not one opaque number:

- **Server** (Rust, on quench): DXGI Desktop Duplication →
  BGRA→NV12 via D3D11 VideoProcessor → Media Foundation H.264, low-latency mode
  (async-MFT event contract, `AVLowLatencyMode`, zero B-frames), **parameter
  sets forced in-band** (our decoder requires them — `src/h264.rs:742` errors
  otherwise) → length-prefixed Annex B over TCP. Logs per-frame:
  capture-acquired (DDA `LastPresentTime`), convert start/end, encode in/out,
  send.
- **Input channel** (review finding W3, now a requirement): a second stream
  carrying keystrokes → `SendInput` on quench, so `probe glass` runs against the
  viewer exactly as against row 1. Timestamped at receipt.
- **Viewer** (macOS): reuses mdrdp's `h264::videotoolbox` decode and presents
  via the same presenter path mdrdp uses (review M5: a bare immediate-present
  viewer would confound the client side of the comparison). Logs decode in/out,
  present.
- **Decomposition without cross-machine clock sync**: server stages in server
  clock, client stages in client clock, wire+residual = glass − (server sum) −
  (client sum).
- Stage 1 runs inside an attached RDP session on quench (capture needs an
  attached, unlocked desktop; disconnect lands on the secure desktop and kills
  DDA). Composition is therefore ~66 Hz (DWMFRAMEINTERVAL=15) and the RDP
  session that hosts us idles alongside — both recorded as conditions. Stage 1's
  question is: **what does our path cost vs RDP's on the same desktop, and where
  does every millisecond go?**
- `--release` only; server binds loopback with the viewer connecting over an SSH
  tunnel (no open LAN port carrying an unauthenticated desktop stream); binary
  and any firewall change torn down at phase end; single-session coordination
  and graceful teardown as for all live testing.

Prerequisite, named honestly: this repo has never linked a Windows binary
(`check-windows.sh` type-checks only). Either rustup on quench or a first
cross-link via the existing xwin splat. Contained but real — budget it.
Realistic effort for stage 1: a few focused days, not an afternoon; accepted at
the gate because the effort is the first increment of the real server and the
decomposed numbers need no interpretation.

**Gate B (checkpoint):** stage-1 budget reported. If capture+composite alone
eats the floor (the DWMFRAMEINTERVAL typing result hints repaint/composite may
dominate), stage 2's refresh lever is the confirmed next question; if encode or
pacing dominates, we already know our path's advantage without stage 2.

### P3 — the spike, stage 2: the high-refresh number

The 240 Hz-class question — what does the same instrumented path achieve when
composition stops being 60-ish Hz — requires a virtual display at high refresh.
**Decided (Arthur): we write our own IDD**, building on the MIT-licensed prior
art rather than installing someone else's:

- Base: **Microsoft's IddSampleDriver** (`microsoft/Windows-driver-samples`,
  MIT — reusable, unlike the GPL stacks). IddCx drivers are UMDF (user-mode):
  a crash kills a process, not the box, and dev installation runs under
  test-signing on quench (one `bcdedit` + reboot). The community **Virtual
  Display Driver** (also MIT) is a worked example of the configurable
  high-refresh mode declaration; **virtual-display-rs** shows a Rust UMDF route
  worth evaluating, though the C++ sample is the beaten path — driver thin and
  C++ if that's faster, everything above it Rust.
- Bonus that may reshape stage 1's capture path: an IddCx driver receives the
  **composited frames directly on its swapchain, with present timestamps** —
  no Desktop Duplication polling, no attached-RDP-session dependency, one less
  copy. The driver is therefore not a measurement shim; it is plausibly the
  product's capture stage. Stage 2 measures both ways where cheap (IDD
  swapchain hand-off vs DDA against the virtual display) and keeps the better.

Prerequisites, named: a WDK build environment on a Windows box (heavier than a
plain Rust toolchain), and test-signing mode on quench (reboot). Stage 2 re-runs
the stage-1 measurement on the virtual display at 240 Hz (and 120 Hz as an
intermediate point), same decomposition, same conditions discipline. Note the instrument bound: at a 60 Hz local sampling
grid, single-digit results carry a ±8 ms-scale band — the decomposed server-side
timestamps are what make small numbers credible, which is exactly why the spike
beats a third-party stack here.

**Gate C (the go/no-go), pre-registered before P2 runs:** "go" toward a product
server design requires the spike (stage 2, or stage 1 if stage 2 is skipped) or
the text-path row to beat **row 1's measured glass p50 by ≥2x with
non-overlapping bootstrap CIs**. The DECISION doc records numbers and verdict
either way. Nothing beyond the spike stages is authorized by this HLD; a product
server needs a new signed-off design on the back of the DECISION doc.

## Acceptance criteria

1. `probe glass` passes its oracle checks (glass − internal RTT ≈ present +
   ~half refresh on a live mdrdp session, within the stated band; stable across
   two capture rates) and prints capture rate, uncertainty band, and jitter
   parameters with every result.
2. Quench RTT baseline in `baseline/`; quench host description on record.
3. Anchor table: p50 (bootstrap CI) and p95 for rows 1–3, n≥500 each, full
   conditions blocks; reported at Gate A.
4. Spike stage 1: glass p50 (CI) vs row 1 **plus** the per-stage budget
   (capture, convert, encode, wire+residual, decode, present) — release builds,
   session type and composition cadence recorded.
5. Spike stage 2 (if run): same, at 240 Hz (and 120 Hz) virtual display, driver
   route recorded.
6. A DECISION doc states go/park against the pre-registered Gate C ratio, with
   the numbers.

## Decision log

- **Measurement-first, product later; a gate after every phase** (review: the
  original single end-gate pre-authorized the expensive phase).
- **Glass-to-glass as the one metric; internal metrics demoted to cross-checks**
  (review: the 34 ms anchor stops at the paint; the gate bar is a pre-registered
  *ratio* against the instrument's own row-1 anchor, never an absolute ms figure
  from a different instrument).
- **Windows App row dropped** (Arthur: that loop has been run; it measures a
  client we cannot change).
- **Text rows kept, reframed** — `wezterm connect` measures the hybrid's text
  half (the VT-layer channel), not an alternative product; near-zero cost.
- **Third-party stacks rejected as measurement proxies; bespoke spike restored**
  (Arthur at the gate, reversing a review suggestion): their numbers need
  interpretation we cannot do, and the effort survives no outcome — while the
  spike is instrumented end to end (a decomposed budget, not one number) and is
  the first increment of the thing a "go" would build. Cost honestly stated: a
  few focused days + first Windows link, vs an afternoon for an install.
- **Spike carries the review's requirements**: input channel, in-band SPS/PPS,
  NV12 conversion accounted, mdrdp's presenter in the viewer (client side held
  constant), loopback+SSH binding, teardown, release builds.
- **High-refresh via our own IDD** (Arthur; built on Microsoft's MIT
  IddSampleDriver, not an installed third-party driver) — the driver doubles as
  a candidate capture path (IddCx swapchain hand-off), so the effort survives a
  "go". DWMFRAMEINTERVAL (~66 Hz, TS-scoped) is not a substitute for it.
- **Hydra orders dead at GDI, alive at the VT layer** — ConPTY/VT is the seam;
  measure the shipped implementation before building one.
- **GPL discipline** — read for technique, never copy.
- **`tools/`, not a new `spike/` dir** — the repo already documents the pattern.

## Risks and open questions

- **The typing floor may live in app repaint** (the DWMFRAMEINTERVAL result
  points that way). The spike's decomposed budget answers this directly — if
  capture timestamps show the changed frame arriving late from DWM, no encode
  work helps at 60 Hz and the refresh lever (P3) or the text path are the only
  levers. That is a cheap, useful "park" for the video half, not a failure.
- **DDA session semantics**: capture needs an attached, unlocked session;
  disconnect → secure desktop → `DXGI_ERROR_ACCESS_LOST` (recoverable by
  re-creating the duplication once a desktop is back). Stage 1 runs attached by
  construction; headless product capture ⇒ IDD, priced by the P3 route choice.
- **Concurrent RDP encoder in stage 1**: the hosting RDP session idles while the
  spike streams; its residual load is a recorded condition. Stage 2's virtual
  display removes this confound.
- **First Windows binary** — toolchain on quench or first xwin cross-link;
  budget it, and validate the MF encoder contract early (async event pump,
  NV12, in-band headers) since it is the least-known component.
- **IDD build/signing chain is new** — WDK environment on a Windows box,
  test-signing + reboot on quench, and UMDF driver install/removal mechanics;
  all standard but first-time for us. Driver removed at phase end like every
  other spike artifact.
- **Instrument bound on small numbers** — at 60 Hz local sampling the band is
  ±8 ms-scale; decomposed server timestamps carry the credibility for
  single-digit claims.
- **Deployment/teardown on quench** via the established autoinput/sudo route;
  loopback+SSH only; remove binaries, rules, and any installed driver at phase
  end. Single-session coordination and graceful disconnects as for all live
  testing.
- **Pixel-trigger portability**: caret blink and font smoothing can fire false
  first-change events; block-glyph-at-fixed-cell workload + converged-glyph
  timestamp are the mitigations — verify during P0 validation.

## Review record

Process: three independent reviewers (measurement validity; Windows internals;
scope/process), then cross-refutation — each attacked the other two's findings
against code and journals. 15 of 16 findings survived (one downgraded); all are
folded into the body. The three that most changed the design: the spike's
missing input path (now a required channel), the internal-RTT-vs-glass anchor
mismatch (gate re-anchored as a ratio), and the phase-gating restructure. One
review suggestion — measuring a third-party stack (Sunshine/Moonlight) as the
video ceiling — was considered and **rejected by Arthur at the gate** for
interpretation burden and non-reusable effort; the bespoke spike returned with
the review's feasibility findings folded in as requirements. Residual risks are
listed above; each has a named phase that resolves it.
