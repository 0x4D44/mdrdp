# 2026.08.17 — HLD — Low-latency server exploration (hybrid video + text path)

Status: DRAFT
Author: Claude Fable 5, from a design discussion with Arthur 2026-08-17.

## Problem and goal

Interactive latency over RDP has a server-side floor we cannot remove from the client:
typing RTT to quench is ~34 ms p50 even with DWMFRAMEINTERVAL=15, while our client
spends ~4 ms (decode p50 2.4 ms, present p50 6.4 ms) and the LAN floor is 3.3 ms RTT
(see `wrk_journals/2026.08.17 - JRN - DWMFRAMEINTERVAL experiment on quench.md`). The
floor is the Windows capture pipeline: app repaint → DWM composite → encode, each
vsync-gated. Arthur's hot path is remote terminal use (Windows Terminal / WezTerm),
where a Hydra-style "send orders, render locally" approach survives at the VT/ConPTY
layer even though GDI interception is dead.

**Goal:** decide, with measurements, whether a custom server component — hybrid
H.264 video base layer plus a semantic text path — can cut interactive latency well
below the ~34 ms RDP floor, before committing to building one.

This is an exploration HLD. Its deliverable is **numbers and a go/no-go decision**,
not a product server. A server component is currently out of scope per CLAUDE.md;
this document is the sanctioned architectural-fork discussion, and only the decision
gate at the end can change that scope.

## Non-goals

- No product server, no protocol design, no auth/TLS design.
- No Indirect Display Driver (IDD): driver signing and install cost is out of
  proportion for a spike; DWMFRAMEINTERVAL=15 approximates the high-refresh trick.
- No RAIL-style seamless windows, no changes to mdrdp's shipped session path.
- No code lifted from Sunshine/Moonlight/Parsec-adjacent projects (GPL); we read
  them for technique only.

## Approach — three phases and a gate

### P0 — glass-to-glass probe (small client-side build)

One metric comparable across *any* client is the missing tool. Build
`probe glass`: inject a synthetic keystroke into a target window (CGEvent),
watch a screen region via ScreenCaptureKit for the resulting pixel change, report
keypress-to-photon. Already proposed in the 2026.08.17 cadence journal as "next
candidate 1"; this phase builds it.

- Runs against anything on screen: mdrdp, Windows App, a local terminal.
- Reports p50/p95/p99 over n≥50 keypresses, with the capture-rate quantization
  error stated in the output (ScreenCaptureKit at its max frame rate; even 60 Hz
  sampling (~8 ms quantization) ranks 5 ms vs 34 ms unambiguously).
- Lives beside the existing `probe` subcommands (`rtt`, `stages`, `summarise`) —
  this is shipped measurement-harness code and integrates normally.

### P1 — baselines, zero server code

Same workload (echo of single keystrokes in a full-screen terminal), same host
(quench), same probe, release builds, conditions recorded per repo rules:

| # | Path | What it establishes |
|---|---|---|
| 1 | mdrdp → quench RDP | our current floor (~34 ms expected) |
| 2 | Windows App 11.3.8 → quench | is the reference client's server floor any different |
| 3 | local WezTerm + ssh → quench | the semantic-path floor (RTT-bound, ~5 ms expected) |
| 4 | `wezterm connect` (mux) → quench | the shipped "orders at the VT layer" client-server split |

Row 3/4 vs row 1 is the size of the prize for the text hot path. If ssh + local
terminal already delivers local feel, the text half of the hybrid may need no new
server code at all — that finding alone could end the exploration cheaply.

### P2 — video-floor spike (throwaway server)

Minimal Windows capture server on quench + minimal macOS viewer, to measure what a
custom video path achieves on this LAN:

- **Server** (Rust, ~one file): DXGI Desktop Duplication, poll `AcquireNextFrame`
  aggressively → Media Foundation H.264 encoder in low-latency mode (vendor-neutral;
  hardware MFT if present, else software — record which) → length-prefixed Annex B
  frames over one TCP socket. TCP is deliberate: measured, Windows App runs plain
  TCP on this LAN with no UDP advantage, and the spike inherits that finding.
- **Viewer** (macOS): dev-only binary reusing mdrdp's existing
  `h264::videotoolbox` decode and a bare presenter. Immediate present, no vsync wait.
- Measure with the same `probe glass` method against the viewer window.
- Spike code lives in `spike/latency-server/` as its own Cargo project, **outside
  the workspace**, so `cargo build`, `cargo test`, and `scripts/check-windows.sh`
  are untouched. It is throwaway; the measurements are the deliverable.

Expected budget if the theory holds: composite ~8–16 ms (at DWMFRAMEINTERVAL=15)
+ encode 1–3 ms + wire <1 ms + decode ~2 ms + present ~2 ms ≈ **15–25 ms**, i.e.
roughly one composition interval better than RDP. The gap between that and
Moonlight-class ~5–10 ms is the IDD/high-refresh trick, which we can size on paper
from the spike's numbers without building the driver.

### Gate — decision recorded, then stop

Write the numbers and a recommendation into a DECISION doc. Proceed toward a
product server only if the measured advantage justifies owning a server component
(suggested bar: spike typing p50 ≤ ~17 ms, i.e. ≥2x better than RDP, **or** the
text-path rows show a ≥3x win that a hybrid could deliver seamlessly). Otherwise
park the idea with the evidence attached. Either way the outcome goes back to
Arthur; nothing beyond the spike is authorized by this HLD.

## File impact

| Path | Change |
|---|---|
| `src/probe/…` (wherever `probe` subcommands live) | new `glass` subcommand: keystroke inject + ScreenCaptureKit watch |
| `spike/latency-server/` | new, non-workspace Cargo project: server (`--target windows`) + viewer bins |
| `wrk_docs/` | this HLD; later one DECISION doc with the numbers |
| `baseline/` | probe output JSONL for the four P1 rows and the P2 spike |

No changes to session, connect, gfx, clipboard, or any shipped runtime path.
`probe glass` is the only integration-lane code and is macOS-only by nature
(guarded like existing platform edges; Windows build unaffected —
`scripts/check-windows.sh` must stay green).

## Acceptance criteria

1. `probe glass` measures keypress-to-photon against an arbitrary on-screen window
   and states its own quantization error; demonstrated against a local terminal
   (expected single-digit ms) as a sanity floor.
2. A baseline table with p50/p95 for the four P1 rows, n≥50 each, same host, same
   workload, conditions recorded (host, resolution, codec, build profile, client
   versions — Windows App version quoted per CLAUDE.md).
3. The spike streams the quench desktop at 1920x1080 H.264 to the Mac viewer and
   its keypress-to-photon is measured the same way, encoder type recorded.
4. A DECISION doc states go/park against the gate above, with the numbers.

## Decision log

- **Measurement-first, product later.** The expensive mistake is building a server
  on a theory; every phase here produces a number that can kill the idea cheaply.
- **Glass-to-glass as the one metric.** Internal client metrics (our RTT probe)
  cannot instrument Windows App or WezTerm; pixels can measure anyone.
- **Hydra orders are dead at GDI, alive at the VT layer.** Modern apps composite
  via DX swapchains — no orders to intercept. Terminals are grid state machines;
  ConPTY/VT is the sanctioned seam, and WezTerm mux already ships it. Measure it
  before building anything.
- **TCP for the spike** — measured on this LAN: the reference client uses plain
  TCP with no UDP advantage; QUIC/UDP is a product-phase question.
- **Media Foundation for encode** — vendor-neutral on unknown quench GPU;
  NVENC/AMF/QuickSync specifics are product-phase.
- **No IDD in the spike** — signing/install cost; DWMFRAMEINTERVAL=15 (already
  permanent on quench) approximates the cadence win, and the remaining delta can
  be estimated on paper.
- **GPL discipline** — Sunshine/Moonlight are read for techniques (frame pacing,
  encoder settings, capture polling), never copied.
- **Spike outside the workspace** — keeps shipped builds, tests, and the Windows
  type-check exactly as they are; avoids relitigating the IronRDP architecture,
  which stays decided for the client.

## Risks and open questions

- **Desktop Duplication inside an RDP session.** The spike server will likely be
  launched via an RDP session to quench; DXGI duplication historically misbehaves
  off the console session (modern Windows supports it in-session, but verify
  first — it is the spike's step 1, before any encode work).
- **Deployment to quench.** Getting the server binary onto quench and a firewall
  port open needs the same autoinput/sudo route used for DWMFRAMEINTERVAL, or a
  file-transfer path we haven't set up. Budget time for it; it is not design risk.
- **Single-session quench.** Any fleet agent's connect kicks the current holder;
  spike runs need the same coordination discipline as existing live testing.
- **Probe quantization.** ScreenCaptureKit's achievable capture rate bounds the
  measurement resolution; the probe must report it, and claims must respect it.
- **Comparability.** Different terminals rasterize differently (font, caret
  flash); the P1 workload must trigger an unambiguous pixel change (e.g. echo a
  block character at a fixed cell) so all four rows measure the same event.
- **quench encoder unknown.** If no hardware H.264 MFT is present, software encode
  adds ~5–10 ms; record which engine ran and quote it with the number.
