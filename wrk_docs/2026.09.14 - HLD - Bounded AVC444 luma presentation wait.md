# Bounded AVC444 luma presentation wait

Arthur requested this design and implementation on 2026-09-14. It replaces the
100 ms chroma-refinement debounce, not AVC444 decoding. Tracked recurrence:
MDR-BUG-FLU-00130.

## Decision

Keep the displayed snapshot while new luma waits for chroma, for at most 50 ms.
Present the latest committed pixels as soon as chroma covers the pending luma
regions. If chroma never arrives, make the latest luma eligible at the deadline.
Further luma cannot move that deadline forward.

This is a presentation grace period, not an assertion that two PDUs describe the
same source frame. Decode every update in wire order. Do not preserve obsolete
auxiliary samples or reject ordered chroma using a guessed frame identity.

The existing immutable snapshot is the displayed image; the surface store is the
pending image. No extra desktop-sized buffer or decoded-frame queue is needed.

Protocol basis: [MS-RDPEGFX 2.2.4.6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/3b337b87-f478-4786-a63b-97794aa72075)
allows chroma in later graphics frames and defines no explicit pairing token in
the AVC444 envelope. [Section 3.3.8.3.3](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/781406c3-5e24-4f2b-b6ff-42b76bf64f6d)
requires chroma to use the latest corresponding luma rectangle. Therefore frame
ID inequality is not grounds for dropping chroma; spatial coverage is a
presentation heuristic, not a fabricated protocol identity.

## Why change it

Arthur still sees flicker on bright red terminal text and patterned usage bars.
The previous policy publishes luma immediately, then delays only LC2 chroma.
It can therefore expose alternating low/full chroma detail. LC0 also carries
independent luma and chroma region lists, but was classified entirely immediate.

The existing metadata example records luma at 41.748, chroma at 41.782, and
submission at 42.220. That is 438 ms from chroma to submission. These logs do not
establish why it took that long, which pixels changed, or the on-glass timing.
In particular, `combine_convert_us` includes callback/lock/log overhead and is not
a pure colour-conversion measurement.

Under this design, that luma starts a deadline at 41.798. If the chroma at 41.782
covers the pending regions, it releases the wait immediately. There is no second
chroma-settle timer. Frame completion, the existing large-canvas cadence, OS event
delivery and compositor backpressure still apply; 50 ms is not an on-glass SLA.

## State and ownership

The vendored decoder reports accepted luma and chroma rectangles before emitting
RGBA updates, then reports completion after the last bitmap callback. Rejected
chroma is not reported as coverage. These callbacks also bracket unframed updates,
so the presenter cannot copy pixels halfway through an AVC444 PDU.

`SurfaceStore` tracks a bounded list of pending luma rectangles for the mapped
output. New luma adds coverage; chroma subtracts it. LC0 adds its luma before
subtracting its chroma, including chroma outside its luma rectangles. Offscreen
updates cannot affect the visible wait. Regions are clipped to the mapped source.

The first pending luma sets the deadline. Completion releases it early. A batch
that is complete, expired, or released for urgent non-AVC content cannot be held
again before successful presentation. This prevents continuous traffic or a busy
compositor from repeatedly rearming the wait. If region tracking exceeds its
bound, release the wait rather than allocate without limit or drop pixels.

Normal visible non-AVC changes and reveal release the wait. Surface lifecycle
changes discard obsolete coverage. Existing frame commit, abort, fallback and
suppression rules still decide whether pixels are publishable.

After successful platform submission, the window acknowledges the copied stamp.
Only an acknowledgement matching current committed state can reset the batch.
A stale submission, a failed/busy submission, or a submission racing an active
update cannot clear newer pending work. Scheduling and snapshot-copy checks both
use the same store deadline; a chroma notification replaces the earlier wake.

## Diagnostics and validation

Keep the existing bounded flip-flop logs. Add metadata for wait start/release,
outstanding regions, redraw request/deadline, active-update/compositor deferral,
visibility and redraw-to-submission duration. Never log pixels or terminal text.

Deterministic clock tests cover chroma at 34 ms, timeout at 50 ms, repeated luma,
partial/disjoint coverage, LC0's independent lists, offscreen changes, region
limits, stale acknowledgements, lifecycle and unframed atomicity. Presenter tests
check the old snapshot remains unchanged during the wait and that chroma releases
it without another settle delay. Exercise the real graphics callback chain with
a deterministic decoder, and observe regression tests failing under mutations.

Run focused surface/graphics/window tests, vendored suites, formatting and the
Windows cross-check. A live release-profile client run remains necessary to
judge the reported visual flicker; synthetic tests prove policy, not perception.

Start fixed at 50 ms. Adaptation needs measured arrival-gap distributions and a
separate policy decision, not a guessed estimator in this fix.
