Host: `quench.lan.example`, SSH user `ano`, Windows console session 2.

Date: 2026-08-20. This was a direct P0 run before deploying the changed mdrdp build.
The existing mdrdp agent and IDD were not stopped or replaced. No reboot ran.

## Endpoint result

The install created healthy root device `ROOT\MEDIA\0000`. Observed endpoints:

```text
ACTIVE render  Speakers (VB-Audio Virtual Cable)
ACTIVE render  CABLE In 16 Ch (VB-Audio Virtual Cable)
ACTIVE capture CABLE Output (VB-Audio Virtual Cable)
```

Every endpoint's `DEVPKEY_Device_Parent` was `ROOT\MEDIA\0000`; its own provider and
hardware fields were generic Microsoft endpoint values. Resolving that parent produced
the stable product facts:

```text
DEVPKEY_Device_HardwareIds=VBAudioVACWDM
DEVPKEY_Device_Service=VBAudioVACMME
DEVPKEY_Device_Manufacturer=VB-Audio Software
DEVPKEY_Device_DriverProvider=VB-Audio Software
```

Endpoint instance IDs identify data flow without names: `{0.0.0...}` is render and
`{0.0.1...}` is capture.

The pre-change `audio-probe` then reported two active render endpoints, a present
default, a 48,000 Hz / 2-channel / 32-bit mix format, and successful loopback client
initialisation. Its verdict was `loopback capture is viable on this host`.

The friendly names differ from the older `CABLE Input` label. Product acceptance must
therefore use stable PnP/provider identity; names are evidence only.

## Interactive render check

A temporary `/it /rl highest` scheduled task ran PowerShell in console session 2. It
generated a five-second 48 kHz / 16-bit / stereo PCM WAV with 440 Hz left and 660 Hz
right, then completed `System.Media.SoundPlayer.PlaySync()` without error:

```text
ok session=2 bytes=960044
```

This proves an ordinary console application can render after installation. It does not
claim the mdrdp WASAPI capture or Mac playback path yet. The scheduled task and every
local and remote staging file were removed after the checks.

## Deploy and live identity after implementation

The 2026-08-20 same-version forced deploy completed without a reboot. A following dry
run took the idempotent fast path and reported the agent green, both CABLE endpoints
present, and live format readback healthy. `audio-source` is `loopback`.

The corrected release `audio-probe` mapped each IMMDevice endpoint to its
`SWD\MMDEVAPI\<endpoint-id>` PnP devnode, then to verified parent `ROOT\MEDIA\0000`.
It observed:

- base render: `CABLE Input (VB-Audio Virtual Cable)`, stable role
  `Speakers (VB-Audio Virtual Cable)`;
- capture: `CABLE Output (VB-Audio Virtual Cable)`;
- parent hardware/service/provider: `VBAudioVACWDM`, `VBAudioVACMME`,
  `VB-Audio Software`;
- active default render: base CABLE; shared mix: 48,000 Hz, stereo, 32-bit float;
- policy readback from deploy: both base endpoints pinned to 48,000 Hz, stereo,
  16-bit PCM; loopback initialisation viable.

## Real console playback over the native path

then ran the release client for 65 seconds. The measured continuous-tone window was

All five runs detected the right frequencies in the right channels with nonzero RMS.

JSON metrics report; screenshots were inspected only as session-health evidence and are
