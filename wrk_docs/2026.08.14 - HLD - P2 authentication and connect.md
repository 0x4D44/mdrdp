# HLD — P2 authentication and connect

2026-08-14 · **Status: SELF-APPROVED** · Gauntlet part P2

## Scope

Reach the RDP capability exchange against `temper` from a release build: keychain →
TLS with trust-on-first-use pinning → CredSSP/NLA → MCS → licensing → Demand Active /
Confirm Active, continuing through connection finalization and Save Session Info.

Finalization is in scope deliberately: Save Session Info carries the auto-reconnect
cookie, and P2b cannot prove session *resumption* without it. Stopping at Confirm Active
would leave that with no owner.

**Out of scope:** decoding anything, rendering, input, EGFX capability negotiation (P2c).

## Three decisions, one of them load-bearing

### 1. Do not use `ironrdp-tls`. Write our own upgrade.

`ironrdp-tls` 0.2.2 installs `NoCertificateVerification`
(`src/rustls.rs`, `mod danger`) — `verify_server_cert` returns
`ServerCertVerified::assertion()` unconditionally, and both signature verifiers do the
same. **Every certificate is accepted, always.**

Convenient for a library that cannot know the caller's trust policy; unacceptable here.
`temper` is on a LAN where ARP spoofing is easy, and a client that never validates the
server is exactly the permanent MITM hole a prior review predicted would arrive dressed
as "accept all certs to make P2 pass".

It also sets `config.key_log = KeyLogFile::new()`, honouring `SSLKEYLOGFILE` — a
deliberate debugging aid that writes TLS master secrets to disk. We do not want that
compiled into a release binary.

So P2 uses `rustls` directly with a **trust-on-first-use verifier**:

- First sight of a host: record the SHA-256 of its certificate DER and accept.
- Later connections: accept only that fingerprint.
- A changed fingerprint is a hard failure with a legible error, never a prompt that
  defaults to yes. Replacing a pin is a deliberate act.

Store is `known_hosts` under the platform config directory (`$XDG_CONFIG_HOME/mdrdp` or
`~/.config/mdrdp`; `%APPDATA%\mdrdp` on Windows), one `host:port sha256:<hex>` per line —
ssh's model, because it is well understood and inspectable with a text editor.

This is weaker than PKI and stronger than nothing, and it is the right trade for a fixed
set of personal machines. Recorded so nobody later mistakes it for a full trust chain.

### 2. Synchronous I/O with threads, not async.

`ironrdp` offers both (`ironrdp-blocking` and `ironrdp-async`). Taking blocking.

An RDP session is **one TCP connection**. Multiplexing happens at the RDP channel layer,
above the socket, so an async executor buys no concurrency the design actually needs —
it adds a scheduling layer between a byte arriving and a frame being decoded, which is
the wrong direction for a project whose headline requirement is latency that does not
degrade. Threads with explicit channels are also easier to hold in one's head, and they
sidestep async-in-trait friction in the platform abstractions (window policy, credential
store, hardware decode) that `CLAUDE.md` requires.

Writing our own TLS removes the last reason to go async: `ironrdp-tls::upgrade` is
async in every backend, but sync `rustls::StreamOwned` is not.

Revisit only if a real multiplexing need appears. Cheap to revisit; expensive to unpick
an executor we did not need.

### 3. Evidence is a payload-free event trace.

Under HYBRID_EX everything after negotiation is inside TLS, so a packet capture proves
nothing and decrypting one manufactures material `CLAUDE.md` forbids committing.

The connector therefore emits a structured event per connection stage — stage name,
outcome, elapsed time, PDU type and size where known, negotiated TLS version and cipher,
certificate fingerprint — and **never** payload bytes, usernames, or session content.
That trace is the artifact a critic audits.

## Approach

```
src/creds.rs      keychain lookup (service "mdrdp", account "<user>")
src/tls/mod.rs    TOFU verifier + known_hosts store + sync upgrade
src/connect.rs    drive ironrdp-blocking through the connection sequence
src/trace.rs      payload-free stage events, JSON
src/bin/connect.rs  CLI: mdrdp-connect <host> --user <account>
```

`connect.rs` owns the sequence and stays free of policy: the trust decision lives in
`tls`, the credential in `creds`, so both are unit-testable without a server.

## Acceptance criteria

1. A release build authenticates to `temper` and reaches capability exchange, then
   finalization, emitting a stage trace showing X.224 → TLS → CredSSP → MCS → licensing →
   Demand Active → Confirm Active → finalization.
2. **First connection pins**; the fingerprint lands in `known_hosts` and matches the one
   FreeRDP reported for this host.
3. **A changed fingerprint fails the connection** with a distinguishable error — proven
   by a test that mutates the stored pin, not by argument.
4. **No credential material anywhere**: the trace, all log levels, and `git log -p` grep
   clean for the password; the trace carries no session content.
5. Wrong password produces a clean, named authentication error, not a panic or a hang.
6. `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test` clean; new tests
   mutation-checked.

## Risks

- **sspi/CredSSP against a Microsoft Account** is the least certain part. P1b proved the
  credential works through FreeRDP, which uses its own NTLM implementation; IronRDP uses
  `sspi` 0.21.3. A difference here is plausible and would be a genuine finding.
- **`known_hosts` on first run** must create its directory. A failure to persist should
  warn loudly rather than silently degrade to trust-everything.
