# Native interactive correctness fixes

- **Status:** SELF-APPROVED
- **Bugs:** MDR-BUG-FLU-00029, MDR-BUG-FLU-00030, MDR-BUG-FLU-00031

## Scope

Make the Rhydra native path usable for interactive work at Quench's 5120x2880,
200% desktop: preserve colours, show one responsive pointer, and remove the
multi-second keyboard feedback delay.

Out of scope: RDP transport behaviour, dynamic-resolution policy, exact remote
cursor-shape mirroring, and the postponed eight-hour soak. The soak resumes
after the interactive correctness fixes are integrated and installed.

## Approach and file impact

1. Fix colour at the violated buffer contract. Add a strict RGBA row-copy blit
   for decoded H.264 tiles. Raw wire rectangles remain BGRA and retain their
   existing swizzle. Impact: `src/native/session.rs`, `src/surface.rs`, and
   focused tests with distinct red, green, and blue values.
2. Make cursor ownership explicit. The IDD calls
   `IddCxMonitorSetupHardwareCursor` with alpha support, full colour-XOR support,
   and a 256x256 maximum, then queries every cursor notification into a large
   enough scratch buffer. That prevents unsupported I-beams, masked cursors, or
   200%-scaled/accessibility pointers falling back into software composition.
   The macOS window owns the visible, immediate platform cursor. Rhydra mirrors
   remote visible/hidden state as a small, skippable video message; position
   stays local and exact remote bitmap shapes are deliberately deferred. A fix
   that only hides the local cursor is insufficient.

   Reuse the shared header's reserved u32 as an atomically written `cursor_hidden`
   word (`0` = visible/default, `1` = hidden). This preserves layout v1 and lets
   old/new driver and server builds deploy in either order. The server sends the
   current state on connect and only changes afterward; the client resets visible
   on connect and disconnect. Expected impact: the IDD driver/shared-section
   contract, IDD source, video framing/send path, and native cursor dispatch.
3. Establish causal keyboard latency with `probe glass`: synthetic key into the
   mdrdp process, a visible Notepad cell on Quench, and ScreenCaptureKit detecting
   that cell's change. Server receive-to-injection remains a separate same-clock
   diagnostic; the current client `InputClock` remains labelled a non-causal
   activity proxy and is not acceptance evidence.
4. Remove an independent input starvation path. Native window motion uses one
   replaceable latest-move slot, separate from reliable key/button/wheel events.
   Buttons and wheels emit their embedded absolute position before the action,
   so coalescing cannot change their target. Scripted `autoinput` motion stays
   reliable so drag baselines keep their meaning. Keep the existing RDP queue
   unchanged. Expected impact: `src/input.rs`, `src/main.rs`, `src/window.rs`,
   and `src/native/session.rs`.
5. Re-measure after the strict tile copy before changing video scheduling. If
   the causal run still fails, record received versus painted capture sequence
   depth, client socket bytes waiting, server blocked-write duration, per-tile
   drops, conversion time, and decode errors. Bound presentation work while
   still decoding every H.264 AU needed for reference state. The contingency
   decodes stale intermediate AUs into reusable YUV scratch but skips their
   RGBA allocation/conversion/blit; it converts only the latest paint candidate.
   Never drop a P-frame before decode. Expected impact only on failure:
   `src/h264.rs`, `src/native/session.rs`, and native stats.

## Acceptance criteria

- A distinct-channel tiled decoder test fails before the colour fix and passes
  after it; red, green, and blue reach the RGBA surface unchanged.
- Strict RGBA blits reject an overhanging rectangle and a size mismatch rather
  than clipping either one.
- Raw BGRA rectangles still swizzle once and their existing tests remain green.
- A native Quench screenshot shows the Windows blue Start control as blue.
- Three screenshots taken during continuous motion show one pointer and no
  older pointer baked into the Windows image. Include the alpha arrow, the
  Notepad text I-beam, and one non-default Windows pointer size at 200%. The
  visible pointer follows local movement immediately. Remote hidden/default
  state still changes the local pointer correctly.
- A native input unit test queues at least 10,000 moves around a key transition;
  the key remains reliable, only the latest free-standing move survives, and a
  button/wheel retains its own target coordinates. Each new test is observed red
  before its fix.
- On the integrated release build at 5120x2880, 200%, 240 Hz, `probe glass`
  runs n=100 against a restarted Notepad with caret blink disabled
  (`HKCU\\Control Panel\\Desktop\\CursorBlinkRate = -1`) and a watch region that
  excludes the caret column. It has zero timeouts and at most five poisoned
  trials. First-change p95 is at most 150 ms; p50 with its 95% interval and max
  are reported. The server's same run has receive-to-successful-injection p95
  below 2 ms and reports zero injection failures. This is a usability repair
  bound; the stricter transport target remains p50 CI upper bound 40 ms and
  p95 75 ms.
- Focused tests, formatting, clippy, the Windows cross-check, and the repository
  integration gate pass for each independently landed fix.

## Decision log

- Treat colour, cursor, and keyboard latency as three bugs and three green
  integrations. This lets Arthur test improvements as they land and keeps each
  regression independently revertible.
- The colour mismatch is a proven client-side contract violation, so it lands
  first without waiting for live latency diagnosis.
- Cursor and keyboard symptoms may share a late-frame cause, but stay separate
  until measurements prove that. One fix may close both only if the evidence
  shows one root cause and each bug keeps its own verification record.
- Prefer the local OS cursor because it follows physical input immediately.
  Microsoft's IddCx contract confirms that software composition is the default
  and `IddCxMonitorSetupHardwareCursor` transfers cursor rendering to the
  driver, so this is the narrow correct exclusion layer.
- Treat exact cursor bitmap shapes as a later refinement. Visibility is required
  now because Windows can intentionally hide its pointer; position is not sent
  because the local window already has the freshest position. Remote-only moves
  (`SetCursorPos`, clipping, snap-to-button, accessibility tools) may temporarily
  diverge and are explicitly out of scope; reserve x/y fields in the cursor
  message for a later additive repair.
- Keep reference decoding exact. If video backlog survives the colour-copy fix,
  suppress intermediate presentation only after decoding; never skip dependent
  H.264 input to chase latency.

## Review journal

Two independent reviewers critiqued the draft, then each refuted the other's
findings. The following findings survived a completed refutation:

- Cursor ownership contradicted the draft's protocol scope. Resolved by naming
  IDD hardware-cursor exclusion plus a skippable visibility-only video message;
  exact shape transport stays out of scope.
- The unbounded input FIFO can put keys behind arbitrary mouse motion. Resolved
  by a replaceable native move slot plus reliable non-move input and coordinate
  preservation at action encoding.
- `InputClock` and cross-machine timestamps cannot prove causal key-to-pixel
  latency. Resolved by making `probe glass` the acceptance oracle and using
  server timings only within the server clock domain.
- The existing RGBA blit clips while the tile contract is strict. Resolved by a
  new strict RGBA helper, not reuse of the clipping helper.
- Server input telemetry can silently lose rows, and injection failures currently
  look successful. Resolved by requiring explicit injection success/failure and
  a zero-failure acceptance result; the local glass oracle remains authoritative.
- Existing tiled tests use equal channel bytes. Resolved with a distinct-channel
  regression observed red before the fix.
- One review found unbounded video batch work survived; the reciprocal review
  marked the same concern unverified because the read/reassembly boundaries may
  limit each batch. Resolution: measure sequence backlog after the copy fix and
  change scheduling only on a causal failure, while preserving decode order.

The single external Claude/Fable pass raised one Critical, four Significant,
and three Useful items. Triage:

- Accepted the Critical cursor fallback: claim alpha plus full colour-XOR up to
  256x256, consume every notification, and test I-beam plus non-default size.
  Verified against the repository's WDK 10.0.26100 IddCx 1.6 header. Rejected
  only the suggested `CursorShapeTypes` member because that struct has no such
  field in this WDK.
- Accepted conversion/allocation and in-flight socket backlog as measurements
  for the conditional video step. Paint suppression alone is not enough.
- Accepted the caret-blink false-positive and made the existing blink-disabled,
  caret-excluded protocol explicit.
- Accepted the three-component deployment risk. Reusing the reserved header word
  keeps layout v1 and avoids a lockstep deploy/revert.
- Accepted visible-state reset rules and remote-only position divergence.
- Resolved the `autoinput` baseline concern by coalescing only window motion;
  scripted motion remains reliable.

No critical finding remains unresolved. Residual risk: the cursor API and static
contracts can be tested locally/cross-compiled, but only the installed Quench
driver proves that every Windows cursor shape is absent from captured pixels.
