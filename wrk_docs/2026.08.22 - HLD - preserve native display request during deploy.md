# Preserve native display request during deploy

- **Status:** SELF-APPROVED
- **Bug:** MDR-BUG-FLU-00032

## Scope

A full `mdrdp deploy` must carry a running Rhydra agent's desired width, height,
refresh rate, and desktop scale across agent replacement. This prevents a proven
5K/200% host from reverting to the agent's 1440p/100% safe defaults during an
upgrade.

Fresh hosts and hosts whose agent cannot report a complete desired tuple keep the
existing defaults. The native client remains the owner of each session's requested
mode. The most recent complete request persists in the agent's scheduled-task command
so deployment, logon, and agent restart do not reconcile an unrelated safe default.

## Approach and file impact

- Extend `src/deploy.rs` preflight evidence with the complete desired display tuple
  from schema 5+ running-agent status. Reject zero or partial defaulted fields.
- Add one optional, validated `--display <width> <height> <hz> <scale>` argument to
  Rhydra agent `run` and `install`. `install` writes the same argument into the
  scheduled task; `run` seeds the reconciler before its first tick.
- A full deploy passes the captured tuple to agent install. Final verification
  compares both the replacement's exact desired tuple and its actual green display.
- Add parser, startup, plan, missing-evidence, and exact-verification regressions.
  Keep fast-path, audio-only, and fresh-host plans unchanged.

## Acceptance criteria

1. The regression is observed failing before agent install carries the prior tuple and
   passing afterward.
2. A full deploy with complete prior evidence installs the agent with the exact four
   prior values before audio configuration.
3. Missing prior display evidence adds no display arguments and preserves current
   fresh-host behavior.
4. Old or incomplete status cannot manufacture a tuple from serde defaults. The
   agent validates the same finite mode/scale set as live `prepare-display`.
5. Focused deploy and agent tests, formatting, clippy, and the Windows cross-check
   pass.
6. A fresh integrated deploy on Quench finishes green at 5120x2880, 240 Hz, 200%.

## Decision log

- Seed the existing reconciler through a small agent CLI argument rather than replay
  control after startup. This removes the transient 100% race and makes a failed
  deploy retry recover the same tuple.
- Restore only a complete tuple. Partial or stale guesses are more dangerous than
  the documented safe default.
- Verify the exact desired tuple as well as green state, so a valid but wrong policy
  cannot pass.
- A forced deploy may preserve the preflight snapshot rather than a newer request
  racing after it. This is accepted: force deliberately ends that session, and the
  captured request is the last stable policy deploy can prove.

## Review journal

Two independent adversarial reviews found four common survivors: a post-install
restore could permanently lose the old tuple on failure; acknowledgement would not
prove reconciliation; old schema defaults could manufacture 0x0/100 evidence; and
final verification did not compare the exact tuple. Pre-seeding validated scheduled-
task arguments and exact verification resolve all four. Their PowerShell-helper test
concern became moot when that helper was removed.

The reviewers' stale-snapshot concern was refuted as a correctness blocker: `--force`
already terminates any live session, so preserving the last preflight-proven request is
the safe deterministic choice. A compare-and-set epoch would add protocol machinery
without preserving an active session.

The single Claude Fable review independently confirmed the old-schema and exact-
verification gaps. Its suggestion to reuse an agent CLI rather than add PowerShell was
accepted and strengthened to pre-seed the scheduled task. Its transient-startup warning
is thereby eliminated. There were no unresolved critical findings.
