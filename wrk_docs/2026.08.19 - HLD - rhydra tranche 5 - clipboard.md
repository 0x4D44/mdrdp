# HLD — rhydra tranche 5: clipboard, text-first, both directions

Step 5 of the parent HLD's §9 sequencing (§6 there). Tranche 4 landed the health
ladder (v0.1.77, agent 0.4.0, control schema 3).

This is **product requirement #1** — "clipboard dies mid-session; ours must
survive an all-day soak with zero wedges".

---

## 0. PARKED — an architectural fork, and a question for Arthur

**No code has been written and none should be until §4 is decided.**

Two independent adversarial reviews found the same blocker, and I verified it
against the code myself:

> **There is no client→server message channel in the native transport.**

- The **video socket is server→client only**. `win/send.rs`'s `poll_client_eof`
  *peeks* and never consumes, and its own comment says "The viewer never sends
  on this socket; inbound bytes are ignored." Client bytes there would
  accumulate forever *and* break the EOF detection that frees the single viewer
  slot — the exact bug that function exists to prevent.
- The **input channel cannot carry it**. `input_proto` is frameless and
  fixed-width per kind: "an unknown kind **cannot be skipped** — it is terminal
  for the connection". `win/input.rs:474` closes the connection, and
  `src/native/session.rs` reads that as "the host closed the input channel" and
  **tears the session down**.

So the parent HLD §6's premise — *"the framing already skips unknown types so
old peers stay safe"* — is true **server→client only**. Client→server, a stray
clipboard message to a pre-tranche-5 host does not get ignored: **it kills
keyboard, mouse and the session.**

That needs a parent-HLD amendment, which the loop prompt names as a fork. The
question is §4. Everything else in this document has been corrected against both
reviews and is ready to build once the answer lands.

---

## 1. The one-sentence deliverable

Text on the Mac's pasteboard appears on quench's clipboard and vice versa, over
the native transport, with no state that can fail to return to idle — and with
soak evidence, because a green unit test does not discharge a soak-class
requirement.

## 2. What push-only does and does not buy — corrected

The first draft claimed the native path is "structurally wedge-proof" because
there is no round trip. **That claim was too strong and is withdrawn.**

What is genuinely removed: CLIPRDR's *pending-paste* wedge — the state where we
have asked for content and may never be answered. mdrdp's RDP bridge spends a
5 s timeout and a state machine escaping it. A push design has no such state.

What is **not** removed, and must be designed for:

- **Transport backpressure.** A socket write blocks when the peer's window
  fills; the ssh tunnel adds another buffer. Server→client shares a **2-deep,
  deliberately lossy** `sync_channel` with video (`win/pipeline.rs`,
  `QUEUE_DEPTH = 2`) behind a single writer with a 5 s write timeout. `try_send`
  drops silently under any video load; `send` blocks the clipboard thread. Both
  violate the invariant. **Resolution:** clipboard gets its own depth-1,
  keep-latest slot the sender checks each lap. Clipboard is last-writer-wins, so
  superseding a queued payload is not a loss, and unbounded growth is impossible
  by construction. A stalled slot drops and reports; it never blocks.
- **The OS clipboard.** See §6 — and note the first draft named the wrong
  hazard.
- **The suppressor itself.** §5's first draft relocated the wedge rather than
  removing it: it could silently and permanently refuse to send a legitimate
  copy. Corrected below.

Head-of-line blocking is the reason the text ceiling (§7) is load-bearing rather
than defensive: a multi-MB clipboard message occupies the reassembler while
video queues behind it, on a product whose premise is latency.

## 3. What is reused — corrected

Reused **unchanged**, because they are about the OS rather than CLIPRDR:

- `OsClipboard` / `ArboardClipboard`, whose handle is dropped and recreated on
  any error so a poisoned handle cannot disable the clipboard for the session.
- `ClipboardPolicy`'s **direction gates**.
- `content_fingerprint` — the bounded-cost **hash function**.
- The ~250 ms local poll.

**Corrections to the first draft's claims:**

- It said `ClipboardPolicy` supplies "the size ceiling". It does not: it has
  `max_image_bytes` only, and images are out of scope. **There is no text
  ceiling anywhere in the codebase.** See §7.
- It called `content_fingerprint` "the echo suppressor". The hash function is
  reused; the **suppression policy is new**, and the first draft specified it
  differently from — and worse than — the working RDP one.

## 4. THE OPEN QUESTION: which channel carries Mac→host?

Server→host→client is settled: the video socket is length-prefixed and both
readers already skip unknown types (`session.rs:217`, verified). Only the uplink
is open.

| | Option | Cost | Risk |
|---|---|---|---|
| **A** | Make the video socket bidirectional — a real framed client→server channel | Reuses `framing`; no new port, tunnel or probe change | Rewrites `poll_client_eof` (peek-as-EOF stops working once bytes are buffered) and touches the single-writer discipline tranche 3's review shaped. Shares head-of-line with video. |
| **B** | A length-prefixed escape kind in `input_proto` | Smallest diff | **Reject.** Contaminates a deliberately frameless, fixed-width, latency-critical protocol with variable-length records, and `stats.rs` says `wire_version` couples both dialects — so it forces a fleet-wide redeploy for a feature addition. |
| **C** | A fourth socket: a dedicated session-data channel, framed, bidirectional | Clean isolation; no HOL contention with video; no changes to any proven path | +1 port in `ForwardPorts`, +1 tunnel forward, +1 probe step under the existing 8 s deadline |
| **D** | Carry it on the existing **agent control port**, with the clipboard owned by the agent | No new port; agent already owns session-scoped Windows state, and `--doctor` could report clipboard health as a rung | Control becomes dual-purpose (management + session data) and must go from request/response to push, with a long-lived connection replacing today's open-query-close |

**My recommendation: C.** It is the only option that changes no proven code —
the single-writer video path and the frameless input path both stay exactly as
they are — and it keeps clipboard traffic off the latency-critical video stream
entirely. The cost is one more forwarded port and one more probe step, both
mechanical. A is cheaper in moving parts but pays for that by reworking the EOF
detection and accepting HOL blocking with video; D avoids a new port but turns
the management channel into a data channel.

**In every option the capability flag is a safety gate, not a courtesy.** The
client must not write a clipboard byte upstream unless the host's header
advertises support, because against a 0.4.0 host that write is session-fatal.
The header gains `clipboard: bool` (serde-defaulted false) and `SCHEMA` bumps
5 → 6; **`wire_version` stays 3** — no forced redeploy.

## 5. Echo suppression — corrected, because the first draft was wrong

The first draft: *"each side records the fingerprint of the content it last
applied from the wire, and never sends content whose fingerprint matches it."*
Both reviewers produced the same counterexample:

1. A applies **X** from the wire (`last_applied = X`).
2. The user on A copies **Y**. A sends Y. B now holds Y. `last_applied` is still
   X — A originated Y, it never applied it.
3. The user on A copies **X** again → fingerprint matches `last_applied` →
   **suppressed**. B still holds Y.

"I copied it and it didn't paste" — silent, permanent, trivially reachable. The
draft's justification ("the two ends already agree") was false: they agreed at
the instant of the apply, and the other end has since moved on.

**The correct model is the one the RDP bridge already implements**: one slot
holding the fingerprint of the last content observed **from either source** —
updated on a local observation *and* on a wire apply (`src/clipboard.rs:519`,
`:780`). Replayed against the counterexample, step 2 sets the slot to Y, so
step 3 sends X. Correct.

Two further corrections:

- **Line endings must be canonical on the wire (LF), converted at exactly one
  place** — CRLF on the Windows `SetClipboardData`, LF on read-back. Without
  this, a multi-line copy ping-pongs forever at poll cadence: the Mac sends
  `a\nb`, Windows stores `a\r\nb`, the listener sees a change, sends it back,
  AppKit normalises to `a\nb`, and round it goes. Fingerprint suppression cannot
  break that loop because the round trip is not byte-identical. Belt and braces:
  track the last-**sent** fingerprint too, so residual normalisation costs one
  extra message rather than an infinite series.
- **Seed both slots from current content at connect.** The slot starts empty, so
  the first poll reads as a change and one end clobbers the other's clipboard
  with no user action — and which end wins is a race.

**Stated, not solved:** simultaneous copies at both ends within one poll interval
leave the two clipboards permanently disagreeing (each suppresses the other's).
It is bounded — no loop — and a last-writer tiebreak is a design decision, not a
bug fix. AC3 asserts the bounded-ness rather than pretending the case is absent.

## 6. The Windows side — the first draft defended the wrong hazard

`OpenClipboard` failing while another process holds it is real, and bounded
retry is the right answer. **It is not the wedge.**

The wedge is *after* the open succeeds: `EmptyClipboard()` sends
`WM_DESTROYCLIPBOARD` to the previous owner — a **`SendMessage`**, not a post. A
hung previous owner blocks it **while we hold the clipboard open**, locking the
clipboard for the whole desktop. No retry policy on `OpenClipboard` touches
this, because we are already past it.

So: the open/empty/set/close sequence runs on a thread that owns nothing else,
with a watchdog that **reports** (never kills) if it has not returned within a
bound, and "clipboard sequence outstanding" becomes a state `--doctor` can show.

**Verified fine** (recorded so nobody re-litigates): a message-only
(`HWND_MESSAGE`) window does receive `WM_CLIPBOARDUPDATE`, because
`AddClipboardFormatListener` *posts* it — the message-only limitation bites the
legacy `SetClipboardViewer` chain, which we are not using. Delayed rendering is
avoided by passing real data to `SetClipboardData`, and this document forbids
"optimising" into it. A process dying while owning the clipboard is not a data
hazard: the `GMEM_MOVEABLE` handle belongs to the system after the set.

## 7. Size ceiling — new, and it is a session-safety issue

**There is no text ceiling in the codebase today, and the absence is dangerous.**
Traced: an oversize copy is framed, the receiver's `Reassembler` returns
`FramingError::Oversize` (`DEFAULT_MAX_PAYLOAD = 64 MB`), and `session.rs:197`
turns that into `SessionEnd::TransportFailed`. **Copying a large file's contents
would kill the remote desktop** — worse than the wedge this tranche prevents.

- `ClipboardPolicy` gains `max_text_bytes`, enforced as `min(policy, wire
  ceiling)` with the wire ceiling strictly below the framing limit, on **both**
  send and receive (a peer may ignore the rule).
- Over-ceiling content is **not sent and not truncated** — silently pasting half
  a document is a data-integrity bug. The local end reports once per change,
  naming sizes only.
- **Set the default at or below `HASH_PREFIX_CAP_BYTES` (256 KiB).** This is not
  arbitrary: above that cap the fingerprint hashes a prefix plus the total
  length, so a same-length edit past the prefix is **guaranteed** to be missed
  (`clipboard.rs:829`, and the test named for it). A ceiling at the cap removes
  that whole class by construction rather than documenting it as accepted risk.

## 8. Security — three leak paths the first draft missed

The clipboard carries passwords, OTPs and whole documents. The repo rule is
absolute, and the first draft's §7 was wrong in three ways.

- **The fingerprint must not be logged raw.** `content_fingerprint` is an
  **unsalted SHA-256**. For a 6-digit OTP, a PIN, or a short password the search
  space is trivially brute-forced, and the draft *also* permitted logging the
  length, which narrows it further. Anything logged for correlation is a
  per-session **salted, truncated** value; the salt is generated at connect and
  never logged. This is the tranche-3 hazard again — a mechanism declared safe
  that discloses a secret when the artefact is shared.
- **`Debug` derives are the tranche-3 pattern, and they are already live.**
  `ClipboardContent` and `ClipboardAction` derive `Debug` and carry raw content
  (`clipboard.rs:106`, `:123`). Nothing prints them today; nothing stops it, and
  the new wire type is where `debug!(?msg)` is most tempting. Every type in this
  path that can hold content gets a **hand-written `Debug`** printing kind,
  length and a salted fingerprint — never bytes. No error string may embed
  content, including third-party error text passed through. No
  `unwrap`/`expect`/indexing on content-derived data: a panic message is a log
  line you did not write.
- **"Nothing writes to disk" was false.** True of the Mac (stderr only); false
  of the server, which is where the new code lives — the agent writes
  `agent.log` and the server `server.log` on quench, unrotated, and those are
  read and quoted verbatim during diagnosis (tranche 4 §13 does exactly that).
  Every rule here applies with *more* force to the server thread, and its
  boundary catches panics rather than letting a message reach the log.

**Accepted egress, stated:** content applied to the Mac pasteboard goes to
`NSPasteboard.general`, which macOS syncs to the user's other devices via
Universal Clipboard when enabled, and to any clipboard-history manager. A user
copying to their Mac clipboard arguably expects Mac clipboard behaviour, so this
is accepted rather than fixed — but it is the largest hole in "we know where the
content goes", and a concealed-type marker is worth investigating later.

## 9. Out of scope (stated, not silently)

Images (the format byte reserves them), files, RTF/HTML, and fixing
MDR-BUG-FLUX-00011/00012.

## 10. Acceptance criteria — rewritten; the first draft's oracles could be fooled

1. **Mac → quench, live.** For each of single-line ASCII, multi-line, non-ASCII,
   and already-CRLF payloads, each carrying a **fresh nonce**: assert quench's
   clipboard does *not* already contain the nonce; set the Mac pasteboard; read
   quench's **interactive-session** clipboard back **through a path that did not
   perform the write**; assert byte-exact equality. Then repeat with the network
   path deliberately broken and assert the check goes **red** — an oracle that
   has never failed proves nothing.
2. **quench → Mac, live.** The mirror, read back through an `arboard` handle
   distinct from mdrdp's own, with the same negative control.
3. **Echo, asserted on the wire in both directions.** Exactly **one** message
   each way per user copy, and **zero** further messages over the next 8 poll
   intervals with both clipboards untouched. Both halves — a zero-only assertion
   passes on an implementation that sends nothing. Includes the A/B/A re-copy
   sequence from §5 and at least one run against the **real** quench clipboard,
   because the loop originates in OS normalisation no fake reproduces.
4. **No wedge under OS refusal**, two halves. Unit: with the sequence stuck, the
   thread's own loop keeps making progress. Live on quench: a helper holds the
   clipboard for 10 s; the thread reports, does not spin (CPU sampled), and the
   next transfer succeeds within a stated bound. `check-windows.sh` type-checks
   this code but never runs it, so the live half is the only real evidence.
5. **Oversize is refused, not fatal.** A payload above the ceiling is never
   framed, the session survives, and the local end reports size and limit.
6. **Old host degrades safely** — and this is a safety gate, not a courtesy.
   Against the deployed 0.4.0 agent, before any tranche-5 deploy: the client
   reports clipboard unsupported, sends **zero** upstream clipboard bytes, and
   **a keystroke still lands afterwards**, proving the input channel survived.
7. **Policy on the wire.** `to_remote` off → 0 client→server messages after a
   local copy. `from_remote` off → an inbound message is discarded **before the
   payload is decoded or allocated**, and the pasteboard is byte-identical
   before and after.
8. **Soak — the requirement itself.** Board claim posted before, released after.
   ≥8 h; a ≥4 h run is a **provisional gate and must be labelled as such**, not
   a discharge of "all-day". Per cycle a transfer each way, plus hourly a
   60-transfer burst at 1 Hz and a 5-minute window with a competing
   clipboard-owner process on quench — because the wedge this product exists to
   beat appears under bursts and contention, not at one transfer per 30 s.
   Payloads carry a fresh nonce and are **synthetic by construction**, never a
   real secret, so the harness is free to record them on mismatch. Recorded and
   quoted: versions, host, start/end UTC, attempted/arrived, **arrival latency
   as n/min/median/p95/max**, every non-arrival with timestamp and direction,
   per-direction wire message counts, client RSS and queue depth sampled every
   60 s against a stated threshold, and any competing-session event. A run
   interrupted by another session is **void, not failed**. Two consecutive
   non-arrivals in one direction is a **wedge**: stop and capture state. The
   harness must never recreate the session or the clipboard handle mid-run —
   that masks the failure being tested.
9. **Hygiene**, plus a mechanical leak check: a temporary `debug!(?msg)` at the
   send site must emit no payload byte. That test starts red.

**Named as tranche work, because AC1/AC8 cannot run without it:** an agent verb
to read the interactive-session clipboard. An ssh session on Windows runs in a
different session and window station, so `Get-Clipboard` over ssh reads the
wrong clipboard. That verb is also a second `OpenClipboard` consumer and will
contend with §6's listener — the instrument perturbs what it measures, and the
design must account for it.

## 11. Risks

- **The soak is the long pole and collides with quench's one-session rule.** An
  8 h exclusive hold blocks every other live check for the whole tranche, and a
  competing connect is indistinguishable from a wedge unless the harness detects
  and voids. Worse: an RDP logon by another agent kills capture but **not** the
  clipboard path, so a naive soak would report PASS on a session that was broken
  for an hour. Sequencing must be agreed, not assumed.
- The message-only window is new Windows surface on its own thread; if its loop
  dies the clipboard degrades and nothing else may.
- A `MSG_CLIPBOARD` id must not collide with an input record kind: a stray byte
  `5` is a valid `MouseMove`, so a framing mistake would inject mouse motion
  rather than error cleanly.

## 12. Review record

Two adversarial reviewers, both against the first draft, converging
independently on the §0 blocker. **Adopted: essentially everything.** The draft
was wrong about the uplink channel, wrong about echo suppression, wrong about
which Windows call wedges, wrong that a size ceiling existed, wrong that nothing
writes to disk, and wrong that logging a fingerprint is safe. Its ACs could pass
against a dead feature via a stale clipboard.

**Refuted by the reviewers' own checking (recorded, no change):** server→client
unknown-message skipping is genuinely safe (`session.rs:217` + length-prefixed
framing); the serde-defaulted header flag genuinely costs a deployed host
nothing (`probe.rs` gates on `wire_version` only); `ArboardClipboard`'s
drop-handle-on-error property is real and load-bearing; bounded retry on
`OpenClipboard` is the right rule (just insufficient); the message-only window
and delayed-rendering avoidance are correct; AC3's "assert on the wire, not by
watching the content look right" was the right instinct.
