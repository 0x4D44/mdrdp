# RESEARCH — downstream unknowns for P2b, P2c, P3a and P7

2026-08-14 · four parallel source investigations, each independently fact-checked against
the cited lines by a second agent

Three tracks were verified accurate (citation nits only). **The P7 track was returned
inaccurate** by its checker and is labelled accordingly below — its direction is useful,
its load-bearing claims are not currently reproducible.

Two findings change the plan's shape and are stated first.

---

## 1. P2b cannot prove session resumption with these crates. **Upstream change required.**

This is definite, and it retires an open question rather than deferring it.

**Receive side:** `ironrdp-pdu` fully models the server cookie — `SaveSessionInfoPdu`
decodes into `LogonInfoExtended.auto_reconnect: Option<ServerAutoReconnect>`
(`logon_id`, `random_bits[16]`, i.e. ARC_SC_PRIVATE_PACKET). But the only handler in
`ironrdp-session` logs it at debug and returns an empty output vector. No
`ProcessorOutput` variant can carry it out.

**Send side:** `ironrdp-pdu` *can* encode the 28-byte ARC_CS cookie via
`ExtendedClientOptionalInfo`, but `connector::Config` has no field for it,
`create_client_info_pdu` is private, and the connector never sets
`AUTORECONNECT_SUPPORTED` in its General capability set.

**Consequence.** A client can *sniff* the cookie today — `ActiveStage::process` takes the
raw frame and the PDU decode helpers are public — but it cannot **replay** one without
patching the connector. So P2b's pass condition ("prove the same Windows session was
resumed, not a fresh logon") is unreachable as things stand.

The upstream change is small and well-shaped: a `reconnect_cookie` field on `Config`,
extend the builder chain, add the capability flag — roughly 20–40 lines across two files.
**The real cost is not the plumbing**: the 28-byte ARC_CS packet is an opaque `[u8; 28]`
in these crates, so its field layout and how the security verifier is derived must come
from the spec or a reference client, and be validated live.

**This is an architectural fork and I am not deciding it.** The options are: vendor/fork
`ironrdp-connector`; contribute upstream and wait; or re-scope P2b to "reconnects quickly
and correctly" without claiming session *resumption*. Flagged for Arthur.

## 2. EGFX may not open for us at all — and it is one experiment to find out

`ironrdp-connector` 0.10.0 **never sets `RNS_UD_CS_SUPPORT_DYNVC_GFX_PROTOCOL`** in the
client core early-capability flags, and exposes no `Config` knob to set it. FreeRDP's P1b
trace shows FreeRDP *does* advertise it.

If `temper` gates the graphics channel on that flag, P2c turns from half a day of wiring
into a connector fork (a two-line change in `create_gcc_blocks`, plus an upstream PR).

**Settle it empirically before designing around it:** run the connect with DVC registered
and log whether a `DYNVC_CREATE_REQ` for `Microsoft::Windows::RDS::Graphics` ever arrives.
`ironrdp-dvc` logs "Got DVC Create Request PDU" at debug, which our stage-capture
allowlist can observe by target without touching payload.

### How P2c is wired (verified, and a compiled sketch exists)

- **Register `DrdynvcClient` as a static channel *before* connecting.** It is announced in
  the MCS Connect Initial GCC network block, so it cannot be added afterwards. Our current
  `connect()` does not do this — that is the first change.
- Pre-register the graphics channel inside it:
  `DrdynvcClient::new().with_dynamic_channel(GraphicsPipelineClient::new(handler))`.
- After `connect_finalize`, build an `ActiveStage` from `ConnectionResult` and run a
  read → `process` → write-back loop over `ActiveStageOutput::ResponseFrame`.
- Everything else is automatic: DRDYNVC answers the caps request and the create request,
  `GraphicsPipelineClient::start()` emits `RDPGFX_CAPS_ADVERTISE`, and the server's
  confirm lands in `GraphicsPipelineHandler::on_capabilities_confirmed`.

A 128-line sketch was written and compiled clean offline against the real crates.

**Second risk:** `on_wire_to_surface2` — which is where RFX Progressive arrives — is an
empty default. So "receive a live graphics message" is reachable, but "decode one" is not.

## 3. P3a is ~600–1200 lines of glue, not a codec implementation — but the risk is elsewhere

**Both decoders already exist** and neither has a single call site outside its own tests:

- `ClearCodecDecoder::decode(&mut self, data, width, height) -> DecodeResult<Vec<u8>>`,
  BGRA out, with persistent V-bar and glyph caches across frames.
- `ProgressiveDecoder::decode_bitmap(ctx_id, w, h, data) -> Result<Vec<DecodedTile>, _>`,
  RGBA 64×64 tiles out, handling TILE_SIMPLE / TILE_FIRST / TILE_UPGRADE.

RLGR, SRL, DWT, quantisation and the ClearCodec three-layer composite are all written.

**The integration seam needs no fork for ClearCodec.** `ironrdp-egfx` dispatches
`WireToSurface1` on `Codec1Type`; ClearCodec (0x8) falls to the `_` arm and is handed to
`handler.on_unhandled_pdu()`. Implement `GraphicsPipelineHandler`, decode there.

**The bulk of the work is a surface store that does not exist upstream.**
`ironrdp-egfx`'s `Surface` is metadata only — it holds no pixels. `SolidFill`,
`SurfaceToSurface`, `SurfaceToCache` and `CacheToSurface` are all handler no-ops. Pixel
storage, blitting, the offscreen cache and output compositing are ours: ~400–700 lines,
the dominant chunk.

### Two specific hazards

**A codec id `ironrdp-egfx` does not know is fatal to the entire ZGFX payload, not just
that PDU.** `process()` decodes *all* PDUs into a `Vec` in a first pass before handling
any, so one unknown codec id means nothing in that batch is processed — including PDUs
that preceded it. `Codec1Type` has no 0x9 variant.

**So the highest-value cheap measurement is: which PDU carries CAPROGRESSIVE?**
`Codec2Type` *does* have `RemoteFxProgressive = 0x9` and `WireToSurface2` is a safe
pass-through. If progressive arrives on WireToSurface**2** we are fine; on WireToSurface**1**
it cannot even be parsed and takes the batch down with it. Settle by grepping a FreeRDP
trace for `WIRETOSURFACE_1` / `WIRETOSURFACE_2` adjacent to CAPROGRESSIVE, rather than
grepping codec ids alone as P1b did.

### Correctness is unproven, and that is the real risk

The fact-checker downgraded "the decoders are complete" to **"all code paths are present,
correctness unverified"** — correctly. Specifically: the **ClearCodec bands / V-bar layer
has zero decoder-level test coverage**, and that is the dominant path for text and UI,
which is exactly this workload. There is no end-to-end `decode_bitmap` test and no RLGR
tests. Neither decoder has ever been run against real server bytes.

Also found: ClearCodec's NSCodec subcodec variant is a **silent no-op** — a region encoded
that way leaves whatever was underneath, raising no error. And the progressive decoder
**ignores `ProgressiveRegion.rects`**, so no clipping to the damaged region is applied.

**Build a byte-capture harness before writing the glue**, so first-light failures are
reproducible offline instead of only live against `temper`.

## 4. P7 keychain: two gates, not one — *findings not currently reproducible*

**This track's checker returned it inaccurate**, and the two load-bearing claims are among
those that can no longer be re-verified (the throwaway keychains were deleted). Treat the
direction as plausible and the specifics as unconfirmed.

The claim is that there are **two** cdhash-bound gates and self-signing only fixes one:

1. **The trusted-application ACL** stores a code requirement. Unsigned, that is
   `cdhash H"…"` — dead every rebuild. Self-signed, it becomes
   `identifier "mdrdp" and certificate root = H"<cert sha1>"`, stable across rebuilds.
   *This part was reproduced today by the checker.*
2. **The `partition_id` ACL** exists only on the **login** keychain. Its value derives
   from the creating process's signature: `teamid:<ID>` if present, else `cdhash:<hash>`.
   A self-signed cert produces no Team ID, so on the login keychain a self-signed binary
   is still partitioned by cdhash — and still breaks on every rebuild.

If that holds, `-A` can only be replaced by *both* signing every build with one fixed
identity *and* moving the credential out of the login keychain — which also needs a
credential-store shim, because `keyring` cannot target a keychain file.

**One command would settle it, and only Arthur can run it** (it needs the login keychain
password, which I will not ask for):

```
security set-generic-password-partition-list \
  -S 'apple:,apple-tool:,signingid:mdrdp' -s mdrdp -a <account> -k <login-password>
```

If `signingid:` is honoured as a partition match for a self-signed binary, the whole
dedicated-keychain detour disappears and the Rust-side work drops to zero. Worth trying on
a throwaway item first.
