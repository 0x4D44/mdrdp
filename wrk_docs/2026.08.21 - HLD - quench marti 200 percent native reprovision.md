# Quench `marti` 200% native reprovision

Status: SELF-APPROVED (revision 3)

## Scope and outcome

Reprovision quench's existing rhydra installation so its supported unlocked console is
the `marti` Windows profile associated with `user@example.com`, its 5120x2880 IDD
desktop uses 200% Windows scaling, and Arthur can open the saved Quench connection without
passing `--user`, `--ssh-user`, `--native`, or `--fullscreen`.

This is primarily a one-time host-policy change. It does not add dynamic Windows logon or
user switching to rhydra, change credentials, or reboot quench. Live acceptance exposed
one blocking shipped defect in the agent's DPI-unaware scale measurement; the smallest
correct fix and its focused regression are now in scope.

## Approach

1. Pin and build the current integrated trunk's macOS client plus Windows agent, server,
   creator, and signed driver artefacts. Record current sessions, processes, tasks, agent
   health, task principal/logon type, process session IDs, and a recoverable description of
   the `ano` ownership state before mutation. Verify the Mac's live primary display is
   5120x2880 physical at 200% before making the host change. Prove that SSH login `marti`
   has the elevated token required by deploy before taking down the working stack.
2. Immediately before mutation, re-query sessions and require the target to still be
   disconnected `marti`. Quiesce the old agent while `ano` still owns the console, then run
   `tscon` as the elevated owner `marti` and require `marti` to be the active console user.
   An access-denied transfer fails closed: reinstall the untouched `ano` stack and stop
   without renaming it.
3. Avoid the tracked same-version fast-path defect without changing shipped code: move the
   quiesced v0.5.0 directory to a recoverable non-versioned backup name, and run `mdrdp
   deploy` as SSH login `marti` with current integrated-trunk artefacts. Require the
   resulting task principal/logon mode and the agent, creator, and server process session
   IDs to name `marti`'s interactive session.
4. Measure the IDD scale after transfer. If it is already 200%, retain it. If it is 100%,
   use a temporary explicit 5120x2880 native session (the deliberate 100% compatibility
   path) to change Windows Display Settings to 200% in the `marti` interactive profile;
   reconnect fullscreen and require the client's exact 200% prepare-display check to pass.
   Launch that reconnect explicitly fullscreen and close it cleanly so it overwrites the
   temporary session's remembered windowed state. If Windows initially selects another
   scale such as 150% or 300%, use a conventional RDP connection to the same `marti`
   profile to choose 200% in Display Settings, then recover the expected IDD/console state
   before the native check. Do not write undocumented DPI registry values or add a hidden
   scale setter.
5. Correct the password-free saved Quench favourite to use `quench.lan.example`, explicit
   `native = "always"`, and fullscreen while retaining its existing Windows account and
   keychain account. OpenSSH configuration already selects its login and key, so no
   `ssh_user` is stored.
6. Validate one clean `mdrdp Quench` native connect at 5120x2880, 200% scale, with a complete
   desktop, input, a real rendered-audio signal, a clipboard round trip, clean close, no
   viewer afterward, and an all-green doctor report.

If `marti` deployment fails, first run the partially installed v0.5.0 agent's sanctioned
`uninstall` and verify ports 9500–9503 and all three owned process images are clear. Return
the re-queried `ano` session to the console by running `tscon` as its elevated owner. Move
any failed partial `C:\mdrdp\v0.5.0` to a separate recoverable non-versioned name, then move
the preserved directory back to the exact path, install/start its agent as `ano`, and prove
the task principal/logon mode, child process session IDs, and doctor state before stopping.
A 200% choice already applied to `marti` may remain—it is the requested profile policy and
does not alter `ano`. No reboot is part of either path.

## File and state impact

- Repository: this HLD, a chronological journal, and redacted host-state evidence only.
- Shipped code: keep the Windows session agent's reconcile thread per-monitor-v2 DPI aware,
  but measure the user's effective monitor DPI rather than the monitor's recommended scale,
  plus focused conversion and Windows API regressions.
- Local user configuration: mdrdp's existing Quench favourite; no password or key material.
- Quench: console ownership, rhydra scheduled-task principal/install, and the `marti`
  profile's IDD scale. Versioned `C:\mdrdp\` deployment remains the product-owned layout.

## Acceptance criteria

1. `query session` reports `marti` as the active console user and `ano` is not active.
2. `rhydra-agent` and its creator/server children run in the `marti` interactive session;
   the installed task principal is `marti`, its logon mode is interactive, and agent
   v0.5.0/wire v5 is healthy.
3. A fullscreen native probe reports and verifies 5120x2880 at 240 Hz and Windows scale
   200%; the final frame has both tiles and zero decode errors.
4. `mdrdp Quench` needs no identity or transport flags and reaches the same `marti` desktop.
5. A real audio render produces nonzero correctly formed client audio, and a unique
   clipboard value completes a round trip without content entering logs or evidence.
6. Closing the window is clean; post-run doctor is green and reports no viewer.
7. No reboot, credential mutation, or undocumented DPI mutation occurs; shipped-code impact
   is limited to the tested DPI-awareness fix recorded as `MDR-BUG-FLU-00028`.

## Decision log

- Keep native v1's explicit host posture: one configured unlocked console owner. Dynamic
  logon would require the deferred SYSTEM service/session broker and is outside this change.
- Keep SSH identity separate from Windows identity. OpenSSH config already resolves
  `quench.lan.example`; `--user` remains an RDP credential and is not repurposed.
- Prefer the supported Windows Display Settings UI for the one-time per-profile DPI choice.
  The public Windows APIs query scaling but do not expose the required per-monitor setter.
- Build/deploy only integrated trunk. Do not reuse possibly stale artefacts from old task
  worktrees even when their version strings match.
- The two native reviewers found that partial deployment rollback, task/session ownership
  oracles, exact native favourite selection, Mac-display preflight, and real audio/clipboard
  stimuli were underspecified. All survive refutation and are incorporated above.
- Rejected: final SSH may remain `ano`; deploy's console-user equality gate applies during
  deployment only, while the native tunnel is deliberately independent of desktop owner.
  Also rejected: uploaded deploy probe scripts are the deployer's documented inert preflight
  state, not an unplanned mutation.
- The single Claude/Fable review confirmed the same-version avoidance and measured-scale
  design. Its useful findings added an early `marti` elevation proof, partial-directory
  rollback handling, a non-100/200 scale escape hatch, explicit fullscreen-state repair,
  and lower-churn transfer ordering. Its fleet-board suggestion was rejected: board state
  cannot prove that arbitrary interactive work is idle, while Arthur explicitly authorised
  this host transition and live process/session evidence remains the relevant guard.
- Live 200% acceptance discovered `MDR-BUG-FLU-00028`: Windows visibly applied 200%, but
  the DPI-unaware agent mixed physical `EnumDisplaySettings` geometry with a virtualised
  `MonitorFromPoint` lookup and reported the scale as unknown. Fix the DPI boundary
  rather than weakening the exact scale gate or bypassing it operationally.
- Code review rejected constructing `WinOps` in the Windows test because its constructor
  can recover a real audio lease. The applied form tests a side-effect-free initialization
  seam and sets only the reconcile thread. That also remains valid when an executable
  manifest or test harness has already fixed process-wide awareness.

## Revision 2: effective scale measurement

The integrated DPI-awareness fix made the IDD monitor lookup reliable, but a freshly
deployed agent then reported 180% while Windows Display Settings visibly retained the
selected 200%. The observed behaviour is consistent with `GetScaleFactorForMonitor`
returning a monitor/process scale rather than the live effective DPI assigned to content;
the product gate needs that live content DPI regardless of the API's undocumented cause.

The adversarial review rejected the first revision's direct `GetDpiForMonitor` proposal:
Microsoft explicitly does not support that API from a per-monitor-aware thread. Keep the
per-monitor-v2 reconcile-thread context and physical midpoint lookup, create a one-pixel
hidden `STATIC` window at that midpoint using non-activating tool-window popup styles, query
it with the supported `GetDpiForWindow`, and destroy it before returning. A small same-thread
RAII guard makes destruction unconditional. Convert its DPI to the nearest integer
percentage relative to 96 DPI. Reject a zero DPI result and tolerate the one-DPI rounding
used by Windows for standard non-integral menu scales such as 180%. A failure to establish
the reconcile thread's PMv2 context is fatal rather than permitting a confidently wrong
100% result. No new dependency, feature flag, registry write, persistent window, message
loop, or scale setter is introduced.

Revision 2 acceptance adds these explicit checks:

- pure conversion regressions cover 0 -> unknown, 96 -> 100%, 192 -> 200%, and 173 -> 180%;
  each new regression is observed failing once before the implementation is restored;
- the deployed agent itself, after its production thread initializer, proves the real query
  path reports 200% on Quench's 5120x2880 IDD while Display Settings independently shows
  200%; record the redacted status output in the repository evidence document;
- with that same agent process running, change the IDD through Display Settings from 200%
  to 100% and back to 200%, requiring status to track both values without an agent restart;
  and
- the deployed agent reports `desktop_scale_percent=200`, after which the existing exact
  5120x2880 fullscreen acceptance continues unchanged.

Decision: keep the existing exact scale gate. Treating 180% as equivalent to 200% would
hide a real desktop-policy mismatch and make the fullscreen sizing contract unverifiable.

Review disposition: both independent reviewers' PMv2/API-context finding survived mutual
refutation and caused the `GetDpiForWindow` redesign. Their production-context and
reproducible-evidence findings survive and are reflected in the deployed-agent oracle above.
Zero-DPI coverage survives and is added. Axis mismatch is rejected because
`GetDpiForWindow` returns one DPI value. Accessibility overrides are deliberately part of
the product's effective-scale contract: rhydra must gate on the DPI Windows actually gives
content, not on the text printed beside a settings control.

The one-pass Claude/Fable review accepted the supported `GetDpiForWindow` direction and
added fail-fast PMv2 initialization, non-activating popup styles, unconditional same-thread
window destruction, and live scale-change tracking. Its claim that the agent might have
predated the 200% selection was rejected by the deployment chronology: the 180% observation
came from a fresh post-change deployment. Its differential test against
`GetDpiForMonitor` was rejected because that unsupported API already disagrees on the exact
host under test. The old value remains historical evidence; the new binary need not emit
both. Custom typed scaling is outside this Quench change; the percent contract remains the
standard Windows scale menu values used by fullscreen sizing.
