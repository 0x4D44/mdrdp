Parent: `wrk_docs/2026.08.18 - HLD - native product shape and session ownership.md`

`wrk_docs/2026.08.19 - PARK - tranche 6 audio needs a render endpoint on the host.md`.
Evidence: `wrk_docs/evidence/2026.08.19 - audio-probe on quench and temper.md`.

**Revision 2**, after two adversarial reviews. Revision 1 is in this branch's history;
it was not good enough and the review record (§11) says why.

## 1. What this delivers — and what it does not

**It delivers the audio transport, not audio.**

Landing: the auxiliary-channel outbox, the `MSG_AUDIO` frame, the host-side source
abstraction, and the Mac playback path — proven end to end against deployed rhydra on
quench with a synthetic tone generated on the host.

**Not landing: a single sample of real Windows audio.** Neither fleet host has an
audio render endpoint (§2), so the WASAPI capture stage cannot execute even once. It
is written, type-checked and unit-tested against a fake, and it has never run.

This distinction is the document's most important sentence, and it is first rather
than in a footnote because revision 1 opened by promising "what the rhydra session
plays comes out of the Mac's speakers" while no acceptance criterion required an
audible sample. A design whose headline and whose test suite describe different
products is one nobody can hold to account.

## 2. The constraint — and the decision that is still Arthur's

**Neither fleet host has an audio render endpoint.** quench 6 endpoints / 0 active;
temper 5 / 0 active; both return `0x80070490` from `GetDefaultAudioEndpoint`. Raw
output in the evidence file. Both are headless with nothing in the jack.

WASAPI loopback attaches to a *render* endpoint. With none, there is nothing to
attach to — and applications on those hosts cannot render audio at all, so there is
no audio to capture. Microsoft's RDP does not capture harder; it **supplies a
per-session virtual endpoint** and reads that.

**The PARK document asked Arthur a four-way question and he has not answered it.** He
directed that audio be built now, which is why this tranche is live; he did not choose
between a jack plug, a driver-level jack-detection override, our own virtual audio
device, or descoping. This design therefore proceeds on the **descope** branch by
default:

> **A host with no render endpoint is a supported configuration.** It reports the
> absence, plays nothing, stays healthy, never retries in a loop and never looks like
> a bug.

**That default is recorded as an unmade decision, not a settled one.** It is written
this way so that when an endpoint appears, capture starts working with no other
change.

**The cheapest answer has been requested and not yet actioned: a 3.5 mm plug in
quench's jack.** It makes the Realtek endpoint ACTIVE on the console session — the
session rhydra owns — at zero risk, instantly reversible, and it moves this tranche
from "transport" to "feature" in one step. Everything else on the list costs orders of
magnitude more. It is named here because a design shaped by the absence of a two-pound
part should say so in the design, not only in a chat message.

## 3. Wire format

New messages on the **auxiliary channel** (port 9503), which the parent HLD designates
for audio, ranking above clipboard.

```
MSG_AUDIO = 0x21              host -> client
  u32 LE   sample_rate        validated: 8000..=192000
  u8       channels           validated: 1 or 2
  u8       format             0 = PCM16 interleaved; other values rejected
  u64 LE   capture_pos        host capture sample position of the first sample
  [i16 LE] samples            interleaved; len % (channels*2) == 0, enforced

MSG_AUDIO_CONTROL = 0x22      client -> host
  u8       enable             0 = stop capturing, 1 = start
```

Kind bytes stay disjoint from `MSG_CLIPBOARD = 0x20` and input kinds `1..=7`.

**`capture_pos` is the change that revision 1 most needed.** Both reviewers reached it
independently. Without a timing reference the client cannot distinguish "the host's
clock is 30 ppm fast" from "800 ms of silence was elided" from "12 frames were dropped
in the outbox" — all three present identically as a change in ring depth, and both
correction mechanisms act on depth alone. `capture_pos` **counts elided silence**, so a
jump in position is a silence gap, a missing frame is a loss, and drift is a slope you
can measure. It is 8 bytes against a ~1920-byte payload. Adding it later would be a
wire break, which is precisely the risk the tranche-6 journal refused to take.

**`format` is a tag, not padding.** Declaring it now makes any later codec purely
additive.

**`MSG_AUDIO_CONTROL` exists because "no negotiation" over-generalised.** Revision 1
argued there was nothing to negotiate; there is one thing — on/off. Without it audio is
server-push and always-on, so a client that does not want it still pays the bandwidth
on a channel the parent HLD says must never back up video. Capture starts only when a
client asks. This is a one-byte request, not a handshake with states to wedge in.

**Sizes are named, not implied:**

| Constant | Value | Why |
|---|---|---|
| `FRAME_MS` | 10 | One WASAPI buffer period; 1920-byte payload at 48 kHz stereo |
| `MAX_AUDIO_BYTES` | 16 KiB | **Session-safety, not tuning** — see below |
| `AUDIO_FIFO_FRAMES` | 20 | 200 ms of outbound buffer before drop-oldest |

`MAX_AUDIO_BYTES` is enforced on **both** send and receive, exactly as
`MAX_CLIPBOARD_BYTES` already is and for the same reason — a peer may ignore it. The
client's reassembler otherwise permits `DEFAULT_MAX_PAYLOAD` = 64 MiB, and one
oversized frame would decode to a 128 MiB `Vec<f32>` and then be pushed into the ring
one sample at a time *while holding the lock the cpal realtime callback needs*. That is
a guaranteed device xrun from a single bad length field. Every header field is
validated on receipt; a malformed frame is counted and dropped, never interpreted.

**PCM16, not Opus** — ~1.5 Mbps against video's tens on this LAN, and no new
dependency, which the loop's hard stops forbid without Arthur's word.

## 4. The outbox: bounded priority, not strict priority

Today the aux channel's outbound side is `auxchan::Slot` — depth-1, keep-latest. Right
for a clipboard (a superseded payload was never the current content). Wrong for a
continuous stream, where keep-latest delivers chop.

The replacement is one **`Outbox`** holding both, **behind a single mutex and a single
condvar**. That is stated as a requirement because composing the existing `Slot` (which
owns its own mutex *and* condvar) with a second queue gives two condition variables,
and `std` cannot wait on both: a taker parked on one would miss `put()` and `close()`
on the other, silently regressing two properties this repo deliberately made failable
(`auxchan.rs` — the wake-on-queue and wake-on-close tests).

- `audio`: bounded FIFO, `AUDIO_FIFO_FRAMES` deep, drop-**oldest** on overflow. Oldest
  because when we are behind, stale audio is worthless and the listener wants to catch
  up. Drops are counted.
- `clipboard`: keep-latest slot, behaviour unchanged.

**Priority is bounded, not strict.** Revision 1 said `take()` drains *all* pending
audio first. Both reviewers identified the same bug: audio is continuous, so under the
sustained back-pressure the FIFO exists to survive, audio is *always* pending and the
clipboard is **never** selected. The starvation lasts as long as the congestion, and
its window is exactly "audio is playing", which is also when the user is working.
Product requirement 1 is that the clipboard survives an all-day soak with zero wedges;
strict priority makes a wedge reachable by construction.

The policy instead:

- At most **8 audio frames (80 ms)** are drained before a pending clipboard payload is
  admitted.
- Large clipboard payloads are **chunked at 16 KiB**, so priority is re-evaluated up to
  16 times inside a 256 KiB transfer rather than once.

Chunking matters independently: `write_all` is atomic with respect to the priority
decision, so one 256 KiB write on a congested tunnel blocks the writer for seconds and
the audio FIFO overflows regardless of ordering. Arthur's principle — video critical,
audio continuous, clipboard bursty bulk — is preserved. What changes is that the
clipboard's worst case becomes a number we can write down.

**On close, queued audio is discarded and a pending clipboard payload is still
delivered.** `close()` is followed immediately by `socket.shutdown()`, so a writer
draining 200 ms of audio first would lose the last clipboard copy — breaking a property
this repo already pins ("a copy made a moment before teardown should still reach the
peer").

**Audio is decoded and pushed on its own thread, never on the reader loop.** That loop's
clipboard callback can block on the macOS pasteboard, and both ends carry long comments
explaining that a blocking clipboard call must not stall anything else. Decoding audio
there would let a stuck pasteboard write produce a guaranteed audible dropout.

## 5. Host capture, and the tone as a product feature

`win::audio::LoopbackCapture` behind an `AudioSource` trait, so the pipeline is
testable without WASAPI:

- Default render endpoint, `AUDCLNT_STREAMFLAGS_LOOPBACK`, shared mode; mix format
  (typically 32-bit float) converted to interleaved PCM16.
- **No endpoint**: report once, publish it in the stats header, idle. Never a tight
  loop, never an error.
- **Silent buffers** (`AUDCLNT_BUFFERFLAGS_SILENT`) are not sent, but `capture_pos`
  still advances across them — which is what keeps elision distinguishable from loss.
- Capture is per-connection, stopped by an explicit stop signal the WASAPI event wait
  observes, and stopped before `serve_one` returns so the next `accept` starts clean.

**The 440 Hz tone is a `--doctor` rung, not a test fixture.** Revision 1 justified it as
both and delivered only the fixture half. It now has a product job: the doctor runs the
tone end to end and **verifies the recovered signal is 440 Hz at the expected
amplitude** (Goertzel at the client), answering "is the audio path working?" without
needing anything to be playing. That is requirement 4 (visibility) applied to audio.

It also upgrades the acceptance suite: a frequency check fails on channel swap,
endianness, resampling and gain faults that a frame counter cannot see — and, unlike a
frame counter, **it cannot silently not-run**, which is the lesson this repo paid for
twice on tranche 5.

## 6. Client playback — what it actually costs

Revision 1 called this "almost free". It is not, and the error mattered.

`src/main.rs:1023` reads `settings.audio.playback && !is_native`, so the native path
gets `AudioPlayback::disabled`, which latches `ring.disable()` permanently — there is no
re-enable in the module. **Every `ring.push()` on the native transport is discarded
today, and no cpal device is ever opened.** The session epilogue is likewise gated on
`!is_native`, so nothing would be reported either.

So this tranche must: open the device for native sessions, thread the device format into
the native session, add the native reporting branch, and make `remap_channels` and
`AudioRing::is_enabled` visible to it. The failure mode if missed is precisely the one
`src/audio.rs` warns about — "silence that looks like a working connection".

What *is* reused, and is genuinely already tested: `AudioRing`, `AudioPlayback`, PCM16
decode, channel reconciliation, linear resampling.

**Honest note on the foundation:** `MDR-BUG-FLUX-00019` is open — mdrdp requests
`rdpsnd` and neither fleet host opens an audio channel, so audio output does not
currently work on this fleet through *any* path. These are different stacks and building
the second is defensible, but the first is broken and undiagnosed.

## 7. Drift — stated correctly this time

Revision 1 said "`AudioRing` writes silence on underrun; the missing half is over-fill."
**That was wrong.** Over-fill is already handled: `RingBuf::push` evicts oldest-first at
capacity and returns the count, surfaced as `overruns`. Unbounded growth is impossible
today.

The real gap is different and smaller. `RING_BUFFER_MS = 400`, so a +ppm host clock
fills the ring and **parks it at the ceiling**: steady-state latency becomes the full
400 ms the user did not have at minute one, and every excess sample is then evicted
singly and continuously — not a clean periodic drop but a persistent sub-sample
discontinuity. That is product requirement 3 reproduced inside the new feature.

The fix is a **high-water mark below capacity**: above it, drop a whole frame to catch
up, counted separately from `overruns`. `capture_pos` is what makes this actionable —
without it the mechanism would be correcting a depth reading that means four different
things.

The native path also has no reason to carry RDPSND's 150–250 ms server lead, so a
smaller native ring is likely the simpler half of the fix. Both are settled by
measurement (AC7), not assertion.

## 8. Acceptance criteria

**AC1–AC3 and AC5 run over ssh against deployed rhydra on quench, release build** — not
against in-memory pipes. This is a protocol change and the repo's rule is that protocol
changes need a real server.

- **AC1 — the tone arrives intact.** With the host tone source, the client recovers a
  440 Hz ±1 Hz sine at expected amplitude in both channels, over n ≥ 5 runs. Frequency,
  not frame count: a counter cannot see pitch, channel-swap or endianness faults.
- **AC2 — audio is prioritised.** With both queued, audio frames are taken first.
- **AC3 — the clipboard cannot starve.** With the audio FIFO kept permanently full, a
  queued clipboard payload is still sent within 80 ms. *This is the criterion revision 1
  omitted, and its absence was the tell.*
- **AC4 — a malformed frame is rejected, not interpreted.** Oversize, bad rate, bad
  channel count, and a payload length not a multiple of `channels*2` are each counted
  and dropped; the session survives all four. The alignment case matters because one
  odd-length frame flips ring parity and swaps L/R for the rest of the session.
- **AC5 — silence costs nothing, and the fixture is proven to have run.** An explicitly
  *silent* source produces zero audio bytes while `capture_pos` still advances. The
  advancing position is what distinguishes this from a source that never started —
  without it, AC5 passes on quench today for the wrong reason, because a host with no
  endpoint also sends zero bytes.
- **AC6 — no endpoint is a supported state.** On quench: reported once, nothing sent,
  session healthy for its full duration, and rhydra's CPU delta < 1 s over a 60 s run
  (release build, measured from `Get-Process rhydra-server`).
- **AC7 — drift, soak-class.** An ≥8 h tone run, sampling client ring depth every
  60 s: report n, min, median, max, and the trend. Discharges §7 against the two clock
  domains that matter here — the host's capture timer and the Mac's cpal device clock.
  *Not* the WASAPI capture-device clock, which needs an endpoint; that limit is stated
  in the result.
- **AC8 — audio does not back up video.** Video frame-gap distribution (n, p50, p95,
  max) with audio idle vs streaming at full rate, quench, release build. The parent
  HLD's principle is that nothing lower-priority may back up video; this tranche adds
  the channel's first continuous load, and §4 concedes ssh interleaves them. Measured,
  not assumed.
- **AC9 — real capture** *(blocked: needs a render endpoint)*. Audio played on a Windows
  host arrives intelligibly. **Cannot be discharged on either fleet host as configured.**
  Recorded unproven, and §1 leads with that rather than listing it as one of nine.

## 9. What this deliberately does not do

- **No virtual audio device driver.** The real fix for headless hosts; a separate,
  larger piece with signing implications, and Arthur's to decide. **Its consequence,
  stated plainly: with the driver deferred and no jack plug, this tranche delivers zero
  audio to any user on any fleet host, indefinitely.** §9 is not a tidy boundary here —
  it is the reason the feature does nothing yet.
- **No microphone / capture redirection.** Out of scope, staying out.
- **No Opus.** See §3.

### Cross-family review, 2026-08-20 (Codex `gpt-5.6-sol`, xhigh)

**Verdict: rejected as implementation-ready.** Accepted, and the three
highest-impact findings were verified against the code before acting on any of
them.

The reason to record this prominently is not the findings themselves but *where
they clustered*. Both earlier reviewers were the same model family as the
author. Everything the external reviewer found that they missed sits in
Windows-domain specifics — COM threading, the WASAPI drain contract,
`WAVEFORMATEXTENSIBLE`, loopback's privacy scope. That is a correlated blind
spot, and it is the argument for cross-family review being a distinct step
rather than "another reviewer".

**Fixed** (see the commit "Fix six defects a cross-family review found in code
that had never run"): per-thread COM initialisation, which a process-global
`Once` had reduced to once per *process* so only the first connection could ever
work; draining every available WASAPI packet instead of one per tick, which
otherwise ratchets latency to the buffer size and then loses samples;
`WAVEFORMATEXTENSIBLE` parsing with the real channel count as the read stride, in
place of a clamp that would have rotated a 5.1 endpoint's channels through left
and right; freeing `GetMixFormat`'s buffer on every path; taking `capture_pos`
from WASAPI's device position so a buffer loss actually shows as a jump; the
agent's inability to ever select `loopback`; and an unbounded client queue in
front of a bounded ring.

**Open, and deliberately not fixed quietly:**

1. **`capture_pos` is decorative today.** The client never reads it. The design's
   justification — avoiding a wire break later — still stands, but the claim that
   it lets the client distinguish drift from loss from silence is **not delivered**
   and §3 should be read accordingly.
2. **Bounded priority bounds frames, not time**, and the 16 KiB clipboard chunking
   §4 promises does not exist. Eight `take`s is not 80 ms when each write can
   block, and one 256 KiB clipboard message is a single `write_all` that audio
   cannot interleave with. Either implement chunk records or correct §4.
3. **Teardown races the last clipboard payload.** `close()` is followed
   immediately by `shutdown()`, so the writer may select a payload whose socket is
   already gone. The close test exercises `Outbox::take`, never the socket
   sequence.
4. **A stuck clipboard call still wedges teardown**, now worse: the reader owns
   the audio sender, so a blocked reader leaves the audio thread waiting in `recv`
   forever and the join never completes.
5. **The 16 KiB audio ceiling is enforced after reassembly**, which permits up to
   64 MiB to be materialised first — so the protection is real but weaker than §3
   claims.

**Decided by Arthur, 2026-08-20 — system-mix capture is accepted.**

The reviewer's finding stands: `AUDCLNT_STREAMFLAGS_LOOPBACK` captures the
**system mix, not "the rhydra session"**, and Microsoft documents that default
loopback can include audio from other Terminal Services sessions. Revision 1 and
2 did not consider it at all.

**Why we are taking it anyway.** Per-session capture is not something WASAPI
offers. The only alternative activation mode is
`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, which is scoped to a **process
tree**, not a session — and a Windows session is many unrelated process trees, so
it does not deliver the property even once built. Building it is not cheap
either: `ActivateAudioInterfaceAsync` plus an implementation of
`IActivateAudioInterfaceCompletionHandler` and an async wait, on the order of 200
lines of unsafe COM in a module that still cannot be executed on any fleet host.
Substantial work that does not answer the question is the wrong trade, and rhydra
today has exactly one user.

**What narrows the exposure.** RDP sessions receive their own per-session Remote
Audio endpoints and therefore do not render to the console endpoint rhydra
captures. The realistic leakage is session-0 services and anything else on the
console — system notification sounds, most likely. *This is reasoning from the
endpoint model rather than a measurement; no fleet host can currently
demonstrate it either way, and it should be checked the first time one can.*

**What the compromise costs, and the condition to revisit.** Audio relayed to the
client may include sound the session's user did not produce. Revisit if rhydra
ever runs on a host with more than one interactive user, or on a host whose
services produce audio that should not leave it.

**The obligation this creates: say so.** A compromise that is invisible is
indistinguishable from a defect, which is the same argument as the audio health
rung. The scope is therefore stated at connect and in `--doctor`, so
"audio includes system sounds" is a documented property rather than something a
user has to discover and diagnose.

**The reviewer's sharpest observation about the validation**, worth keeping
because it is a warning about the oracle this tranche is proud of:

> The strongest evidence against the oracle is the live run itself: it reported
> the correct tones while suffering 1,588 underrun episodes. Correct dominant
> frequency does not mean usable audio.
