# HLD — Rhydra exclusive adaptive updates

**Status: SELF-APPROVED**

## Intent and scope

Rhydra must send each changed pixel exactly once, using four representations:

1. a move operation plus raw pixels for newly exposed or otherwise dirty areas;
2. raw BGRA rectangles for small exact changes;
3. H.264 for only the changed persistent regions;
4. full-desktop H.264 for broad or uncertain change, bootstrap, and recovery.

The primary user is Arthur using a 5120×2880 Windows desktop at 200%. Text must stay exact,
typing must not queue behind a redundant full frame, sustained local motion must not consume a
full-desktop stream, and recovery must remain reference-correct.

In scope: the portable wire, Windows selector/capture/encoder pipeline, native client decode and
composition, exactness/recovery state, telemetry, focused tests, and live Quench validation. Move
updates consume trustworthy OS source/destination metadata. General optical flow, OCR, and an
inferred-scroll detector are out of scope until evidence shows their bounded cost beats regional
coding. RDP transport behaviour, clipboard, audio, display provisioning, and compatibility with
pre-change native clients are out of scope; the wire version will fail closed.

## Approach

### One disjoint update plan

Introduce one pure planner whose result partitions trustworthy damage into disjoint coverage:

- `moves`: screen-to-screen copies, each followed by raw pixels for its exposed/dirty remainder;
- `raw`: small exact BGRA block rectangles;
- `video`: larger changed block regions represented by H.264;
- `full`: an exclusive full-desktop H.264 fallback, with all-tile IDR on bootstrap/recovery.

One logical update may contain move, raw, and regional-video operations when their coverage is
disjoint—for example, a raw glyph beside a changing YouTube region. The planner assigns each
changed codec block to exactly one operation. Full fallback is never combined with another
representation. Empty/no-change frames send nothing. Unavailable, overflowed, non-adjacent, or
over-complex damage selects full fallback.

If any required operation cannot enter its bounded sender queue, the whole logical plan is
abandoned and the server enters recovery. It sends no dependent sparse/regional operation until
one all-tile IDR set is admitted. This replaces the current unsafe assumption that a redundant
full frame for the same sequence will repair a dropped rectangle.

### Portable update wire

Bump the native wire version and replace independent rectangle/tile messages with logical update
messages carrying capture sequence, coverage, and representation:

- Sparse update: frame geometry, ordered move records (`source point`, `destination rectangle`),
  and raw BGRA rectangles.
- Video update: frame geometry, update kind (regional/full/recovery), exact block-aligned paint
  coverage per tile, and one Annex-B access unit for each selected persistent tile.

Bounds, lengths, tile membership, unique tile IDs, and masks are fully validated before mutation.
The client applies each message atomically. Move sources are staged from the pre-update canvas
before any destination is written; all moves are then applied, followed by raw pixels. Move
updates require the exact preceding ordered baseline. A full/recovery video update may jump the
sequence and re-establish the baseline.

Raw final pixels travel on a dedicated interactive downstream socket and SSH transport beside
input, so they cannot sit behind video bytes. The client may apply a raw update ahead of an older
bulk-video update. It retains bounded `(sequence, coverage)` fences and subtracts newer raw
coverage before painting an older decoded video update; once bulk video reaches or passes a fence,
the fence retires. A late raw update older than already-painted video is discarded. Moves remain
on the ordered bulk update stream because their source pixels depend on the preceding canvas.

### Regional H.264

At 5K, retain persistent hardware-friendly tile streams, initially the proven two 2560×2880
streams. Each tile gains a persistent GPU `codec canvas` separate from the captured desktop. A
regional plan copies only video-assigned blocks from the current desktop into that canvas, leaving
move/raw-assigned and unchanged blocks untouched, then encodes the canvas. The client retains the
corresponding decoded codec plane and copies only the declared video coverage into its displayed
canvas. Raw/move pixels therefore never enter the H.264 representation and a later decoded tile
cannot overwrite them outside its declared coverage.

Change H.264 rate control away from fixed-rate padding to the lowest-latency supported variable or
quality mode with the configured bitrate as a ceiling. Unchanged codec-canvas macroblocks then
cost only the syntax needed to preserve the persistent reference rather than today's fixed 83 KB
per half-screen AU. The selected Media Foundation mode and refusal remain telemetry-visible.

Raw and move updates feed no codec canvas or encoder. Server and client H.264 references therefore
remain aligned at their last common coded input. When an area later moves from sparse to video
coverage, copying its current pixels into the codec canvas makes the next AU reconcile it from that
shared older reference.

Other geometries retain their current supported layout in this tranche. HEVC remains an explicit
full-desktop startup fallback and does not claim regional capability.

A video update is one logical sender item. If any selected tile is lost before admission, encoder
state is treated as unavailable to the client and the server requests an all-tile recovery IDR.
The client decodes every received AU needed by its tile reference chain and publishes only declared
coverage after the complete set validates. Full/recovery coverage is the whole desktop.

### Move metadata

Preserve DXGI move source coordinates separately from dirty final pixels instead of folding move
destinations into dirty coverage. Emit `MoveRaw` only when the capture metadata spans exactly the
client's preceding baseline and the remaining raw pixels fit the sparse predicate. The client
copies from staged pre-update sources, then applies dirty pixels, matching Windows' move-before-
dirty contract.

The current IDD path continues to expose no move when Windows supplies none. Its existing unioned
final-pixel coverage remains valid input to `Raw`, `RegionVideo`, or `FullVideo`. An inferred move
detector is deliberately deferred: the protocol and selector need no change when a later bounded
detector can prove a move.

### Head-of-line policy

Disjoint selection removes the current steady-state full frame behind every sparse update. Raw
updates use their own interactive SSH transport; move and H.264 updates retain one ordered bulk
connection. Coverage fences make cross-stream precedence explicit rather than timing-dependent.
Telemetry exposes operation kind, coverage, payload bytes, queue delay, and write completion.

## Acceptance criteria

1. A property test proves every changed block belongs to exactly one move/raw/video/full operation;
   full is exclusive and unchanged blocks belong to none. Raw/move coverage never enters the codec
   canvas or H.264 paint coverage.
2. A queue-rejected required operation forces an all-tile IDR recovery before dependent traffic;
   no client can silently retain a missing baseline.
3. A move update copies exact previous pixels, including overlapping moves, then applies exposed
   dirty pixels atomically. Malformed, out-of-bounds, duplicate, and gap updates fail closed.
4. At 5K, trustworthy large local damage updates only its codec-canvas blocks and the client paints
   only declared regional coverage. Broad/unknown damage and recovery paint the full desktop; each
   tile's server/client H.264 reference chain remains aligned across intervening move/raw updates.
5. A newly connected or recovering client receives one complete all-tile IDR desktop before any
   dependent sparse/regional update.
6. Existing input, cursor, clipboard, audio, 5120×2880/200% display, and secure-desktop behaviour
   remain working.
7. Live Quench telemetry proves an isolated typed character produces one raw update and no video
   representation of its blocks; typing during sustained local motion remains raw while disjoint
   motion uses regional video; a cold connection and induced queue-loss oracle recover fully.
8. Focused tests are observed red before their fixes, then formatting, lint, root tests, Rhydra
   tests, and both Windows cross-checks are green.
9. Decoder allocation is bounded by frame pixels, staged move area, raw bytes, AU bytes, fence
   entries, and rectangle-subtraction output; adversarial payloads cannot multiply one valid 5K
   canvas into unbounded memory or partial mutation.

## Decision log

- Partition changed blocks once, then route disjoint coverage. “One type per whole frame” was
  rejected because typing and video can change simultaneously; it would force the character
  through H.264 or redundantly encode it.
- Treat move as a sparse update containing both copy operations and exposed final pixels. A move
  without its dirty remainder is incomplete.
- Use persistent fixed-size H.264 codec planes with explicit paint coverage rather than creating an
  encoder for arbitrary rectangles. Stream dimensions/reference state remain stable while the wire
  and client still treat the result as regional.
- Keep the proven two-stream 5K layout initially. The codec canvas and variable-rate skip blocks
  remove unchanged-pixel payload without betting startup on an unproven four-session hardware
  budget; finer tiling remains an independent measured tuning decision.
- Split final-pixel raw updates onto a dedicated interactive transport. Unlike moves, raw pixels do
  not depend on the preceding canvas. Bounded coverage fences define how they outrank older video.
- Do not infer scrolling in this change. Preserve real move metadata now; add bounded translation
  detection later only with an oracle and measured cost.

## Review journal

- Correctness review found that one representation per whole frame fails simultaneous typing and
  video. Refutation against the user requirement and the live YouTube/input failure preserved it;
  the design now partitions changed blocks and permits disjoint operations in one logical frame.
- Performance review found fixed quadrant streams still send unchanged content and a single socket
  still blocks raw updates behind an in-flight AU. Refutation against H.264's fixed stream geometry
  preserved the first but changed its remedy: persistent codec canvases plus variable rate make the
  stream regional without dynamic encoder churn. The same-direction TCP ordering preserved the
  second, so raw uses a separate interactive SSH transport with explicit coverage precedence.
- Security/correctness review required cumulative bounds on staged move pixels, raw bytes, video
  AUs, fence entries, and rectangle subtraction output. It also required prevalidation before any
  canvas mutation. Both survived refutation and are acceptance requirements.
- A claimed simplification—keep the existing overlay and merely add more tiles—was rejected. It
  cannot prove changed pixels are represented once and retains the head-of-line defect.
- Native reviewer seats were unavailable due the surfaced quota limit. These three lenses and
  their refutations therefore ran sequentially under the agreed fallback.
- The one Claude/Fable pass was invoked read-only and remained alive without output for four
  minutes; it was stopped. External review did not run, which remains a checkpoint residual risk.
