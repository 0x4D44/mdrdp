# IronRDP Rust crates — factual capability inventory

2026-08-14 · Gauntlet part **P1a** · credential-free

## Why this matters — the architectural consequences

Four findings change the build. All four were **independently re-verified against the
pinned registry source** before this document was committed.

1. **IronRDP's client cannot decode RFX Progressive or ClearCodec today.** The maths
   primitives exist in `ironrdp-graphics`, but nothing in `ironrdp-session` calls them —
   zero references. NSCodec has no module at all. This is now the largest risk in the
   project: if `temper` prefers Progressive over EGFX, our decode path does not exist.
2. **AVC444 is an explicit stub** (`ironrdp-egfx-0.3.0/src/client.rs:720`).
3. **`H264Decoder` is a public, pluggable trait** (`ironrdp-egfx-0.3.0/src/decode.rs:162`),
   held as `Option<Box<dyn H264Decoder>>`. A **VideoToolbox backend can be plugged in with
   no upstream changes** — implement the trait, pass it to `GraphicsPipelineClient::new`.
   That is the macOS hardware-decode win, and it is cheap to take.
4. **The connector's legacy Bitmap Codecs capability set only ever advertises RemoteFX**
   (plus QOI/QOIZ if compiled in). EGFX negotiates separately and does advertise AVC.

**Resolves a previously UNVERIFIED claim.** `ironrdp-connector` *does* handle the Early
User Authorization Result PDU: `CredsspState::EarlyUserAuthResult` is entered specifically
when `HYBRID_EX` is selected (`src/credssp.rs:220`), decodes the PDU, and maps
`AccessDenied` to a distinct error rather than parsing and discarding it. `temper` selects
HYBRID_EX, so this sat on our critical path. Status: **Confirmed**.

## B. H.264 specifically

**Yes — a `H264Decoder` trait exists**, defined in `ironrdp-egfx-0.3.0/src/decode.rs:162-178`:

```rust
pub trait H264Decoder: Send {
    /// Decode AVC-format H.264 NAL units (4-byte BE length prefix, not Annex B)
    /// into an RGBA bitmap.
    fn decode(&mut self, data: &[u8]) -> DecoderResult<DecodedFrame>;

    /// Reset the decoder state
    fn reset(&mut self) {
        // Default: no-op
    }
}
```

- **Backend model**: this is a pluggable trait, not hard-wired to one library. `GraphicsPipelineClient` holds `h264_decoder: Option<Box<dyn H264Decoder>>` (`client.rs:385`), injected via `GraphicsPipelineClient::new(handler, h264_decoder)` (`client.rs:404`). If `None`, AVC420 frames are logged and skipped, and the client advertises only non-AVC capability sets (`client.rs:830-844`).
- **Built-in backend**: `OpenH264Decoder`, in `ironrdp-egfx-0.3.0/src/decode.rs:206-320`, wraps Cisco's `openh264` crate (v0.9, per `ironrdp-egfx` `Cargo.toml`). It converts AVC-format (length-prefixed) NAL units to Annex B, decodes to YUV420p via `openh264::decoder::Decoder`, then converts to RGBA with `yuv.write_rgba8`.
- **Feature gating**: in `ironrdp-egfx-0.3.0/Cargo.toml`:
  - `openh264 = ["dep:openh264"]` — pulls the crate in, gates the `OpenH264Decoder` type.
  - `openh264-bundled = ["openh264", "openh264/source"]` — compiles OpenH264 from source (`OpenH264Decoder::new()`), no Cisco patent-license binary involved.
  - `openh264-libloading = ["openh264", "openh264/libloading"]` — loads a prebuilt Cisco OpenH264 binary at runtime (`OpenH264Decoder::from_library_path()`), verified against known Cisco release hashes.
  - None of these three features are enabled by default; the `H264Decoder` trait itself always compiles (it is not behind a feature flag).
- **Could a VideoToolbox (or other platform) backend be plugged in without upstream changes?** **Yes.** Because `H264Decoder` is a public trait taking raw AVC-format NAL bytes in and returning `DecodedFrame` (owned RGBA buffer, `decode.rs:31-70`), any consumer crate can implement it against VideoToolbox, ffmpeg, a hardware decoder, etc., and pass `Some(Box::new(MyDecoder))` into `GraphicsPipelineClient::new`. This is exactly the scenario the module doc comment calls out: *"pluggable decoder traits that allow consumers to bring their own codec implementations (e.g., openh264, ffmpeg, hardware decoders)"* (`decode.rs:1-7`). No IronRDP source change is required — only linking a new implementation.
- **Caveat**: AVC444 is not implemented (see table above) — a custom backend would only be exercised for AVC420 streams today; AVC444 frames are always forwarded to the handler unprocessed regardless of which `H264Decoder` is supplied.

## D. Early User Authorization Result PDU (HYBRID_EX) — VERIFIED, IronRDP DOES handle it

Prior claims of "IronRDP handles it" are now backed by exact source. In
`ironrdp-connector-0.10.0/src/credssp.rs`:

- `CredsspState` enum (`credssp.rs:77-82`) has a dedicated `EarlyUserAuthResult` state, distinct
  from `Ongoing` and `Finished`.
- When the CredSSP client emits its final message, the sequence transitions into
  `CredsspState::EarlyUserAuthResult` specifically **when `HYBRID_EX` was the negotiated protocol**
  (`credssp.rs:213-225`):
  ```rust
  ClientState::FinalMessage(ts_request) => (
      ts_request,
      if self.selected_protocol.contains(nego::SecurityProtocol::HYBRID_EX) {
          CredsspState::EarlyUserAuthResult
      } else {
          CredsspState::Finished
      },
  ),
  ```
- `next_pdu_hint()` (`credssp.rs:85-91`) then tells the caller to expect an
  `EARLY_USER_AUTH_RESULT_PDU_SIZE`-sized PDU next (via `CredsspEarlyUserAuthResultHint`,
  `credssp.rs:57-66`).
- `decode_server_message()` (`credssp.rs:180-207`) parses it with
  `credssp::EarlyUserAuthResult::from_buffer(input)` (the `credssp`/`EarlyUserAuthResult` type
  comes from the `sspi` crate, v0.21.3 — see §F) and acts on the result:
  ```rust
  CredsspState::EarlyUserAuthResult => {
      let early_user_auth_result = credssp::EarlyUserAuthResult::from_buffer(input)
          .map_err(|e| custom_err!("EarlyUserAuthResult", e))?;
      match early_user_auth_result {
          credssp::EarlyUserAuthResult::Success => {
              self.state = CredsspState::Finished;
              Ok(None)
          }
          credssp::EarlyUserAuthResult::AccessDenied => {
              Err(ConnectorError::new("CredSSP", ConnectorErrorKind::AccessDenied))
          }
      }
  }
  ```
  On `AccessDenied` the connector surfaces a distinct `ConnectorErrorKind::AccessDenied` error
  rather than a generic decode failure — i.e. the semantic result (not just the bytes) is consumed.
- This is not dead code: `Config.enable_credssp`'s doc comment in
  `ironrdp-connector-0.10.0/src/lib.rs:173-181` explicitly states *"This option includes the
  extended CredSSP early user authorization result PDU. This PDU is used by the server to deny
  access before any credentials... have been submitted."* And the `CredsspSequence` type this
  logic lives on is driven end-to-end by the async connector glue in
  `ironrdp-async-0.10.0/src/connector.rs` (confirmed present via `grep CredsspSequence`), which is
  what `ironrdp-tokio` and real client binaries (e.g. `ironrdp-client`) use to actually run a
  connection.

**Conclusion: VERIFIED, not UNVERIFIED.** `ironrdp-connector` 0.10.0 explicitly recognizes
HYBRID_EX, waits for the Early User Authorization Result PDU after the CredSSP exchange, decodes
it, and turns `AccessDenied` into a hard connection error.

## E. ironrdp-egfx (MS-RDPEGFX graphics pipeline extension)

`ironrdp-egfx-0.3.0` provides:
- PDU encode/decode for the full RDPGFX PDU set (`src/pdu/{mod.rs,cmd.rs,common.rs,avc.rs}`):
  surface create/delete, wire-to-surface 1 & 2, solid fill, surface-to-surface, cache
  operations, monitor/window mapping, `CapabilitiesAdvertisePdu`/`CapabilitiesConfirmPdu`,
  AVC420/444 bitmap stream structures, `Codec1Type`/`Codec2Type` enums.
- A client-side state machine, `GraphicsPipelineClient` (`src/client.rs`), that drives the
  dynamic-channel exchange: sends `CapabilitiesAdvertise`, waits for `CapabilitiesConfirm`,
  then processes `ResetGraphics`/`CreateSurface`/`WireToSurface1`/`SolidFill`/cache/mapping PDUs,
  dispatching decoded output through the `GraphicsPipelineHandler` trait.
- A server-side counterpart, `GraphicsPipelineServer` (`src/server.rs`), for building an RDP
  server (encode direction — out of scope for this client-focused inventory).
- The pluggable `H264Decoder` trait and `OpenH264Decoder` implementation (`src/decode.rs`, §B).

**Caps advertise/confirm**: yes, explicitly. `client.rs:853` sends
`GfxPdu::CapabilitiesAdvertise(CapabilitiesAdvertisePdu::from_typed(&caps))`;
`client.rs:460` handles the server's `GfxPdu::CapabilitiesConfirm(confirm)` reply and invokes
`handler.on_capabilities_confirmed`.

**Versions advertised**: the default `GraphicsPipelineHandler::capabilities()`
(`client.rs:220-236`) advertises, in order:
- `V10_7` with `SMALL_CACHE` (implies AVC420+AVC444 availability per protocol semantics),
- `V8_1` with `AVC420_ENABLED | SMALL_CACHE`,
- `V8` with `SMALL_CACHE` (no AVC) as a fallback.

Per the doc comment at `client.rs:220-226` and the filtering logic at `client.rs:830-844`: if no
`H264Decoder` is configured, capability sets that imply AVC support are filtered out before
sending, falling back to V8-only. So the AVC-capable advertisement is conditional on a decoder
actually being wired up — consistent with §B.

## F. Authentication (CredSSP / NTLM / Kerberos)

`ironrdp-connector` depends on the external `sspi` crate for all of this — it does not
reimplement CredSSP/NTLM/Kerberos itself. From `ironrdp-connector-0.10.0/Cargo.toml`:
```toml
[dependencies.sspi]
version = "0.21"
features = ["scard"]
```
Pinned in this probe's `Cargo.lock` to **sspi 0.21.3**. `ironrdp-connector-0.10.0/src/credssp.rs`
uses, directly:
- `sspi::credssp::{CredSspClient, ClientState}` — the CredSSP state machine (TSRequest exchange).
- `sspi::credssp::ClientMode::{Ntlm, Negotiate}` — NTLM is used when no Kerberos config is
  supplied (`credssp.rs:155`, `sspi::ntlm::NtlmConfig::default()`); Kerberos/Negotiate is used
  when a `KerberosConfig` is supplied, converted to `sspi::KerberosConfig`
  (`credssp.rs:145-153`).
- `sspi::generator::{Generator, NetworkRequest}` — sspi's generator-based I/O model, meaning
  `ironrdp-connector` stays transport-agnostic and hands network requests (e.g. KDC lookups)
  back to the caller rather than doing sockets itself.
- `sspi::{AuthIdentity, Username, Secret, SmartCardIdentity, SmartCardType}` — credential types,
  including smart-card/PIN-based auth (gated by the `scard` sspi feature, enabled by
  `ironrdp-connector`'s `Cargo.toml` unconditionally, not behind an IronRDP-level feature flag).

**What's pulled in by default**: enabling `ironrdp-connector` always pulls in `sspi` with the
`scard` feature. NTLM support is always available (sspi's NTLM implementation, no extra feature
needed on the IronRDP side). Kerberos support is present in the API (`KerberosConfig`) but is
only exercised if the embedding application supplies a `KerberosConfig`; no separate cargo
feature is required to compile Kerberos support in — it's controlled purely by which config
variant the app passes at runtime, though runtime Kerberos ticket acquisition depends on the
system's Kerberos environment being usable via `sspi`'s network-client machinery (that plumbing
lives inside `sspi` itself and was not further inspected as it is outside the requested crate list).
