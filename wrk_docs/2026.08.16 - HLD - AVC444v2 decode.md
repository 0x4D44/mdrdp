# AVC444/AVC444v2 decode

Status: SELF-APPROVED (rev 3 — adversarial + external review folded)
Date: 2026-08-16
Author: Claude Fable 5 (lead), for Arthur
Reviewers: 3x Opus (protocol / VideoToolbox-FFI / architecture) + Codex gpt-5.6-sol
(external, xhigh). All nine external findings folded or reframed; none rejected.

## Goal

Decode the AVC444v2 (and AVC444 v1) EGFX codec so mdrdp can accept the stream modern
Windows actually sends when AVC is negotiated (measured on quench: V10.7 confirm
`0xA0701`, whole desktop as Avc444v2). Success: a live quench session negotiates V10.7,
renders Avc444v2 frames with correct colors, and video playback is at least as good as
the current software path (~25 fps, input-to-paint p50 72 ms).

**Out of scope:** AVC encoding (server-side), multi-surface AVC streams (Windows sends
AVC to the one primary surface; per-surface decoders are a documented follow-up if that
changes), non-macOS hardware decode.

## Background (measured + verified)

- The wire container (`RFX_AVC444_BITMAP_STREAM` / `…V2`) is already parsed
  (`vendor/ironrdp-egfx/src/pdu/avc.rs::Avc444BitmapStream`): an `LC` encoding field
  plus one or two embedded AVC420 streams, each with **its own rect list**. v1 and v2
  share the wire format; only the aux-frame chroma packing differs.
- `vendor/ironrdp-egfx/src/client.rs:721` currently forwards Avc444/Avc444v2 to
  `on_unhandled_pdu` — the whole gap.
- Both sub-streams are ordinary H.264 **4:2:0** streams. FreeRDP (3.x, field-proven
  against Windows servers) feeds stream1 then stream2 through **one** decoder context
  (`h264.c::avc444_process_rects` — source fetched from FreeRDP master 2026-08-16;
  3.27.1 is installed locally). The Windows encoder produces a jointly-encoded pair
  that decodes correctly through a single sequential decoder. Review note: a probe
  showed that two *independently encoded* streams interleaved through one
  VTDecompressionSession decode silently wrong (status 0, wrong pixels) — that is a
  property of independent streams, not of Windows' joint encoding, but it means our
  live validation MUST verify decode health on captured real pairs, not rely on
  status codes (see Acceptance 2b).
- LC semantics (FreeRDP `avc444_decompress`, verified): 0 = luma in stream1 + chroma
  in stream2 (each with its own rects); 1 = luma only in stream1; 2 = chroma only in
  stream1 (with stream1's rects).
- **VideoToolbox measured facts** (probe-verified on this Mac, 2026-08-16):
  - VT normalises output to the **requested format's range** regardless of stream VUI.
    `'f420'` (`kCVPixelFormatType_420YpCbCr8PlanarFullRange`) is the one correct
    choice for FreeRDP's full-range coefficients; `'y420'` rescales to 16–235 and is
    unconditionally wrong. Not a knob — a determinate answer.
  - VT always delivers **SPS-cropped** dims (1920x1088 coded → 1080 rows out; the
    padding rows are unrecoverable). Planar strides are not width (measured 1728 for
    w=1680) — use `CVPixelBufferGetBytesPerRowOfPlane` per plane.
  - A session rebuilt mid-GOP fails every P-frame with `-12909` until the next IDR.
    Session rebuilds are therefore stream-killers, not glitches: the design must not
    rebuild on codec switches (one output format for everything) and must treat an
    SPS mismatch between the two sub-streams as unsupported (skip + count), not
    rebuild-and-retry.
  - Decode cost at 2560x1440: planar `f420` ≈ 4.9 ms/frame (cheaper than today's
    BGRA at 7.3 ms); combine+convert measured in C at ~3.0–3.7 ms/frame. Two decodes
    + combine ≈ 13 ms against a 33 ms/frame budget at 30 fps.

### Chroma packing (verified against FreeRDP prim_YUV.c source)

Destination is a full-resolution YUV444 frame; the *main* frame provides Y and the
even-row/even-col chroma; the *aux* frame provides the rest.

**Luma pass**: copy Y; replicate main U/V 2x2 into ALL dst chroma positions in the ROI
(the chroma pass overwrites the odd positions; an LC=1 frame therefore degrades its
rects to 4:2:0 chroma until the next chroma frame — reference behavior).

**Chroma v1** (absolute frame coordinates):
- dst U row `2k+1` ← aux Y row `(k/8)*16 + k%8`; dst V row `2k+1` ← aux Y row
  `(k/8)*16 + 8 + k%8` (full width).
- dst U/V even rows `2y`, odd columns `2x+1` ← aux U/V planes at `[y][x]`.

**Chroma v2** (absolute frame coordinates; `W` defined below):
- dst U`[y][2x+1]` ← auxY`[y][x]`; dst V`[y][2x+1]` ← auxY`[y][W/2 + x]` (all rows).
- dst U`[2y+1][4x]` ← auxU`[y][x]`; dst V`[2y+1][4x]` ← auxU`[y][W/4 + x]`;
  dst U`[2y+1][4x+2]` ← auxV`[y][x]`; dst V`[2y+1][4x+2]` ← auxV`[y][W/4 + x]`.

**`W` for v2** mirrors FreeRDP `yuv.c:483` exactly:
`W = min(align32(surface_width), aux_y_plane_row_width)` — 32-alignment of the
*surface* width, capped at what the decoded aux plane actually holds.

**YUV444 → RGB** (FreeRDP `prim_internal.h`, full-range BT.709 fixed point, verified):
```
R = clamp((256*Y                 + 403*(V-128)) >> 8)
G = clamp((256*Y -  48*(U-128)   - 120*(V-128)) >> 8)
B = clamp((256*Y + 475*(U-128)                ) >> 8)
```

**2x2 chroma reconstruction (external review catch, verified in source):** the
encoder stores the 2x2 block *average* at the even/even chroma position, so the RGB
pass first reconstructs the true top-left sample: for each block at `(2y, 2x)`,
`recon = clamp(4*p00 - p01 - p10 - p11)`; use `recon` only if
`|recon - p00| >= 30`, else keep `p00` (FreeRDP `CONDITIONAL_CLIP`, threshold 30 —
a denoise heuristic). Rows/columns without a full 2x2 block (odd frame edge) use the
raw sample. Neighbors come from the full 444 buffer, so per-rect conversion is
unaffected by rect edges.

## Approach

### 1. `vendor/ironrdp-egfx/src/decode.rs` — YUV output on the decoder trait

- `Yuv420Frame { y, u, v: Vec<u8>, width, height }` — tight-packed planes copied out
  of the pixel buffer (row width == width for Y, (width+1)/2 for U/V; the *pixel*
  width, never CoreVideo's bytes-per-row pitch, which may include alignment padding
  that is not image data).
- `fn decode_yuv420(&mut self, data: &[u8], out: &mut Yuv420Frame) -> DecoderResult<()>`
  — default body returns `Err("YUV output not supported")`. Out-param so the caller
  owns buffer reuse: the client keeps two scratch frames (main + aux must be alive
  together on LC=0), and steady state allocates nothing.
- `fn supports_yuv420(&self) -> bool { false }` — lets the client filter
  AVC444-bearing capability sets structurally (see §5), so "advertised 444 but can't
  decode it" is unrepresentable rather than a runtime warning.

### 2. `vendor/ironrdp-graphics/src/avc444.rs` — pure combination math (NEW)

Placed in ironrdp-graphics, not egfx: the repo's stated division of labour puts codec
pixel math there (clearcodec, progressive, color_conversion already live there, and
egfx already depends on it).

- `Yuv444Buffer { y, u, v: Vec<u8>, width, height }` — persistent full-res frame,
  initial fill Y=0, U=V=128 (black).
- `apply_luma(&mut self, main: &Yuv420Frame, rects: &[Rect])`
- `apply_chroma_v1 / apply_chroma_v2(&mut self, aux: &Yuv420Frame, rects: &[Rect])`
- `to_rgba_into(&self, rect: Rect, out: &mut Vec<u8>)` — fixed-point conversion,
  caller-provided scratch buffer (no per-frame allocation).
- `yuv420_to_rgba(frame: &Yuv420Frame) -> Vec<u8>`-equivalent helper for the AVC420
  path (§4).

Implementation style: **absolute-coordinate direct index mapping** — for each dst
position inside the (validated, exclusive) rect, compute the absolute source index.
No ROI-relative pointer walking, therefore **no alignment constraints and no ROI
enlargement**: the encoder packs frame-relative, so absolute mapping is correct for
any rect (FreeRDP's ROI-relative v1 walk is only correct for 16-aligned rect tops —
we do not inherit that constraint). Every source read is bounds-checked against the
actual plane extents; a dst position whose source lies outside the decoded frame is
left unwritten (keeps its replicated/previous value).

### 3. `vendor/ironrdp-egfx/src/client.rs` — the 444 decode path

Replace the `Avc444 | Avc444v2` arm with `decode_avc444`:

1. Parse `Avc444BitmapStream`; dispatch by `encoding` **by equality**
   (`Encoding::LUMA_AND_CHROMA` is bit-value 0, so `.contains()` is always true —
   never use it here).
2. **Rect handling.** Wire rects are RDPGFX_RECT16 = **exclusive** right/bottom
   despite the `InclusiveRectangle` typing (upstream typing artifact; FreeRDP and the
   destRect handling in this same file both treat them as exclusive). Convert
   field-for-field, then validate per rect: `left < right`, `top < bottom`,
   `right <= surface.width`, `bottom <= surface.height`; drop invalid rects
   (counted). Rects are additionally clipped to the decoded frame dims inside the
   combine (bounds-checked reads).
3. LC dispatch: decode stream1 (and stream2 when present) through the **same**
   `self.h264_decoder` via `decode_yuv420`, sequentially, then luma-pass with
   stream1's rects / chroma-pass with the chroma stream's own rects.
4. Guards before the chroma pass: decoded frame dims must equal
   `(align16(surface.width), align16(surface.height))` — the geometry the encoder
   packed against — and aux dims must equal main dims when both are present. On
   violation, skip the chroma pass and count (luma-only 4:2:0 output is the graceful
   degradation, never sheared chroma). This closes the case where main and aux are
   equally SPS-cropped to an unaligned size: equal to each other, but not to the
   packing geometry.
5. Persistent `Yuv444Buffer` per surface (`BTreeMap<u16, Yuv444Buffer>`): sized from
   the **surface** dims at first use (known at CreateSurface, stable; LC=2-first
   works), cleared when a CreateSurface reuses the id, dropped on DeleteSurface,
   survives ResetGraphics.
6. **Emission:** one `BitmapUpdate` per validated region rect (from the rect lists
   actually combined this PDU), converted via `to_rgba_into` from the 444 buffer.
   The PDU's `destination_rectangle` is NOT used as the paint region (FreeRDP
   ignores it for AVC): painting it would both miss chroma-only rects outside it and
   repaint non-AVC surface content (SolidFill/CacheToSurface results) with stale 444
   buffer data.
7. **Resilience + visibility:** every failure (parse, decode, dim guard) logs, counts,
   and skips the frame — never errors the channel. New handler callback
   `on_decode_failure(codec_id, reason: &'static str)` (default no-op) gives mdrdp's
   stats a seam with the reason preserved (GfxStats already tallies by reason); the
   existing AVC420 arm is fixed to match (today a frame-smaller-than-rect error
   tears down the DVC channel — same fix, same seam).
8. Fix the stale vendored test `reset_graphics_clears_surfaces_and_frame_tracking`
   (asserts pre-patch behavior; currently red) so "vendored egfx tests green" is a
   meaningful gate again.

### 4. `src/h264.rs` — VideoToolbox planar output, ONE session format

- The session requests `'f420'` planar output — for **everything**. `decode_yuv420`
  returns the planes; `decode` (RGBA, used by the AVC420 path) is implemented as
  `decode_yuv420` + software conversion (measured cheaper than the BGRA session it
  replaces: 4.9+1.4 ms vs 7.3 ms). One output format ⇒ codec switches never rebuild
  the session ⇒ no mid-GOP `-12909` stalls from our own design.
- Callback: gate on `CVPixelBufferGetPixelFormatType` / `CVPixelBufferIsPlanar` +
  `GetPlaneCount() == 3`; per-plane null-check and `bytes_per_row >= plane_width`
  validation; **no panic paths** (guards set `slot.status`, callback is `extern "C"`
  and a panic aborts the process). Plane copies use per-plane
  `CVPixelBufferGetBytesPerRowOfPlane`.
- New FFI: `CVPixelBufferIsPlanar`, `CVPixelBufferGetPixelFormatType`,
  `CVPixelBufferGetPlaneCount`, `CVPixelBufferGetBaseAddressOfPlane`,
  `CVPixelBufferGetBytesPerRowOfPlane`, `CVPixelBufferGetWidthOfPlane`,
  `CVPixelBufferGetHeightOfPlane`.
- Buffer reuse: the decoder retains reusable plane buffers (avoid ~25 MB/frame of
  fresh zeroed allocation; measured 0.8 ms/frame wasted).
- Session rebuild policy for genuine death (`kVTInvalidSessionErr`) unchanged, with
  the known limitation that recovery completes at the next IDR. `reset()` on
  ResetGraphics stays as-is: Windows follows a reset with fresh SPS + IDR (it is the
  resolution-change path), so the mid-GOP-death hazard does not apply there. H.264
  state lifetime, stated explicitly: session dies on `reset()` and on parameter-set
  change; the 444 buffers are surface-keyed and independent of it.
- **SPS oscillation guard (external review):** a naive rebuild-on-change would let a
  divergent aux SPS destroy the main stream's reference chain *before* any
  client-side dim guard runs. The decoder therefore remembers the previous parameter
  set pair; when a "new" SPS/PPS equals the pair-before-last (ABAB alternation — the
  dual-stream divergence signature), it returns an error WITHOUT rebuilding. A
  genuine new stream (A→B, no oscillation) rebuilds as today. Windows uses one SPS
  for both sub-streams, so this is a guard, not a path.

### 5. Capability advertisement — `src/gfx.rs`, `src/main.rs`, client filter

- `GfxHandler::advertising_avc420()` is **replaced** by `advertising_avc()`:
  `[V10_7 { SMALL_CACHE }, V8_1 { AVC420_ENABLED | SMALL_CACHE }, V8 { SMALL_CACHE }]`.
  The old AVC420-only advertisement is dead configuration once 444 ships; its test
  is replaced by one pinning the shipped selection.
- `GraphicsPipelineClient::start` extends its existing no-decoder filter: sets whose
  `CodecCapabilities` imply avc444 are dropped when `!decoder.supports_yuv420()`,
  sets implying avc420 are dropped when there is no decoder at all. Fallback is
  structural: no YUV support → V8.1/AVC420 wins; no decoder → V8.
- `main.rs` keys `advertising_avc()` off `h264::hardware_decode_available()`
  (unchanged gate, one call site).

## Acceptance criteria

1. **Differential oracle (primary):** our `apply_luma` / `apply_chroma_v1` /
   `apply_chroma_v2` / `to_rgba` byte-match FreeRDP 3.27.1's
   `primitives_get()->YUV420CombineToYUV444` (types LUMA/CHROMAv1/CHROMAv2) and
   `YUV444ToRGB_8u_P3AC4R` on randomized frames and rects, following the established
   `tools/codec-oracles` pattern. **Comparison domain:** phase-aligned rects only —
   even left/top for luma and v2, full-frame (or 16-aligned top) for v1 — because
   FreeRDP's ROI-relative walks and our absolute mapping agree exactly there, and
   that domain is where FreeRDP is field-proven against Windows (which sends aligned
   rects). Our behavior on unaligned rects is a deliberate superset pinned by our own
   hand fixtures instead. The v1 fixture uses height ≥ 32 so the 16-row block
   interleave is actually exercised (below 32 rows it is indistinguishable from the
   identity mapping).
   **Client-level LC tests:** encoded Avc444/v2 PDUs driven through
   `GraphicsPipelineClient` with a scripted stub YUV decoder — LC=0 with *distinct*
   stream1/stream2 rect lists (proves rect ownership and that the zero-valued
   `LUMA_AND_CHROMA` dispatch is by equality), LC=1 (chroma persistence outside the
   luma rects), LC=2 (stream1 as chroma; LC=2-first buffer creation).
2. **Live (quench, 2560x1440, release build, LAN):**
   a. capability confirm `0xA0701`; GfxStats shows Avc444v2 frames > 0 AND
      decode-failure count == 0 (now a real signal via `on_decode_failure`) over a
      ≥60 s video playback run;
   b. **decode-health check on real pairs:** colors numerically correct on a
      captured final buffer — known-white UI regions ≥ RGB 250, known-black ≤ 5
      (catches the range error), AND **saturated-color regions** (e.g. the Windows
      accent-colored UI elements / a colored test image) sampled and compared
      numerically against the reference client, because white/black have neutral
      chroma and cannot see a chroma-packing or reference-chain fault. The capture
      is taken after ≥60 s of P-frame-heavy content (video), not on a fresh IDR,
      so single-session reference corruption (silent, status-0) would be visible.
      Sub-stream payload capture (opt-in dump) is added so any anomaly can be
      replayed offline; a full FreeRDP replay differential is the contingency, not
      built up front.
3. **Perf (quench, 2560x1440, release, LAN):** video playback ≥ software-path
   baseline ~25 fps measured by the painted-frames meter in `src/window.rs` (baseline
   2711 frames/110 s, same meter, 2026-08-16); input-to-paint p50 ≤ 72 ms (same
   instrumentation as the baseline measurement); combine+convert p50 < 10 ms/frame
   (debug-level log instrumentation).
4. **Regression:** temper still negotiates and renders (ClearCodec/Progressive,
   no AVC) after the advertisement change — live census, temper health permitting
   (it was refusing logons on 2026-08-14; if still down, recorded as residual risk).
   `cargo fmt` / `clippy -D warnings` / `cargo test` clean at root, PLUS
   `cargo test` run inside `vendor/ironrdp-egfx` and `vendor/ironrdp-graphics`
   (vendored crates are not workspace members — the root suite does not run them).

## Decision log

1. Combination math in `ironrdp-graphics` (repo's codec-math crate), dispatch and
   buffer lifecycle in the egfx client. (Rev 1 had it in egfx; review moved it.)
2. One decoder instance, both sub-streams sequentially — FreeRDP-proven against
   Windows. A probe refutation attempt used independently-encoded streams (which do
   corrupt) but that is not what Windows emits; live acceptance 2b is the guard.
   Fallback if ever needed: stream-index parameter, two sessions.
3. Trait gains `decode_yuv420` + `supports_yuv420`; RGBA `decode` retained and, for
   VideoToolbox, implemented on top of the YUV path — one session format, no
   rebuild-on-switch stalls.
4. `'f420'` full-range planar output — measured as the only correct constant against
   FreeRDP's full-range coefficients; `'y420'` measurably rescales to video range.
   (Rev 1 had this inverted.)
5. Absolute-coordinate direct index mapping, no ROI enlargement/alignment — encoder
   packs frame-relative, so absolute mapping is correct for arbitrary rects; ROI
   enlargement (rev 1) would have written stale fringe pixels and was dropped.
6. Wire rects treated as exclusive despite `InclusiveRectangle` typing; validated
   and dropped when malformed (a reversed rect must not underflow or paint).
7. Per-rect combine AND per-rect emission; destRect not used as a paint region.
   (Rev 1 painted destRect; review showed that both misses chroma-only rects and
   repaints non-AVC content with stale buffer data.)
8. Per-surface 444 buffer sized from surface dims (not decoded dims): stable,
   LC=2-first safe, no resize policy needed; cleared on CreateSurface id reuse.
9. `advertising_avc420` deleted, not kept alongside — dead configuration; the
   structural `supports_yuv420` filter covers the "decoder can't do YUV" case.
10. v1 (Avc444) kept: pinned by the same differential oracle and a ≥32-row fixture,
    so it ships tested even though no measured server sends it.
11. (External review) 2x2 chroma reconstruction with CONDITIONAL_CLIP added to the
    RGB pass — the even/even chroma sample is the encoder's block average and must
    be inverted; rev 2 omitted it entirely.
12. (External review) `decode_yuv420` takes an out-param frame; the client owns two
    scratch frames — resolves the owned-Vec-vs-reuse conflict explicitly.
13. (External review) SPS oscillation (ABAB) detected inside the decoder and
    rejected without a rebuild, so a divergent aux stream cannot destroy the main
    reference chain before any client-side guard runs.

Status: SELF-APPROVED (per the lean unattended flow: adversarial 3-lens review +
cross-family external review folded; the human gate remains integration).

## Risks

- **Single-decoder premise** (see decision 2): guarded by acceptance 2b; visible
  failure mode is gross frame corruption with clean status codes.
- **Non-16-aligned desktop sizes:** VT always crops to SPS display size, so at
  unaligned widths the aux offsets shift relative to the aligned coded frame. The
  `min(align32(surface), plane_row)` cap plus dim-equality guard degrade to
  luma-only (counted) rather than shearing. Live-validated only at an aligned
  resolution; unaligned is a known follow-up (scratchpad).
- **temper regression run** may be blocked by temper's health; recorded if so.
- **SPS/PPS divergence between sub-streams** → skipped frames, counted, with a
  documented two-session fallback design. Not observed in AVC420 diagnostics.
