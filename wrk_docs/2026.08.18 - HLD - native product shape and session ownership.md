# HLD — `mdrdp --native`: product shape and session/desktop ownership

Status: DRAFT for Arthur. Designs §7 of the native-transport HLD (2026.08.17) to the
point where productisation can start. The transport itself is proven (Increments 0–3,
p50 55.6 ms measured 2026-08-18); this document is about everything around it: how a
session comes to exist on the host, who owns the desktop, and how the pieces ship.

## 1. The one-sentence product

`mdrdp <host> --native` opens an SSH connection to a Windows host it has previously
been deployed to, ensures the capture server is running in the interactive session,
and presents the desktop over the spike's wire protocol — sub-60 ms glass-to-glass
today, aiming at ~45 with the remaining client work.

## 2. What the spike already settled

- **Transport**: framed TCP over SSH port-forwards (video + input), H.264 AVC +
  raw-rect overlay + pixel-diff verification. Wire v2, versioned, unknown-type-skippable.
- **Capture**: DXGI duplication default; the IddCx driver provides the 240 Hz virtual
  display and an alternative direct source behind `--source idd`.
- **Auth**: SSH is the security boundary. The server binds loopback only; no
  credential ever crosses our wire.
- **Input**: scancode records injected via `SendInput` from a loopback listener.

## 3. The hard problem: session and desktop ownership

Everything above assumes what the rig provides by hand: *a logged-on, unlocked
interactive session with the virtual display attached and DWM composing it.* The
product has to create and defend that state. Windows offers no clean API for most of
it, so the design is explicit about which states we handle, which we refuse, and
which we document as host configuration.

### 3.1 Session states and our stance (v1)

| state | what capture sees | v1 stance |
|---|---|---|
| Console session, unlocked | the desktop | **the supported state** |
| Locked (secure desktop) | lock screen or nothing; input injection blocked | detect and report; unlock is **out of scope v1** (host config: disable lock on the dev box) |
| Nobody logged on | no session to capture | refuse with a clear message; host config: auto-logon |
| RDP session holds the desktop (mstsc took it) | console disconnected, displays detached | detect; offer `tscon`-back only when credentials/elevation allow; else report |
| DWM not composing the target display | silent zero-frame capture | health check + remediation ladder (§3.4) |

The honest v1 posture: **the target is a machine you own, configured for remote
bring-up** — auto-logon, no lock screen, our driver installed. That is exactly the
population mdrdp serves (your own boxes on your own LAN), and it converts the
unsolvable general problem into a documented checklist `mdrdp deploy` can verify.

### 3.2 Getting the server into the interactive session

An SSH exec session lands in a service context (session 0): it cannot capture the
desktop, enumerate its windows, or inject input (proven repeatedly on quench). The
server must run *in the interactive session*. Options considered:

1. **Logon-triggered scheduled task** (v1 choice). `mdrdp deploy` registers a task
   (run-at-logon, interactive token, `/RL HIGHEST` for the elevated ops) that starts
   a small **session agent**. The agent supervises the capture server: starts it on
   demand, restarts it across display topology changes, runs the health checks. SSH
   only ever talks to the agent's loopback control port. No service, no
   `CreateProcessAsUser`, no new privilege machinery — the mechanism is exactly what
   the rig has proven for months, made permanent.
2. A SYSTEM service + `CreateProcessAsUser` into the session — the "real" remote
   desktop architecture. More capable (survives logoff, can drive logon), and much
   more code and risk. Deferred until v1's stance on logon/lock proves too tight.

### 3.3 The virtual display is a product feature, not a test rig

Product requirement #2 (window geometry destroyed by monitor sleep) is *solved* by
the permanent virtual display: sessions target a display whose geometry never
changes because no physical monitor backs it. v1 ships the IddCx driver as the
default session surface:

- Attach at agent start; keep attached (today's rig behaviour).
- The physical console keeps its own displays; we capture only ours. (Mirroring or
  blanking the physical outputs is a privacy question deliberately deferred.)
- Resolution changes ride the existing renegotiation path: the client asks, the
  agent sets the display mode, capture follows.

### 3.4 Health and remediation (born from today's wedge)

Today (2026-08-18) DWM silently stopped composing the virtual display on quench:
GDI saw the desktop, the device restarted cleanly, and both capture sources
delivered zero frames with zero errors. The product must notice this class of
failure itself:

- **Health check** (agent, cheap): frames-presented counter over the last N seconds
  vs input/window activity. "Input flowed, zero presents" is the wedge signature.
- **Remediation ladder**, each step logged and reported to the client: restart
  duplication → restart capture server → cycle the IDD device → restart DWM
  (elevated) → advise reboot. Never loop; one pass, then surface the state.

**Post-mortem update (2026-08-18 evening):** the quench incident that motivated
this section turned out to be rig errors, not a DWM fault — the diagnostics ran
the capture server without a connected viewer, which records nothing by design
(see the 2026.08.18 wedge post-mortem journal). The section survives the
correction with two amendments. First, the ladder gains an earlier rung:
**verify the IDD creator process is alive and the device present** — the device
lives only while `mdrdp-idd-create.exe --wait` runs, so a reboot (or a crashed
creator) removes it outright, and `mdrdp deploy` must install the creator as a
boot/logon task. Second, demote "restart DWM" to a last resort behind "advise
reboot" evidence-gathering: we have not yet observed a genuine DWM composition
wedge, and the one time we killed DWM for this symptom it fixed nothing.
- `mdrdp <host> --native --doctor` runs the ladder's diagnosis read-only from the
  Mac, like `probe stages` does for RDP.

## 4. Client-side shape

- `mdrdp <host> --native` — one session per process, same as RDP mode. The launcher
  treats native favourites identically.
- **SSH transport v1: shell out to the system `ssh`** (`-L` forwards, `BatchMode`,
  config-respecting). No new Rust dependency, users keep their `~/.ssh/config`
  identities, and the deploy step can verify connectivity with the same binary.
  A library transport (russh) is a later, deliberate dependency decision.
- The viewer window reuses mdrdp's session window plumbing (input path, geometry
  persistence, HUD). The spike viewer's presenter work (Increment 4's damage-aware
  canvas) migrates into `mdrdp::window` when the native mode lands there.
- Wire/protocol version: client refuses to run against a server whose header
  `wire_version`/`schema` it does not know; `mdrdp deploy` closes the gap.

## 5. Deploy

`mdrdp deploy <host>` over SSH, idempotent:

1. Copy server + agent binaries to `C:\mdrdp\` (versioned directory, previous kept).
2. Driver: install/upgrade the signed IDD package (the `install-notest.ps1` sequence,
   productised; DriverVer discipline so pnputil actually installs).
3. Register the logon task; start the agent now if a session exists.
4. Verify: agent handshake, display attached, one test frame captured.
5. Report the host-config checklist state (auto-logon, lock policy, firewall).

## 6. Clipboard (product requirement #1) — the next wire feature

Text-first (UTF-8), both directions, after the transport lands in mdrdp proper:

- Two new wire messages (clipboard-data client→server and server→client with a
  format byte; the framing already skips unknown types so old peers stay safe).
- Windows side in the agent/server: `AddClipboardFormatListener` + `SetClipboardData`
  via the existing session presence.
- Mac side: reuse mdrdp's existing pasteboard plumbing from the RDP path.
- The soak requirement (survive all-day, zero wedges) inherits mdrdp's existing
  clipboard test discipline; the native path has no cliprdr state machine to wedge,
  which is the point.

Audio (RDPSND equivalent) explicitly after clipboard; nothing in this design blocks it.

## 7. What v1 refuses, and says so

- Unlocking a locked session; logging a user on. (Host config instead.)
- Multi-monitor remote desktops. (One virtual display.)
- Contending with an active RDP session for the console beyond detect-and-report.
- Any unauthenticated or non-SSH transport.

   quench/temper-class boxes, or is session-0-service + logon machinery worth its

   mirror?
3. Where does `--native` live: inside mdrdp's existing binary from day one (my

   spike viewer grow into a second binary first?

## 9. Sequencing (each step separately integrable)

1. Agent + logon-task bring-up on quench; retire the ad-hoc rig tasks.
2. `mdrdp deploy` (subsumes deploy.ps1 + install-notest.ps1).
3. `mdrdp <host> --native` MVP: ssh spawn, forwards, spike-viewer presenter embedded
   in the mdrdp window shell.
4. Health ladder + `--doctor`.
5. Clipboard. 6. Audio. 7. IddCx-direct capture promotion if its tail clears.
