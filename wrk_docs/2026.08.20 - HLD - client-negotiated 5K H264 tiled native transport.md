# Client-negotiated 5K H.264 native transport

## Decision

The live rhydra video path is H.264 4:2:0 only. HEVC is retired because its measured
21.1 ms host encode median consumes the latency budget before network, decode or present.

The client chooses the IDD backing-pixel mode before video starts:

- a 5120x2880 fullscreen client requests 5120x2880 at 240 Hz and its local UI scale;
- a 2560x1440 fullscreen client requests 2560x1440 at 240 Hz and its local UI scale;
- every other native geometry starts at the 2560x1440, 240 Hz control.

The 5K stream is two vertical 2560x2880 H.264 4:2:0 tiles. The 1440p control is one
2560x1440 tile. AVC444 and four-view 5K are deferred until a measured 5K 4:2:0 quality
test proves they are needed.

## Connect contract

Wire v5 adds `prepare-display` on the loopback control channel. It carries width,
height, refresh and Windows UI scale. The agent accepts only the two experiment
geometries at 60, 120 or 240 Hz.

The agent stops the old capture server, applies the requested IDD mode, reads the mode
back, and measures the effective per-monitor Windows scale. It starts the encoder only
when both values exactly match the request. Status reports actual and desired values
separately. The client polls that status before opening the video channel and refuses a
mismatch. The video header then independently echoes codec, desktop geometry and tiles;
the client validates exact non-overlapping coverage again before allocating decoders.

Windows documents mode setting and scale querying, but no per-monitor UI-scale setter.
This implementation therefore fails closed when the requested scale is not already in
force. An automatic scaling hook is a separate design decision: it would require an
undocumented display-config packet or a session-level mechanism comparable to RDP's.

## Host pipeline

One capture produces one full-desktop BGRA texture and one capture sequence. Each tile
owns a D3D11 video processor whose source rectangle crops that texture to tile-local
NV12, then an independent Media Foundation H.264 encoder. Both 5K tile access units carry
the same capture sequence and their tile ID in `MSG_VIDEO_TILE`.

Bitrate is divided evenly between encoders. Parameter-set caches, keyframe requests,
surface leases, encoder epochs and queue-drop recovery remain independent per tile. A
queue drop requests recovery keyframes rather than presenting a stale access unit as
current. Server telemetry writes one row per tile and names `tile_id`.

The existing raw dirty-rectangle path remains a full-desktop overlay. Its change-area
telemetry uses full-desktop pixels as the denominator on both tile rows. Further dirty
rectangle calculation and tile-local encoding are later optimisation work.

## Client pipeline

The client creates one hardware H.264 decoder per advertised tile. Each decoder has its
own exact-through sequence, so tile 1 cannot suppress tile 2 merely because both came
from one capture. A decoded tile must have its advertised dimensions and is blitted only
inside its advertised rectangle.

Rendering may wake after either tile to minimise visible delay. Frame, byte, decode and
input-to-paint telemetry completes only after every tile for that capture sequence has
painted, so 5K does not report two logical frames or close input latency on a half-frame.
Incomplete tile-frame accounting is bounded to 16 capture sequences.

## Acceptance

1. The 2560x1440 control connects at 240 Hz, advertises one H.264 tile, paints and takes
   input without decode errors.
2. A 5K client makes the IDD report 5120x2880 at 240 Hz before the encoder starts.
3. The 5K header advertises two exact 2560x2880 tiles and the client paints both halves
   for one capture sequence without a seam, suppression or double frame count.
4. A wrong mode, scale, codec, tile gap, overlap or decoded tile size refuses the session.
5. Live telemetry reports encode time separately per tile and one logical client frame.
6. Text quality at 5K 4:2:0 is judged before any AVC444 four-view build starts.
