# HLD — rhydra tranche 4: health ladder and `--doctor`

Step 4 of the parent HLD's §9 sequencing (`wrk_docs/2026.08.18 - HLD - native
product shape and session ownership.md`, §3.4). Tranche 3 landed the native
transport (v0.1.71); this tranche upgrades health from "a port answered" to
named rungs, and gives the Mac a read-only diagnosis.

**This document was substantially rewritten after review.** The first draft put
the wedge detector in the client and had the ladder auto-restart the capture
server. Both were wrong, and §12 records why. What follows is the corrected
design.

## 1. The one-sentence deliverable

rhydra notices the class of failure where **everything reports healthy and no
pixels move**, names which rung is broken, remediates only what it can
remediate *correctly*, and `mdrdp <host> --doctor` reports that whole ladder
from the Mac without touching the rhydra stack.

## 2. Settled inputs (not re-litigated here)

- Never auto-reboot quench; never write logon config (loop prompt hard stops).
  "Advise reboot" is the ladder's terminal rung, not an action it takes.
- "Restart DWM" is demoted behind evidence-gathering: the one time we killed
  DWM for this symptom it fixed nothing (parent HLD §3.4 post-mortem).
- stable-green (two samples ≥3 s apart, death counters unchanged) stays the
  bring-up health rule. This tranche adds rungs **beside** it and changes
  neither `green()` nor `stuck` (§8).

## 3. What exists today, precisely

`agent.rs::Reconciler` already reconciles a **bring-up** ladder every tick and
reports it: creator → device → display-mode → server, with the first
unsatisfied step in `StatusReport.stuck`. It restarts the server when the GDI
device name changes (`device_replaced`). `control.rs` carries `Status` and
`RestartServer` at schema 2.

Bring-up health is largely solved. **Liveness is not covered at all.**

## 4. The evidence base, and what it does and does not establish

**Incident A — the capture server delivered nothing while every check passed.**
After an RDP logon to quench's console, the agent was green, the creator alive,
the device present, the mode right, the server running and accepting, and a
client connected and wrote **176 input records** — with `native: frames 0`.
Recovery took three ordered steps (cycle the IDD device, restart the creator so
the section is republished, restart the server).

**What this establishes:** a capture pipeline can be structurally perfect and
deliver nothing, and no existing check notices. That is the tranche's mandate.

**What it does NOT establish — stated plainly because the first draft got this
wrong.** The draft asserted the cause was that `device_replaced` keys on the
GDI display name. That is contradicted by the record: the display *was*
renumbered (`DISPLAY12` → `15` → `16`), and `agent_ops.rs`'s own comment says
the GDI name "changes when the device is re-created, which is exactly the
identity signal the reconciler keys on". So on the evidence it should have
fired. Three candidates remain and the record does not separate them: it fired
and the restart did not help; the rename happened across ticks the agent never
observed; or the agent was not ticking (it was killed and restarted during that
window for AC4's fallback test — the most likely, since a fresh `Reconciler`
starts with `last_device_id: None` and deliberately does not treat first sight
as a replacement).

**The design does not depend on resolving this**, and that is deliberate: the
`pool` rung below detects the *condition* (no pool, or a pool the running
server is not attached to) regardless of which mechanism produced it. The
post-mortem stays open and is recorded as open.

**Incident B — the locked console.** `SendInput` returned success, the injector
thread reported `WinSta0\Default`, and no keystroke reached the desktop: a
locked session's *input* desktop is the secure `Winlogon` one. Invisible to
every capture-side check.

## 5. Where the detector lives — corrected

The first draft claimed only the client can see the wedge, because the agent
"cannot see the client's input channel and, with no viewer, has nothing to
measure". **Both halves of that are false against the code**, and the correction
is the most important change in this document:

- The IDD shared section has a **fixed, well-known name** —
  `SECTION_NAME = r"Global\mdrdp-idd"` (`idd_section.rs:65`) — and any process
  may open it read-only, which is exactly what the capture server does.
- Its header carries `generation: u32` (`idd_section.rs:137`; 0 means the
  driver has published no pool, written by `SharedPool.cpp`'s
  `AdvertiseNoPool`), and its slots carry `frame_seq: u64`
  (`idd_section.rs:184`) — **the driver's presented-frame counter**, advanced
  by the compositor presenting to the virtual display, with no dependence on a
  viewer or even on a capture server existing.

So the agent can answer "is there a pool, and are pixels moving on it?" every
tick, for the cost of one mapped read, **with no viewer at all**. Client-side
detection would have been strictly worse: blind between sessions, lost when the
client dies mid-wedge, one private "escalate once" counter per client, and it
reduces `--doctor` to "untested" on a question the agent can answer outright.

**Decision: the agent detects. The client corroborates but triggers nothing.**

The client still reports what the user experiences ("input flowed, nothing
painted") into the session console, because that is the sentence a user needs.
It drives no remediation.

## 6. The ladder

Rungs in order. Each is named in status, each transition is logged. Rungs 0–3
are today's bring-up ladder, unchanged in behaviour and given names.

| # | Rung | Check | Remediation | Actor |
|---|------|-------|-------------|-------|
| 0 | `creator` | creator process alive | respawn | agent, every tick (exists) |
| 1 | `device` | device present | respawn creator | agent, every tick (exists) |
| 2 | `pool` | section generation ≠ 0, **and** the running server is attached to the current generation | generation 0 → restart **creator**; generation moved → restart **server** | agent, every tick (**new**) |
| 3 | `display-mode` | mode == desired | set mode | agent, every tick (exists) |
| 4 | `server` | process supervised **and** accepting on 9500 | respawn | agent, every tick (accept probe **new**) |
| 5 | `input-desktop` | the agent's own desktop is the current input desktop | none — report | agent, report only (**new**) |
| 6 | `liveness` | `frame_seq` advanced within the window | none — report; names rung 2/5 as the likely cause | agent, report only (**new**) |
| 7 | `section-cycle` | — | cycle device + restart creator + restart server | **explicit operator command only** |
| 8 | `advise-reboot` | — | none | terminal; report evidence |

**Rung 2 (`pool`) is the one that catches Incident A**, and it is the reason
the remediation is now cause-specific. Generation 0 means the driver published
no pool: restarting the *server* cannot help — a fresh server refuses
generation 0 and dies after its 30 s wait, so the "cheap" remediation would
convert a silent wedge into a crash loop with backoff. The creator is what owns
the device's lifetime, so the creator is what gets restarted. A generation that
*moved* while a server is attached to the old one is the stale-attachment case,
and there a server restart is both correct and cheap — the session it drops is
already receiving nothing.

**Rung 4 gains a real accept probe.** Today `running` is set optimistically the
instant spawn returns, which `control.rs` documents; a server that is alive but
not yet listening (the 30 s pool wait) reports green throughout. A loopback
connect-and-close each tick fixes that.

**Rung 5 (`input-desktop`)** compares the **agent's own** thread desktop
against `OpenInputDesktop`. It deliberately does *not* claim to inspect the
injector: the injector is a thread inside the *server* process and Windows
offers no way to read another process's thread desktop. The agent spawns the
server with an inherited station and desktop, so the agent's own desktop is a
sound proxy — and this document says so rather than implying a capability we
do not have. **Access-denied is not a FAIL**: it is also what a different
session or window station returns, so it reports `unknown`. A `FAIL` is only
`OpenInputDesktop` succeeding with a *different* name, corroborated by
`LogonUI.exe` in the session.

**Rung 6 (`liveness`)** reports; it never remediates. When `frame_seq` is
static it says so and names what else is red — a static counter on an idle
desktop is not a fault, and this rung's honesty about that is the point.

**Rung 7 is never automatic.** It recreates the display and drops every session
on the box. §8 puts its guard in the agent, not in client convention.

**Rung 8** gathers evidence and stops. It never reboots.

**No rung above 4 auto-remediates at all.** That is a deliberate reversal of
the first draft, which had the client auto-restart the server on a heuristic
timeout. Three independent reviews converged on why that was wrong: it kills
the session that detected the fault (single-viewer server), it cannot fix the
condition it fires on, a reconnecting client re-fires it, and the one automatic
action would have been the one with the weakest evidence of ever working. The
parent HLD's mandate is "each step logged and reported to the client… one pass,
then surface the state" — reporting *is* the specified behaviour.

## 7. `--doctor`

`mdrdp <host> --doctor` — control-port only **by construction**: its request
set is `{Status}` and nothing else, so it cannot connect the video port, cannot
unpark the capture loop, and cannot force an encode. It does perform an ssh key
logon; that is the one host event it creates and this document says so rather
than claiming "changes nothing".

```
doctor quench.lan.example
  ssh              ok        key auth (BatchMode), 141 ms
  tunnel           ok        9502 forwarded (control only)
  agent            ok        v0.4.0, uptime 4h12m, stable-green
  creator          ok        3 restarts
  device           ok        present
  pool             ok        generation 7, server attached to 7
  display-mode     ok        1920x1080 @ 240 Hz (desired)
  server           ok        supervised, accepting on 9500
  input-desktop    FAIL      input desktop "Winlogon", agent desktop "Default"
                             — the console is locked; injected input cannot
                             land. LogonUI.exe present in session 2.
  liveness         untested  frame_seq static, and nothing is drawing
  viewer           none
```

Precedence, enumerated (tranche 3's standard): `--doctor` implies the native
path whatever the favourite's `native` setting says; `--doctor --rdp` is a
usage error; `--size` is ignored. Against a host with no agent it reports `ssh`
and `agent` and stops — it never falls back to RDP.

**`--doctor --live`** additionally opens a short session and reports frames
seen. It **refuses, naming the holder**, when a viewer already holds the single
slot — the server backlogs a second connect rather than refusing it, so a naive
`--live` would report a wedge on a perfectly healthy host, which is the worst
failure a diagnostic can have. It obeys tranche 3's presence guard. Its
stimulus is stated in §8 and must be shown to produce a decoded frame on a
healthy host before it is trusted as an oracle.

## 8. Wire, protocol and guards

- Control schema **2 → 3**. `StatusReport` gains `rungs: Vec<RungReport>`,
  `pool: Option<PoolReport>`, `input_desktop: Option<InputDesktopReport>` and
  `viewer_connected: Option<bool>`. **Every new field carries
  `#[serde(default)]`** — `query_status` deserialises with
  `serde_json::from_value`, so a missing field without it is a hard
  `QueryError::Bad`, which the connect path turns into a failure. That would
  break the native transport against every not-yet-redeployed host on the day
  this lands. The precedent is already in the file (`version`, added for
  exactly this reason).
- `RungState` is four-way: `Ok | Fail | Unknown | Untested`. The client holds
  the rung vocabulary **statically** and renders any rung the report omits as
  `unknown (agent schema 2)` — an empty `rungs` must never render as green.
- **`stuck` and `green()` are unchanged.** `stuck` stays exactly the bring-up
  precedence over rungs 0–4; rungs 5+ never populate it. This is load-bearing:
  `green()` is `… && stuck.is_none()`, the native connect path hard-refuses on
  `!green`, and `deploy.rs` carries a second hand-rolled copy of the same rule
  in PowerShell. Letting a locked console (rung 5) reach `stuck` would make
  every client on the fleet refuse to open a session on a host whose console is
  merely locked — for a fault that stops no pixel.
- New request `CycleDevice` (rung 7). Its guard lives **in the agent**: the
  request must echo a challenge from the current status (uptime + device
  identity), so a replay, a retry after a read timeout, or any stray loopback
  peer is refused and logged with the caller's reason. Loopback is not an
  authorisation boundary — `probe_over` opens the control forward on every Auto
  connect, and any script on the box can reach it.
- Reverse skew (**schema-3 agent, old client**) is safe, and this is why:
  serde ignores unknown fields, and *nothing* gates on the control envelope's
  `schema` — `query_status` never reads it and the probe deliberately declines
  to version-check the control port. An old agent receiving `cycle-device`
  answers "unrecognised request", a clean degrade.
- New client-side sender `send_request(addr, Request, timeout)` — this does not
  exist today (only `query_status` does), and it carries the same timeout,
  ack-parsing and error-classification hazards, so it gets the same tests.
- `--doctor --live`'s stimulus: a `ScanDown`/`ScanUp` of a key with no effect
  on a focused app (`VK_F13`-class), never a character.

## 9. Out of scope (stated, not silently)

- **Fixing MDR-BUG-FLUX-00011** (the viewer bootstrap). Rung 6 reports it
  honestly; choosing between the two fix shapes is its own change.
- **A native reconnect path.** The first draft's auto-restart implied one; the
  design no longer needs it, and adding one would touch the settled answer that
  transport is chosen at connect time only.
- **MDR-BUG-FLUX-00012's full metrics/HUD wiring.** Rung 6's counter is read
  from the driver's section, not from the client's stats pipeline, so this
  tranche does not need 00012 fixed — which is precisely why the threshold
  problem that worried the first draft has gone away (§11).
- Auto-reboot, DWM restart as a routine rung, any logon/auto-logon config.

## 10. Acceptance criteria

Ordered. AC5's schema-2 clause must run **before** the tranche-4 deploy (the
live agent is schema 2 today); AC7 runs last.

1. **Rung vocabulary and `stuck` isolation.** Table-driven test over all rung
   states: `stuck` == the first non-ok rung among 0–4, and `None` when 0–4 are
   ok **regardless of rungs 5+**. Explicitly: rung 5 `Fail` leaves `stuck`
   absent, `green()` true, and a native connect succeeding. Live: `--doctor`
   prints every rung name with a state from the four-way vocabulary.
2. **Rung 2 catches Incident A's condition.** Induced the cheap way — run
   `mdrdp-cycle-idd` **alone**, which destroys the section while the running
   server holds its old attachment, producing "server bound to a dead section"
   in one step with no RDP logon and no console kick. Assert: rung 2 goes
   `Fail` naming the generation, rung 6 reports `frame_seq` static, and the
   agent's cause-specific remediation (restart creator) restores rung 2 to
   `Ok` — with a viewer then decoding ≥1 frame under the doctor's stimulus,
   n=3, counts quoted.
3. **Rung 5 catches a locked-console-equivalent without a lock.** The
   comparison logic is proven in a unit test over injected desktop-name pairs
   (including the access-denied → `Unknown` case). Live, the input desktop is
   moved by triggering a **UAC elevation prompt** in the console session, which
   raises the secure desktop and **self-clears on its own timeout** — so the
   run needs no unlock. AC2 of the first draft (lock the console, then unlock
   it) is deliberately abandoned: `LockWorkStation` cannot be driven from ssh,
   and the only proven clear (`tscon`) is evidenced for a *disconnected*
   session, not a locked attached one — an unlock we cannot perform would
   strand the box with no permitted recovery.
4. **Rung 7 cannot be reached except explicitly.** Structural, not an
   enumeration: `CycleDevice` is constructible only through a function taking
   an operator-confirmation token defined in the CLI module, so any other
   caller fails to compile; plus an agent-side test that an unaccompanied or
   replayed `CycleDevice` is **refused and logged**. Live: one explicit run
   performs the recovery and ends with frames flowing (not merely "green").
5. **`--doctor` touches nothing.** Unit: its request set ⊆ `{Status}`, enforced
   structurally. Live: across a run, creator/server restart counts and pids
   identical, device identity and mode identical, agent uptime strictly
   increased and never reset, and **no new `video: connected` line in the
   server log** (the witness the first draft lacked — its chosen witnesses
   could not have detected the violation they existed to catch). Against the
   live **schema-2** agent it names every rung it cannot judge and invents no
   green.
6. **No auto-remediation above rung 4.** Test: with rung 5 `Fail` and rung 6
   reporting static, zero `RestartServer` and zero `CycleDevice` requests are
   emitted. Live: five consecutive fresh connects to an idle quench desktop
   (the scenario tranche 3 measured as 1/1/0/0/4 decoded frames) produce zero
   remediation requests.
7. **Hygiene.** fmt, clippy `-D warnings` (both crates), focused tests with
   stdin closed, `./scripts/check-windows.sh`, rhydra cross-build, viewer
   lockstep. Every new test demonstrated red once from a saved copy.

## 11. Risks

- **The `pool` rung reads a shared section written by the driver.** A
  malformed or torn read must degrade to `Unknown`, never to a confident
  `Fail` that triggers a creator restart. The section reader already has
  precedent for refusing junk; the rung inherits it.
- **Rung 6 on an idle desktop is legitimately static.** It reports
  `untested`/`static`, never `Fail`, and drives nothing — which is why the
  first draft's `LIVENESS_GRACE` threshold problem has disappeared. That
  threshold would have needed a measured healthy input→frame distribution
  (this repo's "quote a distribution, never one run"), and the instrument for
  it does not exist yet (MDR-BUG-FLUX-00012). Removing the automatic action
  removed the need for the number.
- **AC2's inducer still perturbs the rig** — `mdrdp-cycle-idd` alone is far
  cheaper than an RDP logon (no console kick, no renumbering), and the
  recovery is the known two remaining steps. Board claim before the run.
- **If the recovery ever fails**, the box counts as genuinely wedged under the
  loop prompt's clause, the reboot is authorised on that basis, and the
  journal records the evidence. Stated so the run has written authority.

## 12. Review record

Three adversarial reviewers (design, evidence/falsifiability, scope/safety) ran
against the first draft. The external Codex pass is still quota-blocked
(returns 2026-08-20 04:32) and is queued.

**Adopted — the draft was wrong and the design changed:**

- **The detector's placement (§5).** The draft's central claim — only the
  client can see the wedge — was refuted against the driver source: the section
  name is fixed, the header carries `generation`, the slots carry a
  driver-written `frame_seq` that advances with no viewer. Detection moved to
  the agent; the client demoted to corroboration. This one change also
  dissolved the multi-client problem, the "escalate once" enforcement problem,
  and `--doctor`'s "untested" answer.
- **Rung 5's auto-restart is gone.** Traced concretely: the driver writes
  `Generation = 0` on teardown; a *running* server at generation 0 loops on
  timeout forever; a *fresh* server refuses generation 0 and dies after 30 s
  into backoff. So the draft's one automatic action would have turned a silent
  wedge into a crash loop **and** killed the session that detected it (the
  server is single-viewer). Remediation is now cause-specific and lives with
  the reconciler; nothing above rung 4 auto-remediates.
- **`stuck` must not absorb the new rungs.** `green()` gates the native connect
  and `deploy.rs` carries a second copy of the rule, so a merely-locked console
  would have made every client refuse to connect. `stuck` left exactly as it is.
- **`#[serde(default)]` on every new field**, or the schema bump breaks the
  native transport against every deployed host on landing day.
- **Rung 4 gains a real accept probe**; `running` is set optimistically today,
  so "alive but not listening" reported green.
- **Rung 5 cannot inspect the injector's desktop** (different process); it is
  now honestly the agent's own desktop as a stated proxy, and access-denied
  reports `Unknown` rather than a confident "locked".
- **The `CycleDevice` guard moved into the agent** with a challenge echo;
  loopback is not an authorisation boundary.
- **AC2's lock/unlock replaced** by a self-clearing UAC-prompt inducer: the
  unlock was unproven and every fallback was forbidden or harmful.
- **AC3's inducer replaced** by `mdrdp-cycle-idd` alone — a reviewer found this
  cheaper, deterministic route that needs no RDP logon and no console kick.
- **AC5's witnesses replaced**: the draft's (uptime, restart counters, device
  identity) could not have detected the violation the AC exists to prevent, and
  "uptime unchanged" fails on a correct implementation.
- **§4's root cause claim withdrawn.** The draft asserted why `device_replaced`
  did not fire; the record contradicts it. The post-mortem is now recorded as
  open, and the design deliberately does not depend on it.
- **A false claim deleted:** the draft said the detector "fires correctly on
  MDR-BUG-FLUX-00011". That bug's own measurements show input-gating makes it
  self-heal (5/5 decoded when the session types), so an input-gated detector
  never fires on it.

**Minors folded:** flag precedence table; `--doctor` against an agentless host;
`--doctor --live` refusing when the slot is held; the stimulus specified as a
no-effect scancode; `send_request` named as new work with timeout tests; the
`probe stages` safety analogy stated precisely (no RDP logon, no credential);
"one pass, never a loop" scoped to rungs 5+ (rungs 0–3 loop with backoff by
design, so the draft's AC6 was false of the existing reconciler); reverse skew
documented with its reason.

**Refuted by the reviewers' own checking (recorded, no change):** no new
dependency is needed (`Win32_System_StationsAndDesktops` is already enabled);
the logon-config prohibition is not approached anywhere; rung 8 stays clear of
the reboot hard stop; no settled answer is contradicted; no creep into tranches
5–7; AC3's induction is repeatable rather than a race; `§2`'s viewer-parked
capture-loop claim is accurate and correctly load-bearing; the input-gating
rationale itself is sound (the objections were about what the gate measures and
what follows it, not the gate).

### The `liveness` rung's shape, settled by the live runs

It reports `Ok` only while the counter moves, `Untested` when it does not, and
**never `Fail`**. The live runs are why that is right rather than timid:
quench's idle desktop leaves `frame_seq` static for minutes at a time, and any
check that called that a fault would fire constantly on a perfectly healthy
host. The wedge is named by the `pool` rung, which has a structural fact to
point at.
