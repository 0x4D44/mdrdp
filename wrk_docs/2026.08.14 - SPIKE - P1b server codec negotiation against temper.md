# SPIKE — P1b: what `temper` actually negotiates

2026-08-14 · Gauntlet part **P1b** · observed through FreeRDP 3.27.1 (`sdl-freerdp`)

## Headline

**`temper` sends ClearCodec and RFX Progressive. It does not send H.264, even when H.264
is permitted.** Both of those codecs are exactly the two that P1a found are **not wired
into IronRDP's client decode path**.

This is the largest architectural finding in the project so far, and it inverts a working
assumption: H.264 with a VideoToolbox backend was expected to be the macOS win. For this
workload it is irrelevant. The real work is ClearCodec and Progressive.

## Method

Two runs against `temper` (Windows 11 Pro, LAN), differing only in the codec offer — a
two-point offer matrix, because a single run reports one selection, not the server's
ceiling. Authentication is CredSSP/NLA; the certificate is self-signed and was accepted
permanently on first use.

Sessions were ~40 s of an idle-to-lightly-used desktop at 1024×768.

| Run | Client offer | Server confirmed | Codecs received |
|---|---|---|---|
| 1 | default (AVC not enabled; `CAPVERSION_81` carried the AVC-disabled bit, flags `0x12`) | `RDPGFX_CAPVERSION_107`, flags `0x02` | ClearCodec, CAProgressive |
| 2 | `/gfx:AVC444` (AVC-disabled bit cleared — `CAPVERSION_81` flags `0x02`) | `RDPGFX_CAPVERSION_107`, flags `0x02` | **141× ClearCodec, 9× CAProgressive, 0× AVC** |

Run 2 is the load-bearing one: **AVC was not disabled by either side, and the server still
never used it.** Windows' encoder picks per region, and for text and UI, ClearCodec wins;
Progressive handles the photographic regions. H.264 is for video-like content.

## Confirmed

- **Graphics pipeline is EGFX over a dynamic virtual channel.** `drdynvc` loads the
  `rdpgfx` plugin; the server confirms `RDPGFX_CAPVERSION_107` (`0x000A0701`). The
  connection-confirm flags include `DYNVC_GFX_PROTOCOL_SUPPORTED`.
- **`RDPGFX_CODECID_CLEARCODEC` (0x0008) is dominant** — 141 of 150 surface commands in
  run 2, carried on `RDPGFX_CMDID_WIRETOSURFACE_1`.
- **`RDPGFX_CODECID_CAPROGRESSIVE` is the remainder** — 9 of 150.
- **No RemoteFX, no NSCodec, no AVC420, no AVC444** in either run.
- **Session surface** is created at 1024×768, pixel format `0x21`, with
  `MapSurfaceToScaledOutput` — so scaled output is in play, relevant to P3b.
- **CLIPRDR negotiates version 2**, `generalFlags 0x0000003E`:
  `CB_USE_LONG_FORMAT_NAMES`, `CB_STREAM_FILECLIP_ENABLED`, `CB_FILECLIP_NO_FILE_PATHS`,
  `CB_CAN_LOCK_CLIPDATA`, `CB_HUGE_FILE_SUPPORT_ENABLED`. Useful input to P5.
- **Credential format:** `user@example.com` authenticates directly. No
  `MicrosoftAccount\` prefix and no `temper\` prefix were needed.

## Not established

- **Whether `temper` will use H.264 for video content.** Both sessions showed a static
  desktop. A session playing video may well produce AVC420/444 frames. Untested, and it
  matters for whether a VideoToolbox backend is ever worth building.
- **What IronRDP's own offer would elicit.** IronRDP's connector advertises a different
  capability set from FreeRDP's, and codec selection is an intersection. This spike bounds
  the question; only P2c settles it, when our own EGFX caps-advertise/confirm exchange
  runs against this host.

## Consequences for the plan

**P3a grows substantially.** Decoding what this server sends means wiring ClearCodec and
RFX Progressive into the EGFX path ourselves, using the primitives that exist in
`ironrdp-graphics` but have no call site in `ironrdp-session`. That is real work, and it
is now on the critical path rather than being an optional codec-coverage improvement.

**The H.264/VideoToolbox track drops in priority.** It was the cheap, attractive win —
`H264Decoder` is a pluggable trait needing no upstream changes — but on the evidence it
would decode nothing during ordinary desktop use. Keep it in reserve, pending the video
question above.

**A fallback exists but is unattractive.** IronRDP's client does decode legacy bitmap
paths and RemoteFX. Forcing the session away from EGFX would work without new decoders,
at a significant cost in bandwidth and quality, and it would concede the performance
argument that motivates this project. Not recommended; recorded so the option is explicit.

## Evidence handling

The raw traces are ~1.1 MB each of full session detail — surface geometry, damage
rectangles, clipboard activity. That is session content and is **deliberately not
committed**. They live at `/tmp/mdrdp-freerdp-trace.log` and `/tmp/mdrdp-freerdp-avc.log`
and should be deleted once no longer needed; the figures above are the extract worth
keeping. Reproduce with:

```
sdl-freerdp /v:temper /u:'<account>' /gfx:AVC444 /log-level:TRACE > trace.log 2>&1
grep -oE 'RDPGFX_CODECID_[A-Z0-9]+' trace.log | sort | uniq -c | sort -rn
```

Note `xfreerdp` is the X11 client and fails immediately on this Mac (`failed to open
display`) — XQuartz is not installed. Use `sdl-freerdp`.
