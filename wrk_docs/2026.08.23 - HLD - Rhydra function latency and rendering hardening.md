# HLD — Rhydra function, latency, and rendering hardening

**Status: SELF-APPROVED**  
**Date:** 2026-08-23  
**Target:** Quench, 5120×2880 at 240 Hz, Windows scale 200%

## Intent

Make Rhydra dependable enough to replace Microsoft Windows App for normal desktop use,
beat Windows App's end-to-end interaction latency under matched conditions, and preserve
at least its visible rendering quality at 5K/200%.

The change is successful only when function, latency, and fidelity pass together. A fast
stream that misses input, presents incomplete tiles, drops clipboard data, or visibly
damages the desktop is a failure.

## Scope

In scope:

- the Windows Rhydra server and the macOS native-viewer boundaries needed to prove or fix
  capture, transport, decode, presentation, input, cursor, clipboard, audio, display, and
  reconnect behaviour;
- the listener and stream lifecycle, queue bounds, pacing, timestamp truth, and failure
  reporting that affect reliability or latency;
- deterministic and live 5K/200% rendering checks, including colour, scale, text, tile
  completeness, recovery, and motion;
- matched release-build measurements on Quench against Windows App 11.3.8, rechecking its
  installed version before the comparison;
- small, independently green fixes, each integrated before the next unit starts.

Out of scope:

- replacing SSH as Rhydra's authenticated control plane;
- RemoteApp, multi-monitor support, or a new Windows protocol-provider architecture;
- a new codec subsystem, dependency, compatibility layer, or speculative feature flag;
- trading correctness or fidelity for a flattering latency number;
- migration or rollback choreography in this development sandbox.

## Approach

### 1. Establish truthful baselines

Use release builds only. Record the Mac model/display refresh and fixed/variable refresh
state; network path; Quench session, resolution, refresh, and scale; codec; server/client
versions; and load. Confirm one viewer only and validate the measurement oracle before
quoting comparisons.

Run `probe glass` against the same deterministic Notepad workload in Rhydra and Windows
App. Take at least 500 randomized trials per arm. Report first-pixel and converged-glyph
p50 with confidence interval, p95, min, max, timeouts, poisoned samples, observed sample
gap, and the instrument's uncertainty band. Interleave or run the arms back-to-back in the
same session and power state. A median-only or unmatched comparison is not evidence.

Capture Rhydra's joined server/client stage telemetry by `frame_seq` alongside glass so a
latency regression can be assigned to capture, conversion, encode, send, decode, present,
or the uninstrumented residual instead of guessed from the total.

### 2. Harden function before optimizing it

Resolve reviewed correctness failures in descending impact. Each defect gets its own fresh
bug worktree and regression test that is observed red before the fix. Integrate each green
unit before starting the next so Quench always runs a known trunk build.

The initial known queue is:

1. memory-safe clipboard reads (`MDR-BUG-FLU-00042`);
2. favourite/doctor identity, first/static frame, and listener truth
   (`MDR-BUG-FLU-00034`, `MDR-BUG-FLUX-00011`, `MDR-BUG-FLU-00037`);
3. input and auxiliary-stream progress/deadlines (`MDR-BUG-FLU-00038`,
   `MDR-BUG-FLU-00039`);
4. bounded converter/control resources and targeted shutdown
   (`MDR-BUG-FLU-00043`, `MDR-BUG-FLU-00044`, `MDR-BUG-FLU-00040`);
5. honest send and native-session telemetry (`MDR-BUG-FLU-00045`,
   `MDR-BUG-FLUX-00012`);
6. valid 5K HEVC signalling (`MDR-BUG-FLU-00041`).

The adversarial review may reorder, refute, merge, or add items. Existing ledger entries
are inputs, not proof.

### 3. Optimize only measured critical paths

After the functional baseline is green, rank stage medians and tails. Change the narrowest
load-bearing stage. Prefer removing waits, redundant copies, stale queued work, and broad
locks over adding threads or buffering. Keep newest-complete-frame semantics and explicit
backpressure. Never suppress codec input because a dirty-rectangle path appears exact.

Every latency change must show:

- a red or slower control arm and a same-session release-build treatment arm;
- no increase in timeouts, poisoned samples, dropped/incomplete frames, stale tiles,
  input loss, memory growth, or visible damage;
- joined internal stage data that agrees with the glass direction and magnitude;
- at least 500 valid trials per quoted final arm.

### 4. Prove rendering, not just codec output

Use both deterministic pixels and the live compositor:

- exercise the existing 5120×2880 real Windows capture and adversarial code/spreadsheet
  test card through the actual negotiated codec path;
- require correct BGRA/RGBA colour identity, full-range BT.709 handling, 200% geometry,
  two-tile frame completeness, keyframe recovery, and no stale or unpainted regions;
- compare captured Rhydra and Windows App output for the same desktop and scale, including
  text, gradients, saturated colours, thin lines, scrolling, video, and cursor edges;
- retain the established 4:2:0 controls: luma PSNR `inf` and SSIM `1.000000` for the
  lossless conversion control; on the real 5K frame, chroma PSNR no worse than the measured
  U 54.23 dB / V 58.59 dB and whole-frame ΔE2000 p95 no worse than 0.68 for the realistic
  encoded path, unless an actual hardware-path baseline justifies a documented replacement;
- treat one-device-pixel saturated chroma at 100% as the known 4:2:0 limit, not as evidence
  that ordinary 2× text is damaged.

Subjective inspection can catch defects but cannot waive a failed pixel or completeness
oracle.

### 5. Validate realistic use and stability

On the combined integrated trunk build, exercise cold and warm connect, static first frame,
two consecutive fresh-viewer joins without server restart, reconnect after a broken stream,
visible app launch/placement, typing, pointer/cursor, clipboard both ways, audio playback,
scrolling, and YouTube motion while typing and moving the pointer.

Once interactive acceptance is green, run an eight-hour Quench soak with periodic motion,
audio, input, and reconnects. Record distributions and counter deltas, not a single final
health observation. Restore the console and release Quench afterward.

## File impact

Expected, subject to surviving findings:

- `tools/latency-spike/server/src/` — Windows capture, encode, listeners, input,
  clipboard, auxiliary channels, resource bounds, and telemetry;
- `src/native/`, `src/probe/`, and `src/bin/probe.rs` — only where client behaviour or the
  measurement oracle needs correction;
- platform-focused tests beside the affected modules and existing Windows check scripts;
- `bugs/`, `wrk_docs/evidence/`, and `wrk_journals/` for durable findings and evidence.

No dependency or wire-format change is planned. Any such need is an architectural fork.

## Acceptance criteria

1. Every surviving critical/high finding from the function, latency, and rendering reviews
   is fixed and integrated, or work stops at a genuine unresolved architectural fork.
2. Quench reports 5120×2880 at 240 Hz and effective 200% scale; cold/warm connection,
   static first frame, app visibility, reconnect, keyboard, pointer, single visible cursor,
   clipboard both ways, and real audio all work without restarting the host.
3. Under matched Quench conditions, Rhydra's glass p50 confidence interval and p95 for both
   first-pixel and converged-glyph latency are lower than Windows App 11.3.8's. Rhydra also
   satisfies its existing absolute gate: p50 CI upper bound ≤40 ms, p95 ≤75 ms, zero
   timeouts, and at most five poisoned trials. If sampling cannot distinguish the clients,
   the result is undecided, not a win.
4. The actual 5K negotiated path preserves colour identity, 200% geometry, complete tiles,
   recovery, and the deterministic quality gates above. Side-by-side captured output is no
   worse than Windows App on normal 2× desktop content.
5. Video load does not make input or pointer interaction seconds late. Queue-depth,
   dropped-work, memory, and stage telemetry remain bounded and truthful throughout the
   interactive run and eight-hour soak.
6. Each new regression test is observed failing once. Focused tests, format/lint checks,
   the server Windows check, and the repository integration gate pass on the exact commit
   that is pushed.

## Review record

Three independent adversarial reviews covered function/reliability, end-to-end latency,
and rendering/5K quality. Each other lane then tried to refute the concrete findings. All
checks executed; nothing below is `UNVERIFIED`.

| survivor | verdict after refutation | disposition |
|---|---|---|
| A disconnect can leave injected keys/buttons held | confirmed by latency and quality reviewers | `MDR-BUG-FLU-00048`, Must/High; fix early |
| Native readiness retries can overshoot/misclassify deadlines | confirmed narrowly; startup only, normal refusal is immediate | `MDR-BUG-FLU-00049`, Should/Medium |
| Per-message stats persistence/socket telemetry blocks the sole server sender and is absent from `send_done_us` | confirmed by function and quality reviewers | `MDR-BUG-FLU-00050`, Must/High; measure then remove from the critical path |
| A two-message queue can accept rect + tile 0 and drop tile 1 | confirmed; stale visible output is conditional when rects already painted | `MDR-BUG-FLU-00051`, Must/High; require logical-frame coherence rather than simply enlarging backlog |
| Spike-viewer decode-side stats writes block decode | confirmed, but only some decode-side rows rather than all rows | `MDR-BUG-FLU-00052`, Could/Medium; harness accuracy, not production client |
| Spike-viewer rect COW clones the full 56.25 MiB 5K canvas | confirmed | `MDR-BUG-FLU-00053`, Could/Medium; harness accuracy, not production client |
| One 64 KiB reader batch can run roughly 1,600 tiny rect callbacks before later video | confirmed for decode dispatch, not the UI event loop | `MDR-BUG-FLU-00054`, Should/Medium |
| Native input latency stamps after the last write in a burst | confirmed; glass remains the external oracle | `MDR-BUG-FLU-00055`, Should/Medium; repair before trusting stage attribution |
| Spike-viewer input writes can block the window thread | confirmed, conditional on a non-reading peer | `MDR-BUG-FLU-00056`, Should/High; harness reliability |
| IOSurface selection overwrites an in-use non-last surface when all candidates are busy | confirmed by function and latency reviewers | `MDR-BUG-FLU-00057`, Must/High; never trade tearing for throughput |

Refuted overclaims were removed: the deadline defect does not affect steady-state latency;
the queue defect does not guarantee stale visible pixels when the rect overlay already
painted the change; not every spike stats row runs on decode; and batch dispatch does not
monopolise the separate UI event loop.

The one fresh-eyes Claude/Fable design review did not run: Claude Code 2.1.240 returned a
session-limit refusal before reading the design. It was not retried. Residual risk: all
executed reviewers are from the Codex model family, so correlated blind spots remain.

## Decision log

- Correctness and resource bounds precede speed work because corrupt or stale output makes
  a low latency number meaningless.
- Compare with Windows App because Arthur made replacement quality and latency the product
  bar; the older decision to omit that row no longer applies.
- Keep HEVC 4:2:0 unless actual 5K evidence fails. Existing data says it preserves ordinary
  2× desktop luma and avoids a large speculative 4:4:4 subsystem.
- Preserve the established 1440p H.264 bits-per-pixel budget at 5K: 5K has four times the
  pixels, so its supervised budget is 80 Mbit/s total, split across two tiles. Fail and
  retry if the display mode cannot be read rather than silently launching at 20 Mbit/s.
- Prefer deletion, tighter ownership, and explicit limits over new abstractions, flags, or
  buffering.
- Integrate small green units so interactive testing always exercises combined trunk, not
  an unshared branch.
