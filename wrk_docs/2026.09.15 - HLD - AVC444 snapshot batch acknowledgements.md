# AVC444 snapshot batch acknowledgements

<!-- STATUS: Implemented; live visual verification pending -->

This corrects MDR-BUG-FLU-00130's 0.1.247 acknowledgement race. It supersedes
the current-stamp acknowledgement section of the 2026.09.14 bounded luma-wait
design, not its ordered decoding or fixed 50 ms first-luma deadline.

## Decision

Keep a released-batch token separately from the pending luma regions and their
deadline. The presenter captures that token with its coherent snapshot. A
successful submission retires only that token, without testing whether the
producer is idle or still at the same presentation stamp.

A Fable cross-family consult checked the acknowledgement, retry and lifecycle
invariants. The lead accepted this token design. Advice about rarity of early
luma exposure and zero ignored acknowledgements is not a measured guarantee:
newer released tokens can legitimately make an older acknowledgement obsolete.

## State and transitions

- Pending: bounded disjoint luma regions and one deadline, armed by the first
  luma and never extended by later luma in that batch.
- Ready: an optional sequence token for released work awaiting submission.
- Snapshot: pixels, mapping, presentation stamp and captured ready token.

Completion, timeout, region-budget fallback and urgent non-AVC mutation release
pending work: clear its ledger/deadline and advance the ready token. New incoming
luma is still tracked, even while ready work exists. An outstanding ready token
overrides the newer pending deadline for scheduling, so a failed submission can
retry without an ever-moving wait.

Both metadata ingestion and the presenter timer settle expired deadlines. The
timer must do this before copying: expiry may occur without any further server
message. Coherent copy still rejects active updates/frames and retains the old
snapshot for aborted or suppressed output. Only Copied/Empty capture a token.

On success, acknowledge the snapshot token. Equality clears ready only; it
never clears pending regions or their deadline. A nonmatching/absent token is
harmless. Busy/error paths do not acknowledge or update the displayed stamp.
If newer work released another token during rendering, the old token cannot
retire it, and the next draw remains due.

Reveal and surface/mapping lifecycle changes clear obsolete policy state but
never reset the sequence counter. Therefore a delayed acknowledgement cannot
erase a new incarnation's ready token. No new pixel buffer, codec change or
dependency is required.

## Limits and validation

Latest-snapshot supersession remains intentional. New luma arriving between
release and copying, including during a failed draw's retry, can appear early
alongside older ready work. Its pending ledger survives the acknowledgement.
This fixes persistent bypass, not every possible coarse/refined transition.

The 50 ms deadline is still fixed, not adaptive. Chroma later than the cap, or
never arriving, can still produce separate presentations. Adaptation needs
measured arrival timing and a bounded latency policy; it is a separate change.

Deterministic tests must cover an acknowledgement during newer active decode,
timer-only expiry, newer completed stamps, stale/duplicate tokens, lifecycle
reset, and a failed submission followed by newer luma and successful retry.
Assert pixels as well as policy where the existing window harness permits.
Observe the regression fail before the fix and mutate new token protections
to prove their assertions. Focused surface/window/graphics checks, formatting,
Clippy and Windows type-check precede integration. A live affected release
session remains necessary to judge the visual outcome.
