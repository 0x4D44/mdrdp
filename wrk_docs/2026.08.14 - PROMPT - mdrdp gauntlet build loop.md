# PROMPT — mdrdp Gauntlet build loop

2026-08-14

The build charter for mdrdp. It fuses two things:

- **Matt Shumer's Gauntlet Loop** — the agent (not the human) splits the goal into parts;
  each part gets a specialist builder and a *separate, blind* critic; the critic passes a
  part only when it beats a concrete real-world reference, compared side by side. The
  builder never grades its own work, and a critic who saw round N never grades round N+1.
- **The fleet's 2L "Light - full flow"** — worktree-first, mini-HLD, adversarial review,
  cross-family external review, self-approved checkpoint, implement, code review, simplify,
  validate, journal.

They fuse without friction: 2L is the *method inside a part*, the Gauntlet is the *loop
over parts* and the *bar that says when a part is done*.

## Why this shape, for this project

Shumer's original Gauntlet judged a game — a critic can look at a screenshot and say
"worse than Call of Duty". An RDP client cannot be graded by eye. Its whole point is
behaviour over hours: a clipboard that does not wedge, latency that does not drift, a
window that survives the night.

So the bar here is **measured, not aesthetic**, and that forces one hard sequencing rule:
**the scoreboard is built before anything it judges.** You cannot run a Gauntlet without a
metric, and Arthur wanted the stats anyway — so the instrumentation is Part 0, not a
nice-to-have bolted on at the end.

The second consequence is an honesty rule. Some comparisons against Microsoft's client are
genuinely hard to instrument. A critic that could not run its measurement must report
**UNVERIFIED**, never PASS. That is the same rule the fleet's own prompts use, and it is
what stops a Gauntlet degenerating into agents agreeing with each other.

## The prompt

Paste everything between the rules below.

---

Build **mdrdp** to completion under a Gauntlet Loop. Read `CLAUDE.md` first — it carries
the decided architecture, the scope boundary, and the validation rules, and it wins over
your own preferences on all three.

### OBJECTIVE

Ship a portable (macOS + Windows), all-Rust RDP client that is *measurably* better than
Microsoft's Windows App on the five failures that motivated it: clipboard death, window
geometry destroyed by display sleep, latency degrading over a session, no visibility into
what the client is doing, and general performance. Plus a favourites launcher, one server
per invocation, and audio output.

Done means: Arthur uses it daily instead of Microsoft's client, and can show the numbers
that justify the switch.

### METRIC — the bar you must beat

**The reference is Microsoft's Windows App (Remote Desktop) for macOS**, connecting from
the same Mac to the same Windows 11 Pro host over the same LAN, under the same conditions.
It is installed and it is the thing being replaced. For protocol *correctness* questions,
FreeRDP is the secondary reference — read it, do not copy from it.

A part passes only when a blind critic produces **evidence** that mdrdp equals-and-is-
simpler, or beats, the reference on that part's dimension. Concretely, these are the
dimensions and how each is honestly measurable:

| Dimension | How to measure | Feasibility |
|---|---|---|
| Clipboard reliability | Scripted round-trip soak: N transfers over hours, both directions, text + image + large payloads. Count wedges. | Straightforward on both clients |
| Window geometry survival | Drive display-configuration changes (`displayplacer`, monitor power-off, lock/unlock, sleep/wake) and assert window frame *and* remote session resolution afterwards | Straightforward |
| Latency stability | Internal input→frame-ack RTT over a long session; watch for monotonic drift. Cross-client comparison via high-FPS screen capture of a timestamp pattern | Internal: easy. Cross-client: hard — say so |
| Resource cost | Sample CPU / RSS / GPU during a fixed workload (1080p video playback, scrolling text) on both clients | Straightforward |
| Reconnect time | Scripted kill/restore of the link, stopwatch to usable session | Straightforward |
| Visibility | Reference has none. Ours must expose codec mix, cache hit rate, decode p50/p99, frame drops, RTT | Ours wins by existing — but the numbers must be *correct*, which is itself testable |

**Rules that keep this bar honest:**

- A measurement that did not actually run is **UNVERIFIED**, never PASS. Rate-limited,
  skipped, or degraded checks are incomplete results, not passing ones.
- Debug builds are never evidence (see `CLAUDE.md`).
- Every number carries its conditions: host, network, resolution, codec, build profile.
- A critic may not pass a part on reasoning alone. No evidence, no pass.

### BOUNDARY

- **Rust only.** Portable macOS + Windows from one codebase; platform code confined behind
  traits in named modules.
- **Build on IronRDP.** Do not reimplement the protocol.
- **Scope is `CLAUDE.md`'s.** Audio in; drive redirection, multi-monitor, RAIL, smart-card
  out. If a part seems to need one, stop and raise it — do not quietly widen scope.
- **No cloud CI.** Validation is local.
- **Never weaken a gate to pass it.** Fix the code, or report that you cannot.
- **Stop and ask Arthur** on: a genuine architectural fork; a critical finding
  (correctness, data loss, security) you cannot resolve; a part that fails its Gauntlet
  three rounds running; or anything needing a credential.
- **Never log or commit** credentials, clipboard payloads, or session contents.

### THE LOOP

**Phase 0 — decompose (you, not Arthur).** Read `CLAUDE.md` and the current state of the
repo. Split the objective into parts that are independently buildable and independently
*judgeable against the bar*. Write the part list, its ordering, and the one-line pass
condition for each part into `wrk_docs/` before building anything. Two hard constraints on
your cut:

1. **The scoreboard comes first.** The instrumentation and the A/B measurement harness are
   Part 0. Prove the harness works by pointing it at the *reference client* and getting
   numbers out. A bar you cannot measure is not a bar.
2. **Prove the protocol path early.** Before committing to the render and UI architecture,
   spike what actually negotiates against Windows 11 Pro over LAN — which codecs, whether
   EGFX comes up, whether IronRDP's client-side H.264 path is needed at all at this
   bandwidth. This is the single largest unknown in the project. Report what you find
   before designing around a guess.

Appendix A below is my seam analysis. Treat it as input, not instruction — re-cut it if
you have a better read, and say why.

**Phase 1 — per part, run the 2L flow.** In its own worktree
(`deltic start-task <slug>`), never the main clone:

1. **Understand** the relevant code. Restate in one line what this part achieves.
2. **Design** a mini-HLD — scope, approach, file impact, explicit acceptance criteria, short
   decision log — to `wrk_docs/YYYY.MM.DD - HLD - <desc>.md`. The part's pass condition from
   Phase 0 is among its acceptance criteria.
3. **Adversarial review**: 2-3 independent reviewers critique the design, then each tries to
   refute the others' findings. Only survivors count; a finding whose refutation check did
   not run is UNVERIFIED, not a survivor. Fold survivors into the doc.
4. **External review**: one light pass from a *different model family* — you are Claude, so
   review with Codex (`codex exec -s read-only --skip-git-repo-check -m gpt-5.6-sol -c
   model_reasoning_effort=xhigh "<prompt + design path>" < /dev/null`). One pass, no fan-out.
   If it cannot run, journal that and carry "external review did not run" as a residual risk.
5. **Checkpoint**: mark the design `Status: SELF-APPROVED`, commit it, post a short summary,
   and proceed without waiting — unless a Boundary stop condition fired.
6. **Implement**, tests-first where apt, to the acceptance criteria.
7. **Code review** (`/code-reviewer`), then a quality-only simplicity pass (`/simplify`).
   Prefer deleting over abstracting.
8. **Validate**: fmt, clippy, tests clean, acceptance criteria met. Commit.

**Phase 2 — the Gauntlet gate.** Now the part faces a critic it has never met.

- The critic is a **fresh agent that did not build this part** and has not seen a previous
  round of it. A builder never grades its own work. A critic who failed round N never
  grades round N+1 — spawn a new one.
- Brief the critic with: the part's pass condition, the bar (Microsoft's client on the same
  dimension), and the measurement harness. Not with the builder's summary of how well it went.
- The critic's mandate is **ruthless**: pass only on evidence that the part meets or beats
  the reference. Its output is a verdict plus the measurements that justify it, and every
  measurement is labelled Confirmed or UNVERIFIED.
- **FAIL** → back to Phase 1 with the critic's findings, a fresh builder brief, and a fresh
  critic waiting. **Three failed rounds on one part → stop and bring it to Arthur.**

**Phase 3 — integrate.** A part that passes its Gauntlet gets integrated to `origin/main`
via the worktree-first flow (`deltic integrate`), then its worktree and branch cleaned up.
Integrate part by part — do not accumulate a mountain of unintegrated work. Integration
owns the single version bump; never pre-bump on the branch.

**Phase 4 — next part.** Re-read the part list. Re-cut it if what you learned changes the
right seams, and say why in the journal. Then loop.

### THROUGHOUT

- Maintain a journal in `wrk_journals/YYYY.MM.DD - JRN - <desc>.md`: decisions, surprises,
  dead ends, and every Gauntlet verdict with its evidence.
- Defects you find but are not fixing now go to the `bugs/` ledger. Out-of-scope
  observations go to `scratchpad.md`. Durable non-obvious gotchas go to `lessons_learnt.md`.
- Commit after each unit of work that compiles and passes tests. Stage by explicit path,
  never `git add -A`.
- This build is far too large for one context. Run it under a self-paced continuation loop
  (`/loop`, see the `loop-build` skill) so each iteration re-enters with fresh context,
  bootstrapping from committed-green work plus the journal handoff.

## Appendix A — seam analysis (input to Phase 0, not instruction)

My read on where the natural part boundaries fall, and why. The lead agent may re-cut this.

- **P0 · Scoreboard.** Stats collection, the HUD, and the A/B harness. First because
  everything after it is judged by it. Proven by measuring the reference client.
- **P1 · Protocol spike.** What actually negotiates against Windows 11 Pro over LAN. Not a
  shippable part — a report that de-risks every architectural choice after it. The one
  genuinely unknown thing in the project.
- **P2 · Session core.** Connect, authenticate (NLA), decode, present. Keyboard and mouse.
  The vertical slice that makes it an RDP client at all.
- **P3 · Latency discipline.** Frame-ack flow control, drop-to-latest presentation,
  `TCP_NODELAY`, input path off the render loop. Judged on drift over a long session — this
  is where the reference client loses.
- **P4 · Clipboard.** Bounded-request state machine that cannot wedge, plus the pasteboard
  polling loop. Judged by soak, not by unit test.
- **P5 · Window policy.** Geometry persistence across display-configuration changes, and the
  fixed-resolution default that stops the remote session ever reflowing. The requirement
  that is most macOS-specific and most valuable.
- **P6 · Favourites launcher.** Process model, the list UI, keychain-backed credentials.
- **P7 · Audio.** RDPSND output.

P3, P4 and P5 are the three that justify the project existing. P2 is table stakes and the
reference client already does it well — do not sink the budget there.
