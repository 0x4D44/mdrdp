# SPIKE — what quench can *encode*, by codec × chroma × depth, and through which API

2026-08-19 · quench = Intel Core Ultra 7 270K Plus (Xe-LPG iGPU, device 0x7D67), Intel
driver 32.0.101.8331, Windows 11 25H2 build 26200.9168 · `tools/mf-caps-probe`
Companion to `2026.08.19 - SPIKE - VideoToolbox chroma and codec decode matrix on M5 Max.md`
(the client half). Raw output: `wrk_docs/evidence/2026.08.19 - mf-caps-probe - quench.txt`
(SSH, session 0) and `… - quench (interactive session).txt` (console session, the one with
hardware results).

## Headline

**Through Media Foundation, quench's hardware encodes 4:2:0 only — and it lies about it.**
Intel's HEVC MFT accepts every 4:2:2/4:4:4 profile value (`Main_444_8`, `Main_444_10`, …),
offers ARGB32 input, takes the frames, and emits a bitstream whose SPS says
`general_profile_idc=1, chroma_format_idc=1` — Main, 4:2:0, 8-bit. Intel's H.264 MFT does
the same (`profile_idc=100`, 4:2:0). The only genuine 4:4:4 bitstream on the box comes from
the *software* `HEVCVideoExtensionEncoder` (`profile_idc=4, chroma_format_idc=3`), 1080p only.

**But the silicon can do it, via a different API.** D3D12 Video Encode
(`ID3D12VideoDevice3::CheckFeatureSupport`) reports `HEVC_MAIN_444` and `HEVC_MAIN10_444`
as supported profiles with AYUV/Y410 input formats, and a 16384×16384 HEVC ceiling. That
is a driver capability statement, not yet an encoded bitstream — the one thing this spike
did not manage is to drive the D3D12 path to completion (details below).

Two further facts, each confirmed by two independent APIs:
- **HEVC encodes 5K, H.264 does not.** Intel's H.264 MFT refuses 5120×2880
  (`0xC00D36B4`); D3D12 says H.264 max 4096×4096, HEVC max 16384×16384. Intel's HEVC MFT
  encoded 5K 4:2:0 at 8 and 10-bit, 12/12 frames. So the "AVC server dies past 4096×2304"
  lesson is the *encoder's* limit, and the fix for native 5K on the host side is HEVC.
- **No AV1 encoder MFT is registered on quench**, though D3D12 reports AV1 Main/High as
  supported codec profiles (and then contradicts itself on the full support query — see
  caveats). Treat AV1 encode on this part as reported-but-unproven.

## Method

`tools/mf-caps-probe` (Rust, `windows` 0.62, cross-built from the Mac with the rhydra xwin
recipe) runs six escalating sections:
1. host identity; 2. `MFTEnumEx` inventory per output subtype, hardware-only and all;
3. `SetOutputType` acceptance per (encoder, profile, 1080p/5K), then the input types the
encoder offers back; 4. real 12-frame encodes with the chroma **parsed from the output
bitstream** (H.264/HEVC SPS after emulation-prevention stripping, VP9 uncompressed header);
5. a summary matrix; 6. D3D12 Video Encode `CheckFeatureSupport` — codec, profile/level,
input format, output resolution, and full-support queries.

The gap between "accepted" and "bitstream says" is the finding; only the bitstream column
is evidence. I hand-decoded the SPS bytes from the hex dumps for the Intel `Main_444_8`
(`0x21` → profile_idc 1) and the software 4:4:4 (`0x04` → profile_idc 4) cases to check the
parser; they agree.

**Session matters.** Over SSH (session 0) the Intel MFTs enumerate and then every
`ActivateObject` fails `E_FAIL`; the console session (via `schtasks /it`) activates them.
Sections 1–5 therefore come from the interactive run. Section 6 (D3D12 capability queries)
is byte-identical in both sessions — it can be collected over plain SSH.

figure to quote): Intel H.264 1080p ≈ 6/16; Intel HEVC 1080p ≈ 10/40, **5K ≈ 45/111**

one that matters for rhydra at native resolution and deserves a warm, per-frame
measurement in the real pipeline before anyone designs around it.

## Results — D3D12 Video Encode capabilities (identical in both sessions)

| Query | H.264 | HEVC | AV1 |
|---|---|---|---|
| Codec supported | yes | yes | yes |
| Profiles supported | Main, High (not High10) | Main, Main10, **Main_444, Main10_444** (not 12-bit, not 4:2:2) | Main, High (not Professional) |
| Input formats (any supported profile) | NV12 | NV12, P010, **AYUV, Y410** | NV12, P010 |
| Resolution | 16×16 … **4096×4096** | 64×64 … **16384×16384** | 64×64 … 4096×4096 |
| Full support @1080p (High+NV12 / Main+NV12) | **GENERAL_SUPPORT_OK** | inconclusive — `CODEC_CONFIGURATION_NOT_SUPPORTED` for the configuration supplied, under both the v0 and `_HEVC1` config structs | `CODEC_NOT_SUPPORTED` (contradicts the codec/profile queries) |
| Full support @5K | `RESOLUTION_NOT_SUPPORTED_IN_LIST` | inconclusive, as above | `CODEC_NOT_SUPPORTED` |

Note the input-format query answers per *profile* but returns the same set for `HEVC_MAIN`
as for `HEVC_MAIN_444` — so it shows the engine accepts 4:4:4 surfaces, not that a 4:2:0
profile keeps the chroma. The profile/level query saying `MAIN_444` *is supported* is the
statement that matters; the Intel MFT's clamping is then an MFT-layer limitation, not a
silicon one.

## What this changes

1. **The host is the 4:4:4 constraint, and the API is the lever.** The Mac decodes HEVC
   4:4:4 in hardware at 5K; quench's hardware reports it can encode HEVC 4:4:4 at 5K — but
   not through the Media Foundation MFT rhydra uses today. Reaching it means either
   **D3D12 Video Encode directly** (vendor-neutral, also the only AV1 route on this box,
   but a real subsystem: DPB management, rate control, bitstream headers are the caller's
   job) or **Intel VPL** (vendor-specific, higher level). That is an HLD-sized decision,
   not a tweak.
2. **HEVC 4:2:0 at 5K via the existing MFT works today** and is the cheap, proven step:
   same `Encoder` trait, different subtype GUID and profile, Annex B NAL framing
   generalised. It lifts the 4096×2304 ceiling on the host side; the client already
   decodes it. If the 4:2:0-at-HiDPI A/B passes, this is the whole job.
3. **AV1 on quench is not a product path yet.** No MFT; D3D12 reports the codec then
   refuses the full-support query; max 4096×4096 anyway. Park it for this host.
4. **VP9 is a dead end on both ends.** Intel's VP9 MFT ignores the profile attribute
   entirely (identical bytes for every value) and the Mac has no VideoToolbox VP9 decoder.
5. **Never trust `SetOutputType`.** Intel's MFTs accept profiles they do not honour. Any
   future encoder negotiation in rhydra must read the SPS/sequence header of the first
   frame back and assert the chroma it asked for — `mf-caps-probe`'s parsers are the
   start of that check.
6. **Session 0 is a trap for Media Foundation hardware MFTs** (enumerate yes, activate
   no) but not for D3D12 capability queries. The rhydra agent's interactive-task model is
   already the right shape.

## Caveats and gaps

- The D3D12 4:4:4 claim is a capability report, not a decoded bitstream. Closing it
  needs either the D3D12 full-support query with a codec configuration this driver accepts
  (it rejected ours under both struct revisions, and the `CODEC_CONFIGURATION_SUPPORT`
  query itself returns `IsSupported=false` / `E_INVALIDARG` for HEVC) or an actual D3D12
  encode. The Microsoft HEVC DX12 MFT probably needs a D3D12 device manager, which the
  probe does not build.
- AV1's three-way contradiction (codec yes, profiles yes, full support `CODEC_NOT_SUPPORTED`)
  is unresolved; it may be the same configuration-rejection class as HEVC.
- Five Intel rows (H.264 `422`, HEVC `422_10/12`, `444_10/12`) were fed the Intel-private
  NV12-tagged input GUID `{3231564E-3961-42AE-BA67-FF47CCC13EED}` because no named 4:2:2/
  10-bit-4:4:4 input was offered; they prove the profile is clamped, not what that input is.
  The `Main_444_8` row used real ARGB32 and is the clean clamp evidence.
- Latencies are cold, n=12, synthetic content, one run. The software H.264 encoder
  "beating" Quick Sync at 1080p is start-up cost, not throughput.
- One box, one driver. The probe is cheap; run it on the next host rather than extrapolate.
