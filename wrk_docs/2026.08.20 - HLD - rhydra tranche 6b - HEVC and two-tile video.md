# HLD — rhydra tranche 6b: HEVC, and two-tile video

Decision record: `wrk_docs/2026.08.20 - DEC - rhydra codec choice - HEVC 4-2-0, two
tiles at 5K.md` (measurements). Gating question closed by
`wrk_docs/2026.08.20 - SPIKE - does HEVC 4-2-0 damage text at 5K.md`.
Parent: `wrk_docs/2026.08.18 - HLD - native product shape and session ownership.md`.

## 1. What this delivers

rhydra encodes **HEVC Main, 4:2:0, 8-bit**. A full repaint at 5K goes as **two
2560×2880 tiles** encoded concurrently on quench's two media engines; everything
smaller stays a single stream; dirty rects remain the main path and are
untouched.

Measured basis, all on quench/M5 Max and re-runnable: two tiles **8.0 ms p50**
against **12.9 ms** for one 5K stream, decoded on the Mac in the same ~2.6 ms a
single 5K frame costs. H.264 cannot encode 5K on this hardware at all.

**4:4:4 is rejected, not deferred.** The spike closed it: 4:2:0 leaves luma
bit-exact, so it can only change the colour of text and never its shape; on a
real Windows 5K capture the subsampling costs ΔE p95 0.48, *below* the 0.52
RGB↔YUV rounding floor the pipeline already pays — while 4:4:4 costs 39% more
bytes and measured fractionally worse.

## 2. The wire

**A new message type, not a changed payload.** `framing.rs` already states this
principle and follows it: `MSG_VIDEO_SEQ` exists as its own type rather than a
new `MSG_VIDEO` body so that "a reader that predates it skips it via the length
prefix instead of misparsing eight bytes of sequence number as the start of an
access unit". Tiles get the same treatment.

```
MSG_VIDEO_TILE = 5            host -> client
  u64 LE  capture_seq         the frame this tile belongs to
  u8      tile_index          0-based
  u8      tile_count          how many tiles compose this frame
  u16 LE  x, y, w, h          where the tile lands in the frame
  [Annex-B access unit]       HEVC, this tile's own stream
```

**Why geometry travels with every tile** rather than being derived from
`tile_index`/`tile_count`: the client would otherwise have to reimplement the
host's tiling rule, and the two would drift the first time the rule changes. It
also means a later non-uniform split — tiles aligned to dirty regions, say —
needs no wire change. Eighteen bytes against a payload of tens to hundreds of
kilobytes. This is the same call made for audio's self-describing frames, and
for the same reason.

**Codec is announced in the stats header, not inferred.** The client must know
before the first access unit arrives, because it has to build the right decoder.

## 3. The compatibility rule, which is the one that bites

An old client meeting `MSG_VIDEO_TILE` skips it safely — that is what the length
prefix is for. **It then shows a black screen and reports no error.**

That is the exact failure this repo has now paid for twice: silence that looks
like a working connection. So:

> **If the header announces a codec the client cannot decode, the connect
> FAILS, with a message naming the codec.** It does not connect and paint
> nothing.

The `--doctor` ladder gains nothing here; this belongs at connect, where the
user is looking.

## 4. Composition

- The client keeps one decoder **per tile index**. The tiles are independent
  streams with their own VPS/SPS/PPS and their own reference chains, so they
  cannot share a decoder session however identical their geometry.
- Tiles decode into the surface as they arrive; **the frame is presented only
  when every tile of that `capture_seq` has landed.** Presenting progressively
  would show a seam down the middle of a repaint.
- **An incomplete tile set is dropped whole**, counted, and never presented. A
  half-updated surface is worse than a late one, and a counter is what tells us
  it is happening.
- The Mac decodes serially — one hardware decode engine, and async submission
  changes nothing — so tile decode is ~1.4 ms each, ~2.6 ms for the pair. That
  is measured, not assumed.

**Deferred with its evidence:** progressive present. The first tile's pixels are
ready at ~1.4 ms, so a renderer *could* show the top half early. Not in v1 — it
trades a visible seam for latency nobody has asked for yet.

## 5. When to tile

| Frame | Path |
|---|---|
| Dirty rects | `MSG_RECTS`, unchanged — **this is the main path** |
| Full repaint, width ≤ 2560 | single stream, `MSG_VIDEO_SEQ` |
| Full repaint, width > 2560 | two tiles, `MSG_VIDEO_TILE` |

Tiling below 2560 wide buys nothing: a single 2560×1440 encode is already 3.7 ms
and 1080p is 2.2 ms. Four tiles were measured and buy nothing over two — two
hardware queues serve four instances pairwise. The threshold is
measurement-derived and belongs in one named constant, not scattered.

## 6. Host encoder

The `Encoder` trait, the async `IMFMediaEventGenerator` contract, the
low-latency/CBR/B=0 settings and the Annex-B framing all carry over. HEVC
differs in NAL header layout and adds a **VPS** alongside SPS/PPS.

Two encoder instances share one D3D11 device and device manager and are released
together. Texture input stays — it saves ~0.8 ms at 1080p over system-memory
samples, so the existing D3D11 route is right.

**Never trust `SetOutputType`.** Intel's MFTs accept `Main_444_8` and silently
emit `chroma_format_idc=1`. Any negotiation must parse the first keyframe's SPS
and assert the profile and chroma it asked for; `tools/mf-caps-probe`'s parsers
are the starting point. **A codec that lies about itself is worse than one that
refuses**, and this one lies.

**IDR policy: both tiles key on the same `capture_seq`, never staggered.** A
client must never hold one tile at a keyframe and the other mid-GOP after a
reset. Budget ~2× a P-frame for the keyframe.

## 7. Client decoder — more than a subtype swap

The current decoder is a `VTDecompressionSession` typed as
`ironrdp_egfx::decode::H264Decoder` (`src/native/session.rs:29,211`) — an
**RDP-specific trait with an H.264-shaped contract**, borrowed by the native
path. The DEC's "generalises the same way" understates this. Needed:

1. `kCMVideoCodecType_HEVC`, and an **hvcC** format description built from
   VPS/SPS/PPS rather than avcC from SPS/PPS.
2. rhydra's own `VideoDecoder` trait, so the native path stops depending on an
   RDP crate's H.264 abstraction.
3. The Annex-B → length-prefix repack generalised: VideoToolbox consumes 4-byte
   length prefixes for HEVC as it does for H.264, but the parameter-set handling
   differs.

**Ordering constraint:** this rewires `src/native/session.rs`, which
`task/20260820-TSK-HUM-fix-native-session-stats` also touches. That branch lands
first.

## 8. Acceptance criteria

Written as executable checks, and against this repo's rules: a real server for
protocol work, a number *and its conditions* for any latency claim, and a
distribution rather than one run.

- **AC1 — the bitstream is what we asked for.** The first keyframe's SPS parses
  as `general_profile_idc=1, chroma_format_idc=1` (Main, 4:2:0, 8-bit). Asserted
  in the product, not only in a probe, because Intel accepts profiles it does
  not honour.
- **AC2 — a 5K repaint arrives whole and correct.** Both tiles decode, compose
  seam-free, and the presented surface matches a reference capture. A seam at
  x=2560 is the specific failure to look for.
- **AC3 — an incomplete tile set is never presented.** Drop one tile
  deliberately; the client counts it and shows the previous frame, not half a
  new one.
- **AC4 — an old client fails loudly.** A client without HEVC meeting an HEVC
  header refuses the connect naming the codec, rather than painting nothing.
- **AC5 — the two-tile win is real in the product.** Frame-complete latency for
  a 5K repaint, n ≥ 30, min/p50/p95/max, release build, on quench, tiles vs
  single stream. The bench measured 8.0 vs 12.9 ms; this is the same measurement
  through the real pipeline, which is where the DEC says it has not yet been
  taken.
- **AC6 — bitrate, which the DEC does not state.** Bytes/second for a 5K repaint
  and for a typical desk-work minute. This is the number that decides whether
  audio and clipboard sharing the ssh tunnel is a real problem, and tranche 6's
  own priority claim is currently unmeasured against it.

## 9. What this does not do

- **No 4:4:4, and no D3D12 Video Encode.** Closed on evidence (§1).
- **No AV1.** No encoder MFT is registered on quench, and VideoToolbox has no
  4:4:4/4:2:2 AV1 decoder at all.
- **No H.264 as a second codec.** It cannot do 5K here, is slower everywhere
  from 1080p up, and wins only on tiny regions by ≤0.1 ms. A second code path is
  not worth that.
- **No progressive present.** §4.
- **mdrdp's RDP path is untouched** — it stays on AVC444 with the 4096×2304
  clamp. The codec freedom is rhydra's, where we own both ends.
