# One H.264 decode session per AVC444 view

**Status: REJECTED — do not implement. Kept as the record of why.**
Date: 2026-08-19
Bug: MDR-BUG-FLUX-00008 (residual), and the `oscillating SPS/PPS` guard it forced

**2026-08-20 addendum:** The rejection still applies to splitting AVC444's main and
auxiliary views. A distinct per-*surface* split has now landed for MDR-BUG-FLUX-00008.
The claim below that only one surface can be live was disproved by kiln's physical-display
transitions and by the channel-wide decoder reset's field regression. Each surface keeps
one decoder, and that decoder still handles both AVC444 views sequentially.

## Why this was rejected

The design's load-bearing premise — that the AVC444 main and auxiliary views are
independent H.264 sequences needing separate decode sessions — is not established, and it
contradicts an earlier decision in this repo that WAS established.

`vendor/ironrdp-egfx/src/client.rs`, the doc comment on `decode_avc444` itself:

> Both sub-streams go through the SAME decoder sequentially — the Windows encoder
> produces a jointly-encoded, single-decoder-compatible pair (FreeRDP decodes it the same
> way).

`wrk_docs/2026.08.16 - HLD - AVC444v2 decode.md`, decision log item 2:

> One decoder instance, both sub-streams sequentially — FreeRDP-proven against Windows. A
> probe refutation attempt used independently-encoded streams (which do corrupt) but that
> is not what Windows emits; live acceptance 2b is the guard. **Fallback if ever needed:
> stream-index parameter, two sessions.**

So this question was asked three days earlier, a refutation probe was run, one decoder was
chosen for what Windows actually emits, and "two sessions" was written down as the
fallback. That HLD carried external review. This document proposed exactly that fallback
without re-establishing its trigger.

**What settled it.** Arthur has eyeballed AVC444v2 output on 0.1.79 and later and it is
correct. That is the August HLD's own acceptance criterion ("live acceptance 2b is the
guard") being met, and it validates the single decoder **together with** the ABAB guard in
`h264::decode_yuv420` — which, when it fires, refuses the rebuild and keeps the working
session alive at a cost of one skipped frame. That explains the one guard firing on kiln
without needing this redesign: the views diverged once, the guard absorbed it, the picture
stayed correct.

The evidence assembled here for splitting was one guard firing (n=1) plus `-12909`
failures that MDR-BUG-FLUX-00008's own STILL OPEN section attributes to a different
mechanism — reference loss across suppress/resume — which afflicts a single-view session
equally and would be untouched by this change.

**What was salvaged.** Acceptance criterion 6 of this design was to delete the ABAB guard
as dead code. That would have been a regression: it converts one skipped frame into a
double rebuild per frame, i.e. the permanent-black failure 0.1.79 removed. The comment
that invited that reading ("Windows uses one SPS for both, so in practice this guard never
fires") was false and has been corrected in `src/h264.rs` to record the measured firing and
mark the guard load-bearing.

**If this is ever revisited**, the trigger to establish first is whether Windows emits
divergent SPS/PPS across the two views often enough to matter. That is measurable, not
arguable: capture payloads with `--capture-failures <dir>` from kiln and replay through
`examples/avcreplay.rs`. Note that avcreplay itself feeds both sub-streams through one
shared decoder, so it would need updating alongside any split or it stops mirroring
production.

The original design follows, unchanged, for the record.

## Goal

One line: give the AVC444 main and auxiliary views their own H.264 decode sessions, so
each decodes against its own reference frames instead of sharing one session with an
unrelated video.

## Why

AVC444 sends **two independent H.264 bitstreams** per surface update — a main view (luma
plus 4:2:0 chroma) and an auxiliary view (the chroma 4:2:0 discards, packed as a fake
luma frame). They are separate video sequences with their own parameter sets and their
own reference chains.

We decode both through a single `h264_decoder`. Every P-frame is therefore predicted
against whatever frame the *other* view decoded last. Two consequences, both observed:

- `vendor/ironrdp-egfx/src/client.rs` carries a guard, `"oscillating SPS/PPS (divergent
  AVC444 sub-streams); refusing to rebuild"`, whose entire purpose is to stop the shared
  session thrashing between the two views' parameter sets. It fired in a live kiln
  session on 2026-08-19.
- The same session reported `VideoToolbox decode callback failed (status -12909)` — the
  decoder rejecting frames it had no references for.

Fixing the ResetGraphics teardown (landed, 0.1.79) turned a permanent black desktop into
a recoverable burst. This removes the remaining structural cause.

## Non-goals

- **Not asynchronous or parallel decode.** This machine has ONE hardware decode engine
  (`avd0` in the device tree; two *encode* engines, `ave0`/`ave1`, confirm the numbering
  reflects real instances). Two sessions multiplex onto that one engine, so parallel
  submission buys pipelining crumbs, and going async means moving decode output off the
  stack — which `h264::decode_with_session` deliberately protects against today
  ("the callback writes through raw pointers into THIS stack frame"). Decided with
  Arthur: keep it synchronous.
- **Not per-surface decoders.** There is only ever one live surface — a surface's size is
  fixed at `CreateSurface`, so a resolution change *replaces* it (`+2 -1` on a healthy
  session, `+4 -3` after a maximize), and multi-monitor is out of scope per `CLAUDE.md`.
  A map keyed by surface would be machinery for a case that cannot arise.
- No performance claim. Client decode measures ~1.3 ms against a ~30 ms typing round trip
  that lives on the server; any speedup here is unmeasured and is not a justification.

## Approach

Replace the single decoder with a named pair, and route by **view**, never by wire slot:

```rust
pub struct Avc444Decoders {
    /// The main view: stream1 of an LC=0 or LC=1 update, and every AVC420 frame.
    pub main: Box<dyn H264Decoder>,
    /// The auxiliary (chroma) view: stream2 of LC=0, and **stream1 of LC=2**.
    pub aux: Box<dyn H264Decoder>,
}
```

The wire-slot distinction is the trap. Under LC=2 the chroma frame travels in `stream1`,
so routing on "stream1 → main" would feed the aux view's frames to the main decoder and
rebuild the exact defect this change removes. The existing `yuv_scratch.0` / `.1` split
already encodes the view distinction correctly, so decoder choice mirrors scratch choice:

| Update | stream1 decodes with | stream2 decodes with |
|---|---|---|
| LC=0 (luma + chroma) | `main` → `yuv_scratch.0` | `aux` → `yuv_scratch.1` |
| LC=1 (luma only) | `main` → `yuv_scratch.0` | — |
| LC=2 (chroma only) | **`aux`** → `yuv_scratch.1` | — |
| AVC420 | `main` | — |

**Lifecycle.** Reset both sessions when the surface they serve goes away — on
`DeleteSurface`, and on a `CreateSurface` that reuses a live id (the existing code already
clears `avc444_buffers` at both points for the same reason). That is the real stream
boundary; `ResetGraphics` is not, and resetting there was the bug fixed in 0.1.79.

**Remove the `oscillating SPS/PPS` guard.** Its stated cause — divergent sub-streams
sharing one session — cannot occur once the views are split. Leaving it would tell the
next reader the sub-streams still share a decoder.

## Acceptance criteria

1. An LC=2 update decodes with the **aux** session, not main — asserted directly, since
   this is the one routing mistake that recreates the bug.
2. LC=0 decodes stream1 with main and stream2 with aux.
3. The two sessions are independent: parameter sets delivered to one do not rebuild the
   other.
4. `DeleteSurface` and a `CreateSurface` reusing a live id both reset **both** sessions.
5. `ResetGraphics` resets **neither** (the 0.1.79 regression test still passes).
6. The `oscillating SPS/PPS` error string no longer exists anywhere in the tree.
7. `cargo test` green including `-p ironrdp-egfx`; `clippy --all-targets -D warnings`
   clean; `scripts/check-windows.sh` clean.
8. A live kiln session that renegotiates resolution shows no `-12909` attributable to
   sub-stream collision. (Kiln is the only host that can produce the trigger — every
   fleet test host is headless, MDR-BUG-FLUX-00015.)

## Decision log

- **Named pair, not `[Box; 2]` or two `Option`s.** Getting main/aux the wrong way round is
  precisely the defect; named fields make the mistake visible at every use site, and one
  `Option` around the pair makes "both or neither" a type invariant rather than a rule.
- **Route by view, not by wire slot.** LC=2 puts chroma in stream1; slot-based routing
  silently reintroduces the bug.
- **Reset on surface delete, not ResetGraphics.** Established by MDR-BUG-FLUX-00008;
  ResetGraphics resizes the output buffer only.
- **Reset both decoders rather than tracking which surface each served.** Safe because the
  client is single-surface; recorded here so that multi-monitor work knows to revisit it.
- **Delete the guard rather than keep it as a belt-and-braces.** A guard for an impossible
  cause is dead code and actively misleading. Risk accepted: a genuinely oscillating
  single-view stream would rebuild per frame instead of refusing — it would surface as a
  decode-error storm, which the reason tally now names with its OSStatus.
- **Synchronous decode retained.** One decode engine; async costs a memory-ownership
  rework for pipelining crumbs.
