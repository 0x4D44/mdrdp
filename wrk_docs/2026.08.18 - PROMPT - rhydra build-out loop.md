## Tranche 6b — HEVC: how it is sequenced, and why

**Why before tranche 7.** Tranche 7 is a decision gated on a measured tail.
Measuring the tail of a video pipeline that is about to be replaced is wasted
work, and would need redoing on HEVC anyway. HEVC is a certain win with the
measurements already taken; IddCx-direct is explicitly not foregone.

**The gating question comes first.** `DEC` §5 open question 1 — does 4:2:0
visibly damage text at 5K HiDPI? — decides whether D3D12 Video Encode (a large
subsystem: DPB management, rate control and bitstream headers become the
caller's job) is on the critical path. Answer it before building the MFT path,
not after. Spiked 2026-08-20 on this Mac with libx265, no host needed.

**The HLD is lead work, not a delegable chunk.** The decision record settles the
*codec*; it does not settle the *protocol*. Two tiles means two concurrent
streams, which needs a tile identifier on the wire, composition and ordering
rules, and a keyframe policy accounting for ~23 ms 5K IDRs. Those are
invariant-bearing decisions. After the HLD it splits into three chunks with
disjoint files: host encoder swap, client hvcC decoder, two-tile protocol.

**One correction to `DEC` §4.1, verified in the code.** "`src/h264.rs`'s decode
path generalises the same way" understates it. The client decoder is a
`VTDecompressionSession` typed as `ironrdp_egfx::decode::H264Decoder`
(`src/native/session.rs:29,211`) — an RDP-specific trait with an H.264-shaped
contract. The client side needs `kCMVideoCodecType_HEVC`, an **hvcC** format
description built from VPS/SPS/PPS rather than avcC, and rewiring off that
borrowed trait. Contained, but not a subtype swap.

**Ordering constraint:** the client HEVC decoder rewires
`src/native/session.rs`, which the native-stats fix
(`task/20260820-TSK-HUM-fix-native-session-stats`) also touches. Land that
branch first; do not run both in parallel.

**Gap worth filling in the DEC:** it quotes latency thoroughly and says nothing
about bitrate. That is the number deciding whether audio and clipboard sharing
the ssh tunnel is a real problem, and it is cheap to capture from the existing
probes.

## Per-tranche flow (the proven 2L light flow)

Worktree via `deltic start-task` → understand (read the parent HLD section +
prior journals) → author the tranche HLD in `wrk_docs` → 2–3 adversarial
reviewers (refutation standard; reclaim inline on API failure) → attempt the
external Codex review (journal if it cannot run; never block) → mark
SELF-APPROVED, commit, proceed → implement tests-first (every new test made
to fail once — restore mutations from a saved copy, never `git checkout`) →
fmt, clippy -D warnings, focused tests, `./scripts/check-windows.sh`, cross
builds where the server/driver changed → live validation on quench →
journal → integrate.

## Environment realities

- **Quench etiquette**: post a board claim before taking the box, release
  when done; one session per account — check `mdrdp --sessions` and the board
  before long runs; always disconnect gracefully; `query session` is the
  first diagnostic when the IDD display "vanishes" (an attached RDP session
  replaces the console display topology).
- **The Mac can lock.** Screen capture and window focus (glass runs, viewer
  A/Bs) stall on a locked Mac — `caffeinate -dis` for the run, and if the
  display is locked anyway, re-queue the GUI validation and advance a
  non-GUI tranche instead. Never count a stalled GUI check as failed.
- Commit completed work before starting any long validation. Background
  waits need an armed wake-up. Bound every long command with
  `deltic timeout`; run test suites with stdin closed.
- Credentials stay in the macOS keychain (service `mdrdp`); ssh to quench as
  `ano` (password = username, throwaway; SSH_ASKPASS pattern in the journals).

  origin/main; pick up the open tranche or start the next; never redo landed
  work.

  tranche 7's decision is landed (built or declined with evidence), the retro

  build-out. Leave remaining open items (auto-logon, §8 Q1) in that summary.
