# HLD — native low-latency transport: hybrid wire + IddCx direct consumption

Status: SELF-APPROVED (adversarial review + external cross-family review folded in;
human gate remains integration, which needs Arthur's explicit go)
Date: 2026-08-17
Author: Claude (Fable 5), from the P3 spike results agreed with Arthur

## 1. Decision being made

mdrdp gains a **native transport** alongside IronRDP: our own capture→encode→wire→decode
path against a Windows host we control, running over SSH. This is the recorded
architectural decision point — everything before today was a spike; this document commits
the direction and scopes the first build increments.

The RDP path remains. The native path is a **second transport behind the same mdrdp
client**, not a new client: same window, same input handling, same HUD. RDP stays the
fallback for hosts we don't control and for anything the native path doesn't do yet.

**Why.** The spike measured (probe glass, n=100, Notepad, IDD @ 240 Hz) p50 54.3 ms,
p95 70 ms, max 80.6 ms — parity with mdrdp+RDP at the median (54.8) with a much tighter
tail. The per-stage decomposition shows where the remaining time is and that ~13 ms of
it is ours to remove without touching the 31.7 ms input+render+net floor shared by every
remote-display architecture:

| stage (p50, stage-2 run) | ms |
|---|---|
| input + render + net (residual floor) | 31.7 |
| DWM present → DXGI duplication acquire | 7.5 |
| convert BGRA→NV12 | 0.2 |
| encode (Quick Sync H.264) | 5.3 (p95 15.3) |
| send | 0.1 |
| recv → decode in | ~0 |
| decode (VideoToolbox) | 5.9 |
| decode out → present | 5.4 |

(Caveat recorded by review: the 5.3 ms encode figure pairs stamps across the async
MFT's pipelining — see §5 "frame_seq" — so treat it as approximate until re-measured
with correct pairing.)

The increments attack the two largest removable stages: encode+decode (~11 ms,
avoidable for small updates) and the duplication acquire (7.5 ms, avoidable by consuming
the IDD swapchain directly).

## 2. Scope of this build

**In:**
- **Increment 0 (pre-req): mid-GOP join fix.** A viewer that connects to a running
  server must start decoding without a server restart.
- **Increment 0.5 (pre-req, one evening): dirty-rect telemetry.** Instrument today's
  duplication path and measure what dirty/move rects the virtual display actually
  reports under the typing stimulus, *before* building on them (§5a).
- **Increment 1: hybrid wire.** Small dirty regions ship as raw BGRA rects beside the
  H.264 stream; the viewer composites them immediately, skipping encode+decode.
- **Increment 2: IddCx direct swapchain consumption.** The driver hands committed
  frames (with their dirty-rect metadata) straight to the server through named shared
  textures, removing the Desktop Duplication layer and its 7.5 ms.
- Re-measurement after each increment with the same probe-glass instrument, a
  same-session control arm, and the kill/keep gate (§8).

**Out (explicitly):** integrating the transport into the mdrdp session binary (after
the gate passes; own design pass); clipboard, audio, reconnect/roaming; the
wezterm-mux pane overlay (parked — `scratchpad.md`); multi-monitor; mid-session
resolution renegotiation (the rig runs fixed 1920×1080; §6 handles mode change only as
pool invalidation); any non-Windows server. The session/desktop-ownership model is
sketched as direction (§7) but not built here.

## 3. Architecture (settled by the spike, restated)

```
quench (Windows)                                Mac
┌─────────────────────────────┐
│ mdrdp-idd (UMDF IddCx)      │
│   virtual display @240Hz    │
│      │ swapchain buffers    │
│      ▼                      │
│ spike-server (user mode)    │     SSH tunnel      ┌─────────────────┐
│   capture → convert →       │ ──────────────────► │ viewer (spike)  │
│   encode → framed TCP       │  video 9500         │ decode/composite│
│   input ◄────────────────── │ ◄────────────────── │ → present       │
│   SendInput                 │  input 9501         └─────────────────┘
└─────────────────────────────┘
```

- **SSH is the permanent substrate**: authentication, encryption, connection
  establishment, remote exec, and file deploy. The server binds loopback only —
  an unauthenticated screen feed never touches the LAN. This stays true in the
  product (`mdrdp <host> --native` opens the tunnel itself).
- **The IDD virtual display is the display provider.** 240 Hz removes the
  frame-alignment quantisation (worth a measured 7.3 ms p50 vs 60 Hz).
- **One framed TCP stream for video+stats, one for input.** The framing
  (`tools/latency-spike/server/src/framing.rs`) length-prefixes every message, so
  readers skip unknown types — that is the versioning mechanism for this phase, plus
  a `wire_version` field in the JSON header line the server already sends first
  (bumped to 2 by this build: AU messages gain a sequence prefix, §5).

## 4. Increment 0 — mid-GOP join fix

**Problem observed three times in the spike:** a viewer connecting to a running server
gets "no SPS/PPS seen yet" forever. Root causes: Quick Sync's MFT exposes no
out-of-band sequence header (`sequence_header_available:false`), so
`annexb::ensure_parameter_sets` has nothing to prepend; the connect-edge
`request_keyframe()` (`pipeline.rs` `capture_loop`) is not verified to produce an IDR;
and — found in review — the async MFT's event queue is pumped only from inside
`encode()`, so on a static screen the final AU can sit inside the MFT indefinitely.

**Fix (server-side, four parts):**
1. **Cache in-band parameter sets.** In the encode sink, when `parameter_sets()` is
   `None`, scan each outgoing AU with the existing `annexb` NAL walker; whenever
   SPS+PPS appear in-band, **update** the cached `ParameterSets` (every sighting, not
   first-sight-only), and **clear the cache whenever the encoder object is recreated**
   — a stale wrong-geometry SPS prepended to a new stream's IDR would poison it
   permanently. (Recreation doesn't happen in this build; the rule exists so
   Increment 2's mode-change path can't resurrect the bug.) `ensure_parameter_sets`
   then prepends the cached sets to keyframes exactly as with MFT-supplied sets.
2. **Verify the connect-edge IDR.** Keep `request_keyframe()` on the connect edge; if
   no keyframe AU is produced within 1 s of encoded frames after a connect, re-issue
   and log (`keyframe_wait_frames` in stats). Worst case remains the GOP boundary
   (~2 s of *encoded* frames), now decodable thanks to (1).
3. **Pump the encoder when idle.** On `Acquired::Timeout`, drain the MFT's pending
   output events so a finished AU is delivered even when no new frame arrives. This
   also closes the §5 ordering hazard's worst case (a stale AU wiping newer rect
   content and nothing arriving to repair it).
4. **Detect a departed viewer without waiting for a write** (external review). The
   sender holds its one client slot until a write fails and never reads — on a
   static desktop no write ever happens, so a closed viewer wedges `poll_accept`
   forever and the very acceptance test below would hang. The sender polls the
   client socket for EOF each loop tick (non-blocking read) and frees the slot.

**Acceptance:** with the server running and streaming, connect a fresh viewer twice in
succession; each decodes its first frame without a server restart — target < 500 ms,
hard ceiling 2.5 s. Unit tests cover the SPS/PPS cache (update-on-sighting and
clear-on-recreate cases, with two *different* parameter sets so staleness is
distinguishable) — portable, run on macOS.

## 5a. Increment 0.5 — dirty-rect telemetry (precondition for Increment 1)

Increment 1's entire projection rests on an unmeasured premise: that the virtual
display's duplication reports small, accurate dirty rects for typing-class updates.
Some drivers report full-frame dirty; if this one does, Increment 1 is dead before it
is written. `DXGI_OUTDUPL_FRAME_INFO` already lands in `Capture::acquire`
(`dxgi.rs`), so the first cut is nearly free:

- Log `AccumulatedFrames`, `TotalMetadataBufferSize`, and (via
  `GetFrameDirtyRects`/`GetFrameMoveRects`) rect count and total dirty bytes per
  frame into the stats JSONL.
- Run the standard typing stimulus (autoinput against Notepad on the IDD display) for
  ~100 keystrokes and read the distribution.

**Decision point:** the fast-path predicate constants (§5) and the gate's hit-rate
floor (§8) are set from this data. If the typing stimulus does not sit under the
predicate for the majority of detection frames, Increment 1 is redesigned (or
re-scoped to Increment 2's metadata, which comes from DWM, not the duplication layer)
before any wire code is written.

## 5. Increment 1 — hybrid wire (raw dirty rects beside H.264)

### The idea

For typing-class updates (a caret, a glyph, a menu highlight) the dirty region is a few
KB. Encoding it costs ~5 ms (p95 15.3) on the server and 5.9 ms on the Mac — ~11 ms
round-trip spent compressing something that would fit in a single TCP segment raw.
Ship small updates as raw pixels, immediately, and let H.264 remain the base layer for
everything else.

### Design: rects are an overlay, not a replacement

Every captured frame is **still converted, encoded, and sent as H.264**, exactly as
today. When the frame's dirty region is small, the server **additionally** sends the
raw rects *first*. The viewer paints rects into its canvas immediately; the AU for the
same frame arrives a few ms later and repaints the same content (idempotent).

This "always encode, sometimes also send rects" shape is deliberate:
- The **encoder's** reference chain never has gaps — no reference-frame surgery, no
  forced IDR on path switches. (The *wire* can still drop AUs under back-pressure —
  a pre-existing property, handled below.)
- The rect path's latency win comes from *not waiting* for encode: rects are read back
  and sent before the frame enters the converter.
- Cost: the encode still runs (it runs today anyway) and small updates are sent twice.
  A typing update is a few KB; the duplication is noise on this LAN.

### frame_seq — one ordering domain for both paths

Review found a real interleaving hazard: the async MFT pipelines, so the AU delivered
during capture-loop iteration N is routinely frame N−1's. Wire order is then
`rects(N), AU(N−1)` — and a viewer that lets any decoded AU repaint the canvas wipes
the newer rect content until AU(N) arrives (which, on a static screen, required §4's
idle pump). The same pipelining means today's per-stage stats pair iteration-N
capture stamps with an iteration-N−1 AU — a live mis-attribution bug.

Fix, one mechanism for all three problems: a **monotonic `u64 frame_seq`** assigned at
capture.
- It travels through the encoder with the submission, and the output AU is matched
  back to its submission **by the MF sample timestamp** (each submitted sample
  already carries a unique `time_hns`; a small map from timestamp to
  `{seq, present_qpc, acquire_qpc, convert stamps}` replaces blind FIFO pairing —
  external review's point that FIFO order is a no-reordering *assumption*, not a
  contract; a timestamp miss increments a visible counter). Every AU's stats record
  then carries *its own* frame's stamps.
- On the wire it rides a **new message type** `MSG_VIDEO_SEQ = 4`
  (`u64 frame_seq` + AU) rather than a repurposed `MSG_VIDEO` payload — a v1 peer
  skips the unknown type and fails closed instead of misparsing bytes as an AU
  (external review); `wire_version: 2` in the header records the dialect. `MSG_RECTS`
  carries the same field.
- The viewer decodes every AU (decoder state must advance) but paints by an
  **exactness invariant**, not a bare newest-rect comparison. The canvas tracks
  `exact_through` — the capture seq it provably holds *all* content up to. A
  decoded AU repaints the whole desktop, so it is accepted iff
  `au_seq > exact_through` (and sets it); a rect update paints **iff it is
  adjacent** (`seq == exact_through + 1`), because capture seqs are contiguous and
  a metadata-whole rect set is that frame's complete change — applying it extends
  exactness by one. A `stale` update (at or below exactness) is skipped as a
  visible record; a `gap` update (ahead of adjacency) is **held** — one slot,
  newest wins — and applied the moment the AU that closes the gap arrives. The
  hold matters: the encoder runs a frame behind capture, so after one predicate
  miss every later rect update arrives exactly one frame ahead of exactness,
  and pure skipping would kill the fast path until the desktop idles (targeted
  re-review's finding — invisible to the §8 glass probe, which types into an
  idle desktop). A held update expires `stale` when an AU jumps past it (e.g.
  the post-drop keyframe) and is dropped on a rebase it no longer fits; no
  timer is needed. (Implementation review
  killed the first cut — "AU paints iff newer than the newest rect seq" — with a
  live scenario: the async encoder delivers AU(M) *after* rects(M+1), so a
  big-change frame M that sent no rects had its only carrier suppressed, and
  under sustained typing no AU ever passed again.) Redundant AUs update decoder
  state invisibly and are recorded `suppressed`, distinct from `dropped`.
- It is stamped into both ends' JSONL records, giving `decompose.py` an exact join
  (replacing the fragile `au_bytes` arrival-order join) and enabling rect-path
  attribution, which is impossible without a correlation id.

### Server side

`dxgi::Capture::acquire` additionally fetches `GetFrameDirtyRects` and
`GetFrameMoveRects` (cheap metadata calls on the frame already held). Move rects
contribute their **DestinationRect** to the dirty set (the pixels are read from the
current frame, so destination readback carries the correct final content). The first
frame after `Acquired::Recreated` has no valid metadata and is forced down the
full-frame path. "Metadata unavailable" is an explicit state distinct from "nothing
changed" — an absent-metadata frame must never satisfy the predicate as
`rect_count = 0`.

Fast-path predicate, evaluated per frame (constants provisional until §5a data):
- metadata valid, and `rect_count ≤ 32`, and
- total dirty bytes (`Σ w·h·4`) ≤ **96 KB** (≈2.6 ms on this WiFi LAN at ~300 Mbit
  effective; typing updates are 1–10 KB). Constants live in one place and are
  reported in the stats header; they are tuning knobs, not promises.

When the predicate holds: `CopySubresourceRegion` each rect into a small staging
texture, `Map`, pack, and hand to the sender **before** the frame enters the
converter. v1 maps directly and instruments the cost (`rect_pack_us`): between
keystrokes the GPU is near-idle, so the map should cost microseconds — but the
staging map shares the immediate context with the encoder, so a queued-encode flush
can surface in the tail. If `rect_pack_us` p95 shows it, the fallback is a 2-deep
staging ring (`Map` frame N−1 with `DO_NOT_WAIT`), which trades ~4 ms of rect latency
for stall immunity — a measured decision, not a default, because 4 ms is nearly half
the increment's win.

Rect sends share the sender's depth-2 lossy queue, and the sender **drains queued
rect messages ahead of queued AUs**. What that cannot fix is an AU already in flight:
a keyframe (~200–500 KB) ahead of a rect adds up to ~13 ms of head-of-line wait at
this LAN's rate (external review). v1 accepts that bounded, occasional cost and
measures it (`rect_send_done_us` minus pack time shows the wait); a separate
flow-controlled rect channel is the follow-up if stats show it mattering. Rect drops
are **counted separately** (`dropped_rects`) so fast-path pressure is visible. After any *frame*
drop (`dropped_frames` increment), the server requests a keyframe — a wire-level AU
drop desyncs the decoder until the next IDR (up to a full GOP), and under the canvas
model a drifted AU corrupts the whole canvas, not one stale frame. (Review noted the
counter-risk: an IDR is the largest AU and the socket just proved it was behind. The
IDR is generated at the *next captured frame*, by which time a transient stall has
usually cleared; if stats show drop-IDR cascades, revisit.)

### Wire format

New message type on the existing video channel (`framing.rs`):

```
MSG_RECTS = 3
payload (all LE):
  u64 frame_seq
  u32 frame_width, u32 frame_height     # desktop size, as in the stats header
  u16 rect_count
  rect_count ×:
    u16 x, u16 y, u16 w, u16 h
    u8  encoding                        # 0 = raw BGRA8 top-down, tightly packed
    u32 pixel_bytes
    pixel_bytes bytes
```

v1 ships encoding 0 only; the byte exists so LZ4 (encoding 1) can slot in without a
format break — adding that dependency is a separate, flagged decision.

**Viewer-side validation is mandatory, not hygiene:** the blit target is a fixed-size
buffer and the parser walks length fields from the network. Before any blit:
`encoding` known, `pixel_bytes == w·h·4`, `x+w ≤ frame_width`, `y+h ≤ frame_height`,
declared sizes sum to the remaining payload, and `frame_width/height` match the
canvas (mismatch increments a visible counter — never a silent drop). A malformed
message is terminal for the connection, like a framing error.

### Viewer side

The viewer gains a **canvas**: a persistent RGBA framebuffer at the desktop size from
the stats header. (The decoder returns SPS-cropped 1920×1080 — verified against the
committed stage-2 client JSONL — so no 1088-row padding case exists on this stream;
the dimension check above still guards the assumption.)
- A decoded AU replaces the canvas iff its seq passes the ordering rule above.
- A `MSG_RECTS` message swizzles BGRA→RGBA and blits each rect into the canvas.
  Rects arriving before the first decoded keyframe are dropped (counted).
- The canvas lives on the network/decode thread; each mutation publishes an
  `Arc<Vec<u8>>` snapshot through the existing newest-wins `FrameSlot`
  (copy-on-write: `Arc::make_mut` at the next rect blit). Implementation review
  caught the first cut cloning 8.3 MB per decoded frame — a new per-frame cost the
  archived baselines never paid, which would have confounded every comparison the
  §8 gate makes. With the Arc model the AU path publishes with no copy (baseline-
  identical) and the rect path pays one copy per update at typing cadence, which
  is what this section originally sanctioned.
- The present path (`present.rs`) is unchanged in mechanism; dirty-region present is
  a later optimisation.
- Rect messages get their own stats records (`rect_recv/paint/present`, with
  `frame_seq`) mirroring frame records; `decompose.py` gains the rect join and a rule
  for choosing rect-vs-frame as the detection event.

### Expected effect

Typing-class p50 drops by roughly encode+decode minus readback+blit ≈ 9–10 ms:
~54 → ~45 ms probe-measured. Tail should tighten too — the rect path bypasses the
encoder's p95 15.3 ms contention spikes.

## 6. Increment 2 — IddCx direct swapchain consumption

### The idea

The 7.5 ms DWM-present→duplication-acquire gap is Desktop Duplication's internal
latency. The driver (`idd/driver/Driver.cpp`, `SwapChainProcessor::RunCore`)
*already* holds each committed buffer at `IddCxSwapChainReleaseAndAcquireBuffer` —
the earliest possible moment. Hand that buffer to the server directly and the 7.5 ms
collapses to a copy plus a signal.

### Design (reshaped by review — named shared resources, no handle duplication)

- **Driver-side pool:** the driver creates a pool of 3 shared textures on its render
  device, each shared via `IDXGIResource1::CreateSharedHandle` with a **name** and an
  explicit security descriptor granting the interactive user access, plus named
  per-slot events and one named shared-memory section (`CreateFileMappingW`, same
  SD). Naming discipline (external review): the **section** name alone is
  well-known (`Global\mdrdp-idd`), created **once** at driver start and held open
  across swapchain assignments — and creation fails loudly on
  `ERROR_ALREADY_EXISTS`, which is squatting detection. Texture and event names are
  **generation-qualified with a random suffix**, published through the section
  header — fixed names would collide with a straggling server's open handles on
  pool rebuild (`DXGI_ERROR_NAME_ALREADY_EXISTS`) and invite pre-creation
  squatting. The server opens everything **by name**
  (`OpenSharedResourceByName`, `OpenFileMapping`, `OpenEvent`) — no IOCTL, no device
  interface, no cross-process `DuplicateHandle`. (UMDF2 exposes only a requestor
  PID, not a process object; the driver also currently wires no
  `EvtIddCxDeviceIoControl` and registers no device interface — the named-object
  route avoids building all three. If WUDFHost's token turns out unable to create
  `Global\` named objects with the needed DACL, that is the first smoke test, and
  the fallback is exactly that IOCTL plumbing, costed by review at: interface
  registration + IddCx IoControl callback + INF SDDL.)
- **The section is the contract:** a header `{layout_version, generation,
  render_adapter_luid, width, height, format, slot_count}` plus per-slot
  seqlock-written records `{sequence, frame_seq, present_qpc, dirty_rect_count,
  dirty_rects[], move_rects[]}`. **Dirty/move metadata from
  `IDARG_OUT_RELEASEANDACQUIREBUFFER` rides here** — Increment 1's fast path must
  survive the source swap (review caught the original draft deleting it; the agreed
  plan always said "dirty rects included"). Metadata-absent is representable and
  distinct from zero rects.
- **Per frame:** driver copies the acquired swapchain buffer into the next slot
  (keyed mutex, `AcquireSync(key, 0)` — **newest-wins, never blocking**: a blocked
  swapchain thread back-pressures DWM, reintroducing the latency this increment
  removes), orders the copy with a fence/event query **before** releasing the source
  buffer back to the swapchain — the keyed mutex protects the destination, nothing
  protects the source; an unordered copy lets DWM composite into a surface mid-read.
  That ordering puts real, small work on the present path: it is measured
  (driver-side stamp deltas), not asserted free.
- **Server:** capture goes behind a `FrameSource` trait — the existing duplication
  as one impl, the shared-pool consumer as the other, selected by
  `--source idd|dxgi` (default `dxgi` until the IDD source is proven). The consumer
  builds its D3D device on the **section's `render_adapter_luid`** via
  `EnumAdapterByLuid` (quench has one adapter today; hybrid/WARP is when this
  matters), waits on slot events, acquires the keyed mutex — treating
  `WAIT_ABANDONED` (a *SUCCEEDED* HRESULT that `FAILED()` checks wave through) as
  slot-poisoned/reacquire — and feeds the same convert→encode pipeline.
  `present_qpc` comes from the slot record, so the decomposition keeps working.
- **Invalidation:** `generation` bumps on every swapchain Unassign/Assign (the pool
  and device are per-assignment), on mode change, and on driver redeploy; the server
  detects a bump (or abandoned/vanished named objects, e.g. mid-`pnputil` redeploy)
  and reopens from scratch — same shape as today's `Recreated` handling. A dead
  server holding a keyed mutex is the abandonment case above; the driver's
  non-blocking acquire means it never waits on one.

### Risk and fallback

Still the riskiest increment — driver↔user-mode shared-resource plumbing, tested only
on quench, a driver redeploy per iteration (proven reboot-free). The fallback is
explicit and permanent: `--source dxgi` keeps Desktop Duplication and the 7.5 ms;
gate numbers are then presented with that stated.

### Expected effect

~7 ms p50: ~45 → ~38 ms probe-measured. The probe reads high by a one-sided
capture-interval bias whose band the instrument reports per run
(`observed_median_gap_us`, +8.3/+16.7 ms at the observed 60 Hz gap — a Mac-side
capture ceiling, measured invariant across 60 and 240 Hz sources); by that band the
true glass-to-glass lands roughly 30–32 ms, quoted as a band, not a point.

### Increment 2 measured verdict (2026-08-18)

Same-day, same-session A/B, one binary (`--source idd` vs `--source dxgi`),
n=100/arm, 0 timeouts, glass region on the caret cell, quench DISPLAY6 (IDD @
240 Hz), Mac capture @ 120 fps. Artifacts: `baseline/inc2-glass-{idd,dxgi}.jsonl`,
`baseline/inc2-typing-{idd,dxgi}-{client,server}.jsonl`.

| arm | p50 | p50 95% CI | p95 | mean | rect-path detections |
|---|---|---|---|---|---|
| `--source idd` | 75.4 ms | [75.0, 82.2] | 192.5 | 94.2 | **0/98** |
| `--source dxgi` | 74.0 ms | [67.1, 75.0] | 91.5 | 75.8 | 99/100 |

The ~7.5 ms capture saving is **real and visible** (present→acquire ≈0 vs 7.9 ms)
but end-to-end the arms are at p50 parity, because the IDD arm loses the rect
fast path entirely and pays the ~23 ms codec chain on every detection: **IddCx
per-present dirty metadata is buffer-relative** — DWM reports damage since *that
swapchain buffer* last presented, so at paced-keystroke cadence the claimed dirty
is ~a full frame (measured p50 7.25 MB vs DXGI's desktop-relative 25 KB; 68/244
records claim more than one full screen once the slot-ring unions compound it).
The IDD arm also carries a fat residual tail (p95 192 ms, upstream of capture)
the DXGI arm lacks; unexplained, recorded.

Verdict: decision 7's default stands — `--source dxgi` ships as the default and
the IDD source stays behind the flag as built, correct, and measured. The road
to the §8 number is **pixel-diff rect extraction** (previous-frame compare on
predicate-miss frames), which the isolated-keystroke regime demands from *both*
sources — DXGI's DWM cold-recompose (7.2 MB claimed / 2.5 KB encoded) and IddCx's
buffer-relative metadata are the same disease with different vectors. The IDD
source's texture plumbing is where that diff naturally lives.

## 6b. Increment 3 — trusted rects by pixel diff (designed 2026-08-18, not yet built)

Both sources miss the fast path in the isolated-keystroke regime for the same
underlying reason: **their metadata describes something other than the true
per-frame delta** (DXGI: DWM's post-idle full recompose, 7.2 MB claimed / 2.5 KB
encoded; IddCx: buffer-relative damage, p50 7.25 MB claimed for a caret cell).
The frame the user is waiting for is exactly the frame that misses. Stop
trusting metadata there; verify by diffing pixels.

- **Previous-frame retention:** the pipeline keeps one `prev` texture on the
  source's device and `CopyResource`s each consumed frame into it after
  processing — GPU-to-GPU, ~0.2–0.5 ms, no CPU, unconditional (simplicity over
  a conditional copy that saves sub-millisecond GPU).
- **The idle-regime gate:** the diff runs only when (a) the metadata missed the
  predicate (absent, overflow, or over-size) AND (b) the gap since the previous
  consumed frame is ≥ ~100 ms. Isolated keystrokes always satisfy (b); video
  and burst typing never do, so continuous content pays the diff cost zero
  times. The threshold is a stats-reported knob, telemetry-tuned like the
  predicate's (decision 8).
- **The diff:** copy the claimed-dirty region (full frame when absent) of both
  `current` and `prev` to staging, map both, SIMD-compare in 64×16-pixel tiles,
  and coalesce changed tiles into rects. Cost ~5–8 ms for a full-frame compare —
  against the ~23 ms codec chain it avoids when the true change is small. The
  current frame's pixels are already mapped when the diff hits, so the rect
  payload packs straight from that map — no second readback.
- **Trust and the exactness chain:** a diff-produced rect set is the *measured*
  complete delta between two consecutive consumed frames — stronger than any
  metadata claim — so it feeds `emit_rects` under the same predicate and the
  same `frame_seq`, and the viewer's invariant needs no change at all.
- **A scene-cut frame in the idle regime** (rare: window switch after a pause)
  costs the diff and then falls back to the full path — ~8 ms added to a frame
  that already pays 23 ms of codec; accepted, counted in stats
  (`diff_runs`/`diff_hits`/`diff_ms`).
- **Placement:** source-agnostic, between acquire and the fast-path decision in
  `pipeline.rs` (a `diff.rs` beside it); works identically over both
  `FrameSource` impls.

Expected effect, from today's numbers: a diff hit turns a ~74 ms detection into
~74 − 23 (codec skipped) + ~7 (diff) + rect-path client delta ≈ **high 50s p50**
in the measured regime, with the min already demonstrating ~35 ms when nothing
queues. The §8 item-3 number then rests on this plus present-path work, not on
the capture source.

## 6c. Increment 4 — damage-aware client present (designed 2026-08-18)

The Increment 1 decomposition priced the rect path's client tail at ~10 ms
(paint→present 11.3 vs the AU path's 5.4), and the client-ordering pilot split
it: one in-flight present ahead (~5 ms) plus the present's own cost (~5 ms).
Reading softbuffer 0.4.8's macOS backend (`src/backends/cg.rs`) explains where
that cost is unavoidable *through softbuffer*:

- `buffer_mut()` allocates a **fresh zeroed `vec![0; w*h]` on every present**;
  nothing is retained, and `age()` is hardcoded 0.
- `present()` boxes that buffer into a new `CGDataProvider`/`CGImage` and sets
  it as the CALayer contents inside a `CATransaction` — the full 8.3 MB churns
  through allocator, converter and compositor upload per present.
- `present_with_damage()` **ignores its damage argument** and calls `present()`.

So partial presenting through softbuffer is impossible by construction, and
every present pays a full-canvas `present_into` convert into cold memory.

**Phase 1 (this increment): persistent canvas + damage-only convert.** Keep the
converted `Vec<u32>` canvas in the window thread, maintained incrementally:

- **Damage rides the frame slot.** `Frame` gains a `damage` value — `Full` for
  AU paints (H.264 says nothing about what changed), the rect list for rect
  paints. **Union across displacement**: when a publish displaces a frame the
  window thread never took, the damages merge (Full absorbs everything; rect
  lists concatenate, collapsing to Full past a small cap). Without the union, a
  displaced frame's pixels would be painted into the canvas by nobody and the
  next partial present would ship a stale region — the same accumulator
  invariant the server's 3-slot pool needed (§6, decision 18).
- **Region convert.** A 1:1-only region variant of the present pass converts
  just the damaged rects into the persistent canvas; `Full` (and any resize,
  scale change, or unpresentable-geometry fallback) rebuilds the whole canvas
  and revalidates it.
- **Present = memcpy.** softbuffer's fresh buffer is filled by
  `copy_from_slice` from the canvas (~0.8 ms sequential copy, against 3–4 ms of
  convert into cold pages), then `present_with_damage(rects)` — a no-op today,
  correct the day the backend honours it. An expose/redraw with no fresh frame
  becomes pure memcpy, no convert at all.

Expected effect: replaces the full convert with damage-only convert + one
memcpy on every rect present — ~2–4 ms off rect paint→present, and it shrinks
the in-flight-present queueing term by the same amount since presents get
cheaper. Client stats gain `partial: true` on painted records so the A/B can
verify the partial path actually carried the run.

**Phase 2 (designed, deferred pending phase 1 numbers): bypass softbuffer on
macOS.** A direct CALayer presenter with two persistent buffers presented
alternately (buffer-age-2 semantics: partial updates apply the union of the
last two damages), or IOSurface-backed contents to eliminate the CPU→compositor
copy entirely. Kills the remaining per-present allocation + CGImage churn +
full upload. Costs either direct `objc2-quartz-core`/`objc2-core-graphics`
dependencies (already compiled transitively via softbuffer, same versions) or
an IOSurface crate (genuinely new). Build only if phase 1's measured floor
still holds the §8 gate hostage.

## 10. Risks

- **Increment 2 driver plumbing** remains the long pole; first smoke test is
  `Global\` named-object creation with a custom DACL from the UMDF host, with the
  IOCTL route as the costed fallback. Mitigated by `--source dxgi` and the proven

- **Dirty-rect fidelity** is now a measured precondition (§5a), not a hope; if the
  virtual display over-reports, Increment 1 is redesigned before it is built.
- **The copy-and-fence on the DWM present path** (Increment 2) has a real, unmeasured

- **Encoder contention tail** (p95 15.3 ms encode) is *not* addressed for large

1. **Critical:** the `au_seq > last_rect_seq` blit rule suppressed the only

2. **Major:** publish cloned 8.3 MB per decoded frame, a cost the archived

3. **Major:** the §5 "first frame after `Recreated` takes the full-frame path"
   guard was specified but unimplemented → `suppress_rects_once` in the capture
   loop (decision 15).
4. Minor, all fixed: server schema bumped to 3; `dropped_rects` carried on every
   frame row so a total rect blackout is still visible; the u16 `debug_assert`
   moved out of the Map/Unmap window; zero-rect updates skipped (`empty`) rather
   than advancing exactness; `decompose.py` prints `n` per stage row (the rect
   table's server-derived stages can legitimately have smaller n).
5. **Targeted re-review of the fixes** confirmed 1-4 and caught one new major
   introduced by the strict-adjacency gate: after a single predicate miss, every
   later rect update arrives one frame ahead of exactness (encoder lag), so the
   fast path silently collapsed to zero hit rate until the desktop idled — and
   the §8 probe, typing into an idle desktop, would have reported a healthy
   rate. Resolved by the one-slot gap hold (decision 16); the recovery scenario
   is a mutation-proven regression test
   (`a_held_rects_update_applies_once_the_au_closes_the_gap`).
6. Noted, unchanged: an AU snapshot displaced by a newer rect paint records
   `dropped: true` — literally accurate, but at rect cadence the AU drop rate
   partly reflects fast-path displacement rather than pipeline pressure; readers
   should treat viewer `dropped` accordingly (the `suppressed` flag separates the
   ordering-rule case only).
