# SPIKE — P1 protocol posture against `temper`

2026-08-14 · Part 1 of the Gauntlet build charter · **partial — see "Still unknown"**

The charter makes P1 the first substantive part because the protocol posture of the real
target de-risks every architectural choice after it. This is the half that needs no
credentials, plus the baseline the latency requirement is measured against.

## Test host

| | |
|---|---|
| Name | `temper` → `temper.lan.example` → `192.0.2.171` |
| Port | 3389 open and accepting |
| ICMP | Blocked (Windows Firewall default). **Do not use ping to test reachability** — use a TCP connect to 3389 |
| Link | LAN / WiFi 6 |

## Confirmed findings

**1. NLA is mandatory. There is no unauthenticated path to a first pixel.**

The X.224 negotiation that opens every RDP connection happens *before* authentication, so
it can be probed with no credentials at all. Offering the full modern set
(`requestedProtocols = 0x0000000B` — TLS | HYBRID | HYBRID_EX), `temper` replies:

```
030000130ed00000123400022f080008000000
                          ^^ RDP_NEG_RSP
                                ^^^^^^^^ selectedProtocol = 0x00000008
```

→ **HYBRID_EX** — CredSSP with Early User Authorization.

Offering legacy RDP security (`requestedProtocols = 0x00000000`) is rejected outright:

```
030000130ed000001234000300080005000000
                          ^^ RDP_NEG_FAILURE
                                ^^^^^^^^ code 5 = HYBRID_REQUIRED_BY_SERVER
```

**Consequence for the plan — this is the load-bearing one.** CredSSP + NTLM/Kerberos is
not a later hardening phase; it is the gate on the *first working connection*. Any plan
that plots "get pixels on screen, add auth later" is invalid against this host, and
against any default-configured Windows 11 Pro. The credential path (keychain → CredSSP)
must be built in the same part as the first connection, not deferred.

HYBRID_EX additionally means the server sends an Early User Authorization Result PDU
straight after the CredSSP exchange. A hand-rolled connector would silently desync there.
**IronRDP handles it — Confirmed** by P1a against `ironrdp-connector` 0.10.0
(`src/credssp.rs:220`), superseding this doc's original unevidenced assertion.

**2. Latency floor — SUPERSEDED. See the correction below.**

~~TCP handshake RTT p50 = 4.20 ms~~ (10 samples: min 4.05, max 5.11). First connect from
cold measured 12.86 ms — ARP/DNS warm-up, not steady state.

**Corrected 2026-08-14 by P0a — still provisional: p50 = 3.48 ms**, 95% CI [3.46, 3.51] ms,
over 3000 samples from a release build (min 2.15, p95 4.74, p99 5.84). The original
ten-sample burst overstated the floor by roughly 19%.

It remains provisional because all 3000 samples fall inside a single 92-minute afternoon
sitting. Three short batches were run either side of two UTC hour boundaries, which ticked
three distinct hour *labels* without ever sampling a different time of day — satisfying
the letter of the coverage check while reproducing the exact defect it exists to catch.
A Gauntlet critic caught it; the check now requires a ≥6 h wall-clock span, and reports
this artifact as PROVISIONAL.

Even within that short window the variability is visible: hour-label p50 moved between
3.42 and 3.52 ms with barely-overlapping confidence intervals, and the last batch's tail
was markedly worse (p99 7.69 ms against 5.48 in the first). Genuine diurnal spread should
be expected to widen it further.

This is the number the whole latency requirement sits on top of. It also sets the scale for
what "low latency" can mean here: anything we measure in the tens of milliseconds is
dominated by our own pipeline, not the network — which is exactly the regime where the
reference client's degradation over time should be beatable.

## Still unknown — needs credentials

Codec and channel negotiation all happen *after* authentication, so none of it is
reachable from a credential-free probe:

- Whether EGFX comes up, and with which codecs (RemoteFX Progressive vs H.264 AVC420/444)
- Whether IronRDP's client-side H.264 path is needed at all at this bandwidth
- Bitmap cache capabilities offered
- Which virtual channels the host advertises

**Unblocking it without exposing a credential to any agent:** store it in the macOS
keychain and have the spike read it from there.

```
security add-generic-password -s mdrdp -a 'temper\<username>' -w
```

`-w` with no value prompts interactively and does not echo. The spike then reads it via
the `keyring` crate — which is the credential path the product needs anyway, so this
builds the real thing rather than a test-only shortcut.

## Method note

Findings 1 and 2 came from a throwaway Python probe (raw X.224 Connection Request /
Connection Confirm). It is deliberately **not** committed — the repo is all-Rust, and this
capability belongs in the P0 measurement harness in Rust rather than as a stray script.
The exact PDU bytes are recorded above so the result is reproducible without it.

**Follow-up:** port the negotiation probe and the RTT sampler into the P0 harness as its
first two measurements.

## Verdict

The credential-free half of P1 is **Confirmed**. The codec half is **UNVERIFIED** —
blocked on a credential, not on effort. Per the charter, UNVERIFIED is never PASS, so P1
does not close until the codec question is answered against this host.
