# Rhydra latest-state flow control

Status: SELF-APPROVED

## Outcome and scope

Keep window dragging and other interactive desktop changes current when the visual path falls behind. The server will admit only a small window of complete logical updates, stop capture before conversion or encode while that window is full, and resume from the newest IDD state once the client reports an update applied.

This builds on wire v9/layout-v2 metadata-first moves. It does not replace TCP/SSH, add arbitrary window-motion inference, acknowledge OS presentation, tune the window dynamically, or add compatibility/migration machinery.

## Approach

### Exact client progress

- Bump the strict native wire from 9 to 10 and add `MSG_FRAME_ACK = 10`. Its payload is exactly one little-endian `u64 frame_seq`.
- An acknowledgement means one complete logical update has been committed to the client's authoritative canvas. It is an exact update identity, not a cumulative whole-canvas watermark: sparse and video regions can complete out of order.
- Wire-v10 raw and regional-video payloads each carry the logical update's required-part mask (`RAW`, `VIDEO`, or both). A shared client rendezvous records validated completion of each part and emits one acknowledgement only when the mask is complete. Receiving inconsistent masks for one sequence is terminal.
- A validated part that is entirely suppressed by newer per-block state still completes. A malformed part or failed decode/copy does not complete and terminates the viewer instead of leaving a permit silently wedged.
- A move is already an explicit cross-lane transaction. Only the one-shot `MoveRendezvous::complete` transition acknowledges it, after the move and its declared none/raw/video remainder. A provisional move fence cannot acknowledge.
- Send acknowledgements back on the duplex video socket. A tiny client writer thread owns a cloned socket writer; the existing video thread remains the sole reader. The server sender remains the sole writer and a session-scoped reader owns a clone. This preserves the independent input path and avoids making the optional auxiliary channel load-bearing.
- The feedback protocol is strict and its reader accepts no payload larger than eight bytes. Malformed, unknown, duplicate, stale, or unreserved acknowledgements end that viewer session. Acknowledgement write/read failure also ends it, allowing normal reconnect and codec recovery.
- The client acknowledgement queue has capacity four, enough for the two server permits plus a write in progress. Completion enqueues with `try_send` only after releasing canvas, fence, and rendezvous locks. Queue-full or a one-second socket write timeout is terminal; visual reader threads never block behind feedback.

### Bounded server work

- Add a small `VisualFlow` state with a mutex and condition variable. It tracks the current viewer epoch and at most two exact reserved frame sequences. Two permits allow useful overlap without allowing an old visual tail to grow.
- Reserve a frame before its logical update becomes visible to any outbound queue or encoder. Represent the tentative reservation as an RAII token carried by pending encoded plans; dropping any rejected, expired, or suppressed plan cancels by construction. Successful queue admission disarms the token while leaving its exact sequence in `VisualFlow` for the acknowledgement. Cancel a post-acquire reservation only after arming full recovery and invalidating any pixel-diff/client baseline advanced by that capture. Sparse and move scheduling remains suppressed until the recovery update is acknowledged.
- Pump completed asynchronous encodes before consulting the flow window. When both permits are occupied, wait at most one millisecond on the condition variable and loop without acquiring a capture. Acknowledgement, cancellation, disconnect, and epoch changes notify immediately. The short timed slice is required because this capture thread also pumps asynchronous encoder completions.
- A five-second lack of progress fails only the current viewer epoch. It requests a sender-side socket shutdown, wakes the capture gate, clears the epoch's reservations, and returns the same server to accept rather than unwinding the process.
- Keep an accepted H.264 reference chain intact. Do not replace or discard an admitted encoded update for freshness. Move prelude, fence, and remainder remain one logical reservation and one acknowledgement.
- IDD remains the capture truth. Its existing newest-valid-slot selection and accumulated dirty coverage consolidate skipped presents after a wait. Client progress never replaces IDD's `last_consumed`, and it does not replace the server's `last_scheduled_seq` dependency tracking.
- Ordered IDD moves require exact adjacency. A post-wait acquisition can therefore fall back to accumulated final pixels and regional/full H.264; telemetry records that gap and whether a move or pixel path won. The three-slot pool cannot preserve an arbitrarily long skipped move chain, so composing historical moves is deliberately outside this change.
- Require the H.264 encoder's low-latency mode. A codec that may retain both permitted inputs without output cannot make progress under a two-update window and is rejected at startup. Timeout telemetry distinguishes not-yet-emitted work from emitted-but-unacknowledged work.

### Lifecycle and telemetry

- Each accepted video connection creates a new epoch, clears old reservations, and starts one feedback reader. Epoch comparison and reservation mutation occur under the same `VisualFlow` lock. Old-epoch events are ignored.
- The feedback reader is the sole inbound video-socket reader; remove `poll_client_eof`. The sender owns the reader handle. Dropping a viewer shuts down both directions, joins the reader, and retires the epoch before accepting a successor. Client shutdown closes and joins its acknowledgement writer; writer failure sets the shared stop state and shuts the video socket.
- Bump the server telemetry schema from 12 to 13. The header records the configured window. Runtime telemetry exposes current and observed-maximum outstanding work, cumulative acknowledgements, waits, wait time, captures avoided while full, post-wait frame gaps, move-vs-pixel outcomes, and oldest reservation age/state without producing a JSON row per acknowledgement.

## Acceptance criteria

1. Wire v10 frames and validates an exact 8-byte acknowledgement; malformed feedback is terminal.
2. The client acknowledges each successful logical canvas update exactly once and only after all declared parts complete. Applied and validated-suppressed parts complete; provisional moves, partial mixed/tiled updates, and failed updates do not.
3. The server reserves no more than two unacknowledged logical updates. Exact out-of-order acknowledgements free only their matching permits; duplicate, unknown, and old-epoch feedback cannot corrupt current state.
4. At a full window, the server continues pumping completed encodes but does not acquire, convert, diff, or submit another capture. The next IDD acquisition selects its newest valid state with accumulated coverage.
5. Freshness control never drops an admitted H.264 dependency or splits a move transaction. Any post-acquire rejection invalidates speculative baselines and holds sparse/move work behind an acknowledged recovery. Disconnect and timeout affect only the current viewer epoch.
6. Keyboard and mouse remain on their independent interactive connection; sparse pixels retain their dedicated connection.
7. Telemetry identifies the configured and observed window and exposes outstanding work, acknowledgement count, wait count, wait duration, avoided captures, post-wait frame gaps, move/pixel routing, and whether the oldest work is before or after emission.
8. Focused tests are observed failing before their fixes and then pass. Repository format, lint, client tests, portable server tests, Windows server build/tests, and IDD build checks pass as applicable.
9. After integration, repeated Quench 5120x2880/200% drag tests show at most two outstanding logical updates, no ordering/decoder errors, the exact final window position, and no stale replay tail after the pointer stops. Record acknowledgement round-trip distribution and the share of post-wait updates routed as moves versus pixels.

## Decision log

- Use client-applied feedback, not queue occupancy, because only the client knows when bytes have become usable canvas state.
- Use a two-update sliding window, not stop-and-wait, to retain encode/network/decode overlap.
- Acknowledge exact update IDs, not a cumulative maximum. Regional lanes may complete out of order and a maximum would falsely retire unseen work.
- Put the required-part mask on both normal pixel payloads. This lets either lane arrive first and lets one shared client rendezvous prove mixed completion without another round trip.
- Use the reverse video socket rather than input or auxiliary transport. Input is deliberately frameless and latency-critical; auxiliary transport is optional.
- Gate before capture rather than replacing queued video. An accepted P-frame is part of the decoder reference chain.
- Treat canvas commit as completion. Waiting for the OS compositor would add cost and platform coupling without helping server freshness.
- Require low-latency H.264 mode rather than widening the freshness window for an encoder with lookahead.
- Make decode failure terminal. Without a client keyframe request, continuing would leave the canvas stale and the server permit permanently outstanding.

## Review journal

### Adversarial review

Three independent reviews examined protocol correctness, concurrency, and latency, then each reviewer attempted to refute the other two sets against the code. The following findings survived:

- Normal mixed raw/video updates need an explicit required-part mask and one shared completion rendezvous.
- Validated suppressed work must complete, while decode/copy failure must be terminal and unacknowledged.
- Only the final move rendezvous transition may acknowledge a move.
- The new feedback reader must replace `poll_client_eof`, own socket input, and be shut down and joined before accepting another epoch.
- Epoch comparison and flow mutation must be atomic; disconnect must wake the gate and reset capture state without killing the server.
- A full-window wait must use short slices because the capture thread also pumps asynchronous encoder output.
- Feedback enqueue must be bounded and nonblocking after client canvas locks are released.
- Post-acquire rejection must invalidate speculative baselines and force recovery before sparse/move traffic resumes.
- Telemetry must separate configured and observed flow and demonstrate that full-window waits avoid capture work.

The proposed indefinite wait was refuted because no independent encoder-output thread exists. An eight-byte ACK parsing limit and writer ownership were already required but are now explicit. Repeated live percentile measurements remain useful validation, not a protocol requirement; the post-integration Quench acceptance test records observed latency and stale-tail behaviour.

### External review

Claude/Fable completed the one-pass external review and judged the design sound enough to implement after two corrections. Accepted findings:

- Make reservation cancellation structural with an RAII token so every assembler expiry, suppression, and queue rejection releases its permit.
- State and measure that skipped IDD presents lose ordered move metadata and may fall back to a larger pixel update.
- Require H.264 low-latency mode so two retained inputs cannot deadlock the two-permit window.
- Cover the tiled `FrameSet` path, define timeout as oldest outstanding reservation age, and record the deliberate terminal decode-error change.

The suggestion to compose arbitrary skipped move metadata was rejected for this change: the IDD retains only three latest slot records, while a blocked viewer may skip an unbounded number of presents, so it cannot reconstruct a trustworthy chain from the client's baseline. Final-pixel accumulated coverage is the correct fallback. The residual effectiveness risk is measurable: a post-wait drag may need regional/full H.264, and the Quench acceptance run must report that rate and latency.
