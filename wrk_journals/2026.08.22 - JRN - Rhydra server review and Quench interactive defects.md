# Rhydra server review and Quench interactive defects

## 2026-08-22

- Confirmed the live stack was green at 5120×2880, 240 Hz, and 200% scaling without opening a second viewer.
- Confirmed topology, not capture corruption: the IDD server opened at `(1920,0)`, while interactive Win32 inspection showed the physical display remained primary at `(0,0)`. Command Prompt, File Explorer, Media Player, and other reported missing windows were all on the physical display.
- Cleaned the temporary scheduled diagnostic task and its two remote files immediately after collecting the monitor/window geometry.
- Confirmed the load-sensitive client path: each two-tile 5K frame can wake and redraw twice; redraw holds the shared surface lock through full-frame CPU conversion, blocking the native network thread, while the same event loop owns input collection.
- Raised `MDR-BUG-FLU-00035` for display topology and `MDR-BUG-FLU-00036` for full-motion input starvation.
- Three independent reviews covered window placement, latency/backpressure, and holistic server correctness. Significant unrelated server findings will be deduplicated into the bug ledger rather than silently folded into this release unit.
- Refutation preserved the topology, logical-frame wake, bounded-damage, and snapshot findings. It added staged multi-display commit, suppressed-tile arrival accounting, and a 30 fps 5K presentation bound.
- The required Claude/Fable external design review hung without output for ten minutes and was stopped. It did not run; this remains an explicit residual risk rather than triggering a second pass.
- `MDR-BUG-FLU-00035`: made IDD primary-at-origin placement part of agent health, corrected the full attached-display layout with a staged Win32 transaction, verified the applied topology, and restarted a running server after correction because capture caches the display origin.
- The code review found that a failed null-device commit could leave staged registry modes behind. The rollback now restores every original mode and the original primary flag, then commits that restoration. A post-commit verification failure is reported distinctly and retried by reconciliation.
- Display regression proof: removing the placement predicate made `display_health_requires_the_idd_to_be_primary_at_origin` fail on its own `wrong placement must not be healthy` assertion. Restored code passed all 305 server-library tests, server clippy with warnings denied, and the macOS-to-Windows cross-target check.
- The integrated v0.1.122 client built and installed byte-for-byte at `~/.local/bin/mdrdp`. The matching Rhydra binaries deployed to Quench under `marti`, preserving 5120×2880 at 240 Hz and 200% scale, but the primary-display transaction did not land. The placement-aware health gate correctly held the server stopped.
- Independent live verification reopened `MDR-BUG-FLU-00035`: Quench still reported the IDD secondary at `(1920,0)`, `mode_ok=false`, with no viewer. The agent had discarded the exact Win32 correction error, preventing diagnosis.
- Added transient display-correction error evidence to the existing status rung. Its regression failed before implementation on the missing `scripted failure` text and passed after; review also required stale errors to clear on a new display request and on recovery.
- The diagnostic redeploy identified `DISP_CHANGE_FAILED (-1)` at the first `DISPLAY1` staging call; the rollback then failed identically for `DISPLAY1` and `DISPLAY13`. The failing implementation passed the complete `DEVMODEW` returned by `EnumDisplaySettingsW`, including fields it did not intend to change.
- Narrowed Win32 requests to the documented intent: position-only for untouched physical displays, and width/height/frequency/position for the IDD. Rollback reconstructs the same clean mode-plus-position shape and preserves the original primary flag. The live host remains the regression oracle because this path cannot execute on macOS.
- The narrowed GDI request also failed live with `DISP_CHANGE_FAILED (-1)`. That refuted the request-shape hypothesis and isolated the fault to using the legacy mode API for topology; Quench's driver stack accepts mode changes through it but not physical-display placement changes.
- Replaced the topology transaction with Windows CCD (`QueryDisplayConfig`/`SetDisplayConfig`). The transaction preserves all active path and target-mode data, moves only source positions, omits `SDC_ALLOW_CHANGES`, and checks the exact configuration plus GDI primary/origin state after apply.
- Applied all three independent code-review findings: rollback now re-queries path identities immediately before mutation; verification covers target timing, rotation, scaling, flags, source modes, and path order; and a preceding IDD mode change is restored after a safely rolled-back topology failure. If identities or rollback state become uncertain, the agent refuses a potentially stale mode restore and reports that state.
- Regression evidence remains the observed live failure: the old code left the IDD secondary at `(1920,0)` and the server health-red. Platform-free server tests pass (305/305), and the complete macOS-to-Windows type-check passes. Windows Clippy reaches the new code but remains red on six warnings in untouched `audio_policy.rs`, `input.rs`, and the existing `agent_ops.rs` test-module layout; none are suppressed or bundled into this fix.
- The final broad server review confirmed and separately raised nine defects: listener readiness (`MDR-BUG-FLU-00037`), partial input records (`00038`), auxiliary socket deadlines (`00039`), global image-name cleanup (`00040`), the 5K HEVC level contract (`00041`), bounded clipboard reads (`00042`), the NV12 surface pool (`00043`), bounded control lines (`00044`), and false send-completion telemetry (`00045`). It refuted video/stats writer coupling as intentional ordering and the per-tile send queue as compatible with the documented recovery model.
