# JRN — native transport increments (hybrid wire + IddCx direct)

Follows on from `2026.08.17 - JRN - P3 IDD driver spike.md`. Same worktree/branch
(`task/20260817-TSK-HUM-p3-idd-driver-spike`) — a later pass on the same task.

## 2026-08-17 (evening) — design pass

- Arthur endorsed writing the proper design after the spike's control run settled the
  240 Hz question. Agreed scope beforehand: the "simple plan" — hybrid raw-rect wire,
  then IddCx direct swapchain consumption, ~40 ms p50 kill/keep gate; wezterm overlay
  parked.
- Authored `wrk_docs/2026.08.17 - HLD - native low-latency transport.md`. Grounding
  reads first: `framing.rs` (length-prefixed, unknown-type-skippable — versioning
  story), `pipeline.rs` (connect-edge `request_keyframe()` already exists, so the
  mid-GOP wedge is the Quick Sync no-out-of-band-SPS/PPS problem plus an unverified
  keyframe request — fix is caching in-band sets from the stream's first IDR),
  `dxgi.rs` (no dirty-rect consumption yet), `send.rs` (single sender thread makes
  rect/AU interleaving trivially ordered).
- Key design choice worth remembering: rects are an **overlay beside an unbroken
  H.264 stream** (always encode, additionally send rects when small). Suppressing AUs
  would break the decoder's reference chain; the latency win is "don't wait for
  encode", not "don't encode".
- v1 rects are raw BGRA (no LZ4): 96 KB ceiling ≈ 2.6 ms on this WiFi LAN, typing is
  1–10 KB, and it avoids a new dependency; wire format reserves an encoding byte.
- Adversarial review: three parallel reviewers (protocol correctness / measurement
  rigor / Windows-driver feasibility), then a full cross-refutation round. 18
  findings; 2 refuted outright by committed artifact data, the rest folded (§11 of
  the HLD records the disposition). The round earned its cost several times over:
  - The async Quick Sync MFT pipelines, so the AU delivered in capture iteration N is
    routinely frame N−1's — which meant (a) the planned "AU repaints canvas" rule
    would wipe newer rect content, and (b) today's per-stage stats pair iteration-N
    capture stamps with an older AU: the published 5.3 ms encode p50 is a
    mismatched-pair quantity. One `u64 frame_seq` at capture fixes ordering,
    attribution, and the decompose join at once.
  - The MFT's event queue is pumped only inside `encode()` — on a static screen the
    last AU sits undelivered until the next captured frame. Idle pump added to
    Increment 0.
  - The original Increment 2 draft deleted Desktop Duplication — the very source of
    Increment 1's dirty rects — with no replacement; the journal's agreed plan had
    said "dirty rects included" and the HLD had dropped the clause. Metadata now
    rides the shared section.
  - The IOCTL/DuplicateHandle plumbing was wrong for UMDF2 (no caller-process
    object; no device interface or IoControl callback exists in the driver at all).
    Replaced with named shared resources (`CreateSharedHandle` with a name + SD,
    opened by name), IOCTL kept as costed fallback.
  - The gate was not statistically decidable (projection ~38 vs gate 40, inside
    historical CI half-widths). Now gates on the p50 CI upper bound, drops the
    single-sample max, adds a poisoned ceiling and a same-session control arm.
  - Two findings refuted by data already in `baseline/`: the 1920×1088 decoded-size
    mismatch (VideoToolbox crops to 1080 — every committed client frame says so) and
    the probe-bias-shift theory (observed capture gap is 16667 µs across 60 fps and
    240 Hz sources — a Mac-side ceiling indifferent to present count).
- Sequencing change out of review: new Increment 0.5 — a near-free dirty-rect
  telemetry run on the existing duplication path — is a hard precondition before any
  Increment 1 wire code, because the whole projection rests on the virtual display
  reporting small dirty rects, which has never been observed.
- External review: one Codex (Sol, xhigh) pass over the folded doc returned six
  MAJORs, all folded (HLD §11 lists them). The two sharpest were things every
  internal pass missed: the sender never *reads* its client socket, so on a static
  desktop a departed viewer wedges the single accept slot forever — which would have
  hung the mid-GOP acceptance test itself; and fixed `Global\` shared-resource names
  collide with a straggling server's handles on pool rebuild
  (`DXGI_ERROR_NAME_ALREADY_EXISTS`) — Microsoft's docs recommend random names, so
  only the rendezvous section keeps a well-known name (created once, squat-detected)
  and texture/event names rotate through it.
- HLD marked SELF-APPROVED and committed. Proceeding to implement per the lean
  process; the human gate remains integration.
