## 2026-08-17 (evening) — design pass

- Arthur endorsed writing the proper design after the spike's control run settled the
  240 Hz question. Agreed scope beforehand: the "simple plan" — hybrid raw-rect wire,
  then IddCx direct swapchain consumption, ~40 ms p50 kill/keep gate; wezterm overlay
  parked.
- Authored `wrk_docs/2026.08.17 - HLD - native low-latency transport.md`. Grounding
  reads first: `framing.rs` (length-prefixed, unknown-type-skippable — versioning
  story), `pipeline.rs` (connect-edge `request_keyframe()` already exists, so the
  mid-GOP wedge is the Quick Sync no-out-of-band-SPS/PPS problem plus an unverified
  keyframe request — fix is caching in-band sets from the stream's first IDR),
  `dxgi.rs` (no dirty-rect consumption yet), `send.rs` (single sender thread makes
  rect/AU interleaving trivially ordered).
- Key design choice worth remembering: rects are an **overlay beside an unbroken
  H.264 stream** (always encode, additionally send rects when small). Suppressing AUs
  would break the decoder's reference chain; the latency win is "don't wait for
  encode", not "don't encode".
- v1 rects are raw BGRA (no LZ4): 96 KB ceiling ≈ 2.6 ms on this WiFi LAN, typing is
  1–10 KB, and it avoids a new dependency; wire format reserves an encoding byte.
- Adversarial review: three parallel reviewers (protocol correctness / measurement
  rigor / Windows-driver feasibility), then a full cross-refutation round. 18
  findings; 2 refuted outright by committed artifact data, the rest folded (§11 of
  the HLD records the disposition). The round earned its cost several times over:
  - The async Quick Sync MFT pipelines, so the AU delivered in capture iteration N is
    routinely frame N−1's — which meant (a) the planned "AU repaints canvas" rule
    would wipe newer rect content, and (b) today's per-stage stats pair iteration-N
    capture stamps with an older AU: the published 5.3 ms encode p50 is a
    mismatched-pair quantity. One `u64 frame_seq` at capture fixes ordering,
    attribution, and the decompose join at once.
  - The MFT's event queue is pumped only inside `encode()` — on a static screen the
    last AU sits undelivered until the next captured frame. Idle pump added to
    Increment 0.
  - The original Increment 2 draft deleted Desktop Duplication — the very source of
    Increment 1's dirty rects — with no replacement; the journal's agreed plan had
    said "dirty rects included" and the HLD had dropped the clause. Metadata now
    rides the shared section.
  - The IOCTL/DuplicateHandle plumbing was wrong for UMDF2 (no caller-process
    object; no device interface or IoControl callback exists in the driver at all).
    Replaced with named shared resources (`CreateSharedHandle` with a name + SD,
    opened by name), IOCTL kept as costed fallback.
  - The gate was not statistically decidable (projection ~38 vs gate 40, inside
    historical CI half-widths). Now gates on the p50 CI upper bound, drops the
    single-sample max, adds a poisoned ceiling and a same-session control arm.
  - Two findings refuted by data already in `baseline/`: the 1920×1088 decoded-size
    mismatch (VideoToolbox crops to 1080 — every committed client frame says so) and
    the probe-bias-shift theory (observed capture gap is 16667 µs across 60 fps and
    240 Hz sources — a Mac-side ceiling indifferent to present count).
- Sequencing change out of review: new Increment 0.5 — a near-free dirty-rect
  telemetry run on the existing duplication path — is a hard precondition before any
  Increment 1 wire code, because the whole projection rests on the virtual display
  reporting small dirty rects, which has never been observed.
- External review: one Codex (Sol, xhigh) pass over the folded doc returned six
  MAJORs, all folded (HLD §11 lists them). The two sharpest were things every
  internal pass missed: the sender never *reads* its client socket, so on a static
  desktop a departed viewer wedges the single accept slot forever — which would have
  hung the mid-GOP acceptance test itself; and fixed `Global\` shared-resource names
  collide with a straggling server's handles on pool rebuild
  (`DXGI_ERROR_NAME_ALREADY_EXISTS`) — Microsoft's docs recommend random names, so
  only the rendezvous section keeps a well-known name (created once, squat-detected)
  and texture/event names rotate through it.
- HLD marked SELF-APPROVED and committed. Proceeding to implement per the lean
  process; the human gate remains integration.

- **The first-cut blit rule (`au_seq > last_rect_seq`) was wrong.** The async

  rects had its only carrier suppressed, indefinitely under sustained typing.

  (`suppress_rects_once`).

## Targeted re-review: fixes confirmed, one new major, hold-back added

The re-review confirmed all four fixes (the exactness rule kills the original
suppression defect; the Arc path is provably zero-copy on the AU side and
race-free; Recreated consumes exactly one frame; minors all landed) — and
caught a genuine new major the strict gate introduced: with the encoder one
frame behind capture, a single predicate miss leaves every later rect update
exactly one frame ahead of exactness, skipped forever at rect cadence. The §8
glass probe types into an idle desktop, so the acceptance run would have shown
a healthy hit rate while sustained use ran at zero.

Fix: a one-slot **gap hold** (HLD decision 16). A `gap` update is held, newest
wins, and applied the instant the AU that closes the gap arrives — nothing ever
paints over a hole, one delayed rect per miss, full-rate recovery on the next
frame. Expiry is AU-driven (`stale` when an AU jumps past; dropped on rebase);
no timer. Four new tests, including the collapse-recovery regression; the
disable-the-hold mutation turned two red. Viewer now 56+3 green, clippy clean.

## 2026-08-18 (later): client ordering landed; the pilot found the real ceiling

Built and committed (3b44c57) the two client-side ordering fixes the decompose
priced: the pump now dispatches a read batch's MSG_RECTS before its decodes
(mutation-proven order test), and the window presents directly on the wake
instead of `request_redraw` (which rides the display cycle on macOS).
57+3 tests, clippy -D warnings, fmt, release build clean.

The live pilot then rewrote the diagnosis. Per-trial tracing showed:

- The window thread was never the problem: it picks a wake up in ~0.1 ms.
  The residual ~10 ms of rect paint→present is one in-flight present ahead
  (~5 ms) plus the present's own cost (~5 ms: an 8.3 MB `present_into` blit
  plus commit). Present serialization, not scheduling.
- **The keystroke-response frame itself misses the fast path on the server,
  every time, in the isolated-keypress regime.** After ~1 s of idle, DWM's
  first recomposition reports a near-full-screen dirty region — 7,220,580
  bytes claimed across 2 rects — while the same frame's AU encodes to
  2.5 KB. The predicate (≤96 KB) rightly refuses it, the glyph rides the AU
  through the ~21 ms encode, and the follow-up frame's small rect gap-holds
  behind that AU's decode. No client ordering can recover what the server
  never sent.
- The §5a telemetry's 58% hit rate is not contradicted: a continuous typing
  burst keeps DWM hot and the dirty regions honest. Glass's paced trials
  (~1.2 s apart) hit the cold-recomposition path on every response frame —
  and that is the regime an isolated keypress lives in.

Consequence: the next real win is server-side — see through the over-broad
metadata by diffing the captured frame against the previous one (keep a
prev-frame texture on GPU via CopyResource ~0.3 ms/frame; on a
predicate-miss-by-size frame, read back both dirty regions and tile-diff on
CPU, ~3-5 ms, against the ~15-20 ms encode wait it avoids). That design
belongs with Increment 2 (IddCx direct swapchain), which owns the same
textures.

Also settled with Arthur: glass runs get an announced ~4-minute hands-off
window, batched; the machine is his at all other times. An unannounced run

## 2026-08-18: Increment 2 build starts (IddCx direct swapchain consumption)

Arthur's direction after the measured runs: minimal latency — client ordering
(built on its own branch, 3b44c57) and this increment. HLD §6 governs; two
parallel workers on disjoint halves, lead owns the contract and review.

The lead-designed piece is the cross-language section contract, which extends
§6 with one invariant the design sketch left implicit: **union coverage across
skipped slots.** Desktop Duplication accumulated dirty metadata for us;
a 3-slot pool does not. Each slot record therefore carries
`dirty_since_frame_seq` — the previous publish into that slot — and its rect
list is the complete coverage of `(dirty_since, frame_seq]` (the driver folds
every frame's dirty ∪ move-dest into all three slot accumulators). A consumer
may claim rect coverage only if its last consumed frame ≥ `dirty_since`;
otherwise the frame is metadata-absent and takes the always-safe full path.
Without this, a consumer that missed a publish would paint a "complete" delta
that wasn't, and the client's exactness invariant would hold a lie.

with the SDDL DACL — the HLD's named first risk; squatting detection = loud
refusal on ERROR_ALREADY_EXISTS; (2) driver redeploy via the proven

## 2026-08-18 (lunch window): the Increment 2 A/B — parity, and the real lesson

Arthur handed the Mac over; both arms ran clean, n=100 each, zero timeouts
(one pilot hiccup: a single keystroke vanished end-to-end and the doc drifted
a column — a fluke that did not recur in 208 subsequent trials, but worth an
eye). Full tables in the HLD's "Increment 2 measured verdict".

Headline: **idd 75.4 / dxgi 74.0 p50 — parity — with the idd arm worse in the
tail (p95 192 vs 92) and starved of the rect path (0/98 vs 99/100).** The
smoke's "IddCx metadata looks finer" hope from this morning was wrong, and the
A/B data says why: IddCx dirty metadata is relative to the returned swapchain
BUFFER, not to the previous frame — at paced cadence DWM hands back a buffer
that last presented several frames ago and honestly reports most of the screen
dirty (measured p50 7.25 MB claimed vs DXGI's 25 KB for the same keystrokes).
Our 3-slot unions compound it. The capture saving the increment was built for
is real and measurable — present→acquire fell from 7.9 ms to ~0 — but it buys
nothing while every detection pays the 23 ms codec chain the rect path exists
to skip.

So the increments have triangulated the actual problem: the DXGI source's DWM
cold-recompose miss (yesterday) and the IDD source's buffer-relative metadata
(today) are one disease — **metadata cannot be trusted to describe the true
per-frame delta in exactly the regime users feel** — and the cure is one
mechanism: keep the previous frame on the GPU, and on a predicate-miss frame
diff the dirty region down to true changed tiles before deciding the path.
That is the next increment, and the IDD source's texture plumbing (already
holding both frames on one device) is where it naturally lives.

## 2026-08-18 (afternoon): Increment 3 built — the diff that stops trusting metadata

Arthur's word after the A/B report: "Integrate and then continue!" — so the two
ready branches landed (client ordering, then Increment 2, trunk at v0.1.62; one
journal-append conflict resolved by keeping both sections) and this branch
(`task/20260818-TSK-HUM-increment3-pixel-diff-rects`) built HLD §6b.

Two parallel workers on disjoint files, lead-fixed contract between them:

- `src/diff.rs` (portable, tested on macOS): 64×16 desktop-aligned tile
  comparator + run coalescer. Compares only pixel bytes, never pitch padding
  (staging maps carry uninitialized garbage there); unverifiable input (short
  slice, narrow pitch) reads as a diff *miss*, never as clean — the stale-canvas
  direction is the one that must be impossible. 14 tests, 13 mutations each
  observed red; the property-style coverage test caught an over-merge mutation
  through genuine under-coverage it was never written for.
- `src/win/pixel_diff.rs`: prev-frame GPU retention (unconditional CopyResource
  while enabled — the baseline must never silently skip a frame), two staging
  surfaces, region-only copies, both maps held leak-safe, rect payload packed
  straight from the current map (no second readback).
- `pipeline.rs`: five-condition gate — diff enabled, not post-Recreated,
  metadata path didn't fire, valid baseline, ≥100 ms idle gap — plus "a claim of
  no change has nothing to verify". Scan region = clipped bounding box of the
  claim (a claim is never short, only inflated), full frame when metadata is
  absent. Shared `send_rects` tail so the drop-accounting policy exists once.
