# 2026.08.17 — DWMFRAMEINTERVAL=15 on quench: motion halved, typing unmoved

Follow-up to this morning's cadence journal. Arthur enabled sudo on quench;
the knob was applied *through an mdrdp session itself* — an `--input-script`
opened PowerShell, ran `sudo powershell`, set the value elevated, and read it
back, with `--screenshot` capturing the proof ("DWMFI now: 15" in an
Administrator window). Two gotchas that made this work:

- **quench is UK keyboard layout.** autoinput `type` maps ASCII to US
  scancodes, so `"` arrives as `@` and `\` as `#`. Workaround: PowerShell's
  registry provider accepts FORWARD slashes and single quotes —
  `'HKLM:/SYSTEM/CurrentControlSet/Control/Terminal Server/WinStations'` —
  a fully layout-safe charset.
- `sudo powershell` opens the elevated shell in a new focused window, so the
  script just keeps typing into it. No quoting through cmd→sudo→PS needed.

## Results (same scripted workloads, before → after, new connections)

| measure | before | after |
|---|---|---|
| drag frame-gap p50 | 31.8 ms (~30 fps) | **16.0 ms (~60 fps)** |
| drag RTT p50 | 23.3 ms | **12.3 ms** |
| typing frame-gap p50 | 47.8 ms | 33.3 ms |
| typing RTT p50 | 33.0 ms | 34.3 ms (p99 603 → 100) |

Conditions: quench LAN, 1920x1080, AVC444v2, mdrdp 0.1.41, 75 s runs,
2026-08-17. quench now runs with DWMFRAMEINTERVAL=15 permanently — later
measurements against it are on the new baseline.

## Reading

The 30 fps cap was real and is gone: sustained motion runs at 60 fps and
motion latency halved. Typing has a separate ~33 ms server-side floor that
the cap did not cause: keystroke → app repaint → DWM composite → encode
(Windows 11 Notepad's XAML editor plausibly adds a frame or two of its own).
Client share remains ~4 ms (decode p50 2.4, present p50 6.4).
