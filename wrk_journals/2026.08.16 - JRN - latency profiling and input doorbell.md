# 2026.08.16 — Latency profiling with samply; input doorbell; pipeline split

## What happened

Profiled two live sessions against quench (`ano`, 1920x1080, release +
line-tables) with samply 0.13.1: an interactive typing run and a heavy-paint
window-drag run, 75 s each, `--input-script` driven, graceful shutdowns.
Profiles and metrics JSONs are session artifacts (scratchpad, not committed);
the numbers that matter are recorded here and in the metrics schema itself.

## What the profiles said

- Session thread: 647 ms CPU / 75 s. 405 ms of it was `recvfrom` — the 5 ms
  READ_SLICE polling loop, ~200 wakeups/s. Decode itself is cheap: VideoToolbox
  hands back AVC444v2 frames in ~0.2 ms and `to_rgba_into` (CPU YUV→RGBA) was
  110 ms total.
- UI thread: 2.5 s CPU, dominated by a full-frame copy per present
  (`_platform_memmove` 785 ms + `present_into` 294 ms + vImage scaling) — even
  for a caret blink. Scratchpad item: softbuffer `present_with_damage`.
- Quench sends AVC444v2 (H.264), not the ClearCodec/RFX mix temper sends.

## What changed (shipped)

1. **Input doorbell** (`src/wake.rs`): the pump now sleeps in `poll(2)`/`WSAPoll`
   on the RDP socket AND a loopback UDP doorbell every input/command sender
   rings. Keystroke→wire is now microseconds (was 0–5 ms); idle wakeups fell
   from ~200/s to 4/s (`recvfrom` CPU 405 ms → 1.4 ms, verified by a rerun
   profile). Before sleeping the pump checks the framer buffer and rustls
   plaintext so a buffered frame can never stall for the idle wait.
2. **Pipeline split** (`stats::SessionStats::{decode, present}`): per-frame
   decode work (summed `process` time) and paint→present handoff, in the
   overlay ("pipeline" line) and metrics JSON (additive, schema still v1).

## The finding that redirects the work

Typing RTT against quench: p50 30.8 ms before, 34.1 ms after (noise; p95/p99
identical) — removing the 5 ms slice did NOT move the headline number. The new
split explains why: client decode p50 1.3 ms + present p50 2.0 ms ≈ 3.3 ms
client-side, on a 3 ms-RTT LAN. **~27 ms of a ~33 ms typing round trip is the
server's encode/frame cadence** (~15 fps observed while typing). The client is
not the bottleneck for interactive latency against quench; server-side frame
pacing (H.264 encode policy, frame-rate caps) is where the next 20+ ms lives.

Conditions for all numbers: quench over LAN, 1920x1080, AVC444v2, release
build, mdrdp 0.1.38 task branch, 2026-08-16.

## Dead ends / gotchas

- `samply record --save-only` writes unsymbolicated profiles; symbolicate
  offline via `samply load -n` + its `/symbolicate/v5` API (no browser needed).
- macOS loopback UDP delivery can lag the send: a drain immediately after a
  burst of rings can miss late datagrams. Harmless for the pump (spurious
  wake); the test drains until quiet.
