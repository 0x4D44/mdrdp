# Native interactive regressions

## 2026-08-21

- Arthur's first 5K/200% native session exposed three usable-desktop blockers:
  channel-swapped colour, two pointers with a seconds-late captured pointer,
  and seconds-late keyboard feedback.
- Recorded them separately as MDR-BUG-FLU-00029 through 00031 so each green fix
  can integrate as soon as it is proven.
- Code inspection established the colour root cause: the tiled H.264 decoder's
  RGBA output enters the BGRA-only strict blit. Cursor ownership and keyboard
  latency still require measured diagnosis.
- Read-only telemetry from Arthur's still-running 5120x2880 session split the
  keyboard symptom. Across 85 server input records, receive-to-`SendInput`
  injection was 0.123 ms p50, 0.225 ms p95, 0.964 ms max. Across 2,882 encoded
  tile rows, Windows present-to-send was 61.285 ms p50 and 89.753 ms p95. The
  host therefore is not holding keys for seconds; any repeatable multi-second
  delay is after the host socket or is an input-to-visible-change mismatch.
- The current native client presence record reported 1,234 painted frames,
  zero decode errors, and 41.6 ms recent input-to-paint p50 after about eight
  minutes. This metric closes on the first paint after input, not necessarily
  the paint caused by that key, so it rules out a continuously seconds-deep
  client queue but does not refute Arthur's specific visual observation.
- Microsoft documents that IddCx uses a software cursor by default and that a
  driver must call `IddCxMonitorSetupHardwareCursor` to take cursor ownership.
  The current driver never does. The cursor fix therefore needs the IDD cursor
  plane or equivalent separate cursor transport; hiding the immediate local
  cursor would preserve the laggy copy and is rejected.
- Both adversarial reviewers confirmed that the draft needed causal acceptance,
  strict RGBA bounds, explicit cursor ownership, and a bounded native mouse-move
  path. The HLD now uses `probe glass` at n=100, keeps key/button/wheel events
  reliable, and assigns cursor-free capture to IddCx hardware-cursor mode with a
  local macOS pointer.
- The reviewers disagreed on whether one socket read can create unbounded video
  work. That risk is not allowed to justify speculative H.264 dropping: land the
  strict row-copy first, measure received-versus-painted sequence depth, and only
  suppress presentation after required reference decode if the causal run fails.
- The external Fable review found a cursor correctness edge: IddCx falls back to
  software composition for any shape outside the driver's declared capabilities.
  The local WDK 10.0.26100 IddCx 1.6 header confirms monochrome pointers become
  masked-colour pointers and `FULL` is the value that claims them. The design now
  claims alpha plus full XOR at 256x256 and adds I-beam/accessibility-size live
  checks. Its suggested `CursorShapeTypes` field was rejected because the actual
  `IDDCX_CURSOR_CAPS` has no such member.
- The external pass also exposed two false-reassurance risks: `decode()` includes
  scalar YUV-to-RGBA allocation/conversion before the new row copy, and `probe
  glass` can trigger on a Notepad caret blink. The conditional backlog diagnosis
  now measures conversion and socket bytes, while the acceptance run disables
  caret blink and excludes its column.
- Cursor visibility uses the existing shared-header reserved word as an atomic
  hidden flag. Layout v1 remains compatible, so driver, server, and client do not
  become a lockstep deployment unit.
- MDR-BUG-FLU-00029 is fixed in `1b33855`: a distinct-channel tiled decoder test
  first failed with `[51, 34, 17, 68]` instead of `[17, 34, 51, 68]`, directly
  proving the red/blue reversal. A new strict RGBA row-copy preserves those bytes,
  rejects overhang/size mismatch, updates generation/accounting, and leaves raw
  BGRA swizzling unchanged. Native and surface suites, mdrdp clippy, formatting,
  and the Windows cross-check passed. Independent code review found no required
  change; its one useful accounting suggestion was applied.
