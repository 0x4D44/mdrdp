# 2026.08.16 — JRN — drag-resize corruption, remote cursor, audio ring, AVC decode

Follow-on from the bandwidth-measure/codec-state session (v0.1.25). Arthur reported
residual image corruption when dragging/resizing remote windows, no remote cursor
mirroring, and picked the work order: corruption → cursor → audio burst drops, with
AVC/VideoToolbox green-lit as the follow-on feature. All live work on quench as `ano`.

## Drag/resize corruption: the glyph cache is keyed by content, not shape

The input-script DSL gained a `drag x1 y1 x2 y2 [ms]` command (press, interpolated
~16 ms moves, release) because the corruption repro *is* a mouse drag and the DSL could
not express one. A scripted storm — Explorer maximize, three drags, two keyboard resizes
(Alt+Space+S + arrows), snap cycle — reproduced it first try: **12 ClearCodec decode
errors, all "cached glyph dimensions mismatch"**, and visible stale rectangles in the
final buffer.

A temporary probe printed both sets of dimensions on every failing hit. The result was
unambiguous: **24 mismatched hits in one 90 s run, every single one an equal-area
reshape** — 1x6 hit as 2x3, 12x12 as 24x6, 7x5 as 5x7. Windows keys the ClearCodec glyph
cache by pixel content, so identical bytes at a different shape legitimately hit the same
entry. FreeRDP's `clear_decompress_glyph_data` only checks that the cached entry covers
the destination pixel count; our vendored decoder demanded exact width/height equality
and rejected all of them, leaving a stale rectangle per rejection.

Fix in `vendor/ironrdp-graphics/src/clearcodec/mod.rs`: a glyph hit succeeds when the
cached bytes cover the destination area, reinterpreted at the destination shape; larger
destinations still fail. Verified live: the same storm now ends with **0 decode errors
and a pixel-clean desktop** in the final session buffer.

## Remote cursor: enabled, decoded, mirrored natively

`connect.rs` still had `enable_server_pointer: false` from the pre-rendering probe phase,
and the session loop dropped all pointer outputs. Now: the connector enables server
pointers (software rendering stays off), the session thread translates IronRDP's
pointer outputs into a `CursorUpdate` sent through the window `Waker`, and the window
maps bitmap shapes onto winit `CustomCursor`s — straight-alpha RGBA, hotspot clamped,
cached by content hash (Windows re-sends the same few shapes constantly). Hidden/default
states are honoured; server-side pointer warps are deliberately ignored (fighting the
user for their own mouse). Verified live: quench sent 41x39 cursor shapes and the
pipeline forwarded them (`remote cursor shape` debug lines). Visual confirmation of the
rendered pointer needs a human at the Mac — the session buffer no longer contains the
cursor (that is the point).

Caveat noted for later: the custom cursor is not scaled by the viewport, so a heavily
letterboxed window will show a slightly-large cursor.

## Audio: overruns were bursts; "underruns" were mostly a counting artifact

MDR-BUG-FLUX-00001's numbers decoded differently on inspection: `overruns` counts
*samples* (1880 ≈ 20 ms of audio lost in 120 s — bursts marginally exceeding the 200 ms
ring), while `underruns` counted every dry device pull after first audio at ~100 pulls/s,
so any quiet stretch inflated it by thousands. Two changes:

- `RING_BUFFER_MS` 200 → 400. Capacity, not latency: steady-state depth is the server's
  actual lead; the headroom only absorbs bursts.
- Underruns now count dry-spell *episodes* (transition into silence, re-armed when audio
  resumes). One episode = one audible gap.

Verified under real load (YouTube in Edge on quench, 110 s, 78 s of actual playback,
13.8 MB PCM): **overruns 0** (bug's acceptance bar), underruns 16 episodes. The bug is
claimed and will be landed on integration.

## AVC420 via VideoToolbox: client ready, server declines until policy allows

`src/h264.rs` implements `H264Decoder` on a `VTDecompressionSession`: the EGFX wire's
AVCC access units go in unmodified (VideoToolbox's native framing), BGRA comes out, so
the media engine does both decode and colour conversion. Session built lazily from
in-band SPS/PPS, rebuilt on parameter-set change and on `kVTInvalidSessionErr`
(sleep/wake, GPU reset). Hand-written FFI — seven calls, three statics, no new
dependencies. The vendored egfx client now skips a frame whose decode fails instead of
erroring the channel.

Capability advertisement with a decoder present is **V8.1 + AVC420_ENABLED** —
deliberately lower than V10.7, because V10+ has no "AVC420 but not AVC444" flag and an
unrestricted V10.7 invites AVC444, which neither the vendored client nor the decoder
handles. V8.1 keeps ClearCodec and Progressive for desktop content.

Live result: quench **confirmed the capabilities with avc420=false** — same posture
temper showed in the P1b spike. Desktop Windows strips the AVC flag unless the host
enables "Prioritize H.264/AVC 444 graphics mode" (or hardware encoding) policy. The
client half is done and provably negotiating; flipping that policy on quench is the
pending host-side step, after which the VideoToolbox path gets its first real frames.

## The number that matters anyway

The same 110 s YouTube run, still on the software path (ClearCodec + Progressive):
**2,711 frames ≈ 25 fps, input-to-paint p50 72 ms, zero decode errors** — against
188 frames (~1.6 fps) for the equivalent run two days ago. The bandwidth-measure fix is
carrying video respectably even before H.264 lands.
