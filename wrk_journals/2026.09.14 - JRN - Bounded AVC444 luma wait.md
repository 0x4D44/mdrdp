# Bounded AVC444 luma wait

Arthur asked to replace the chroma-only debounce with a short luma wait and to
integrate the implementation. MDR-BUG-FLU-00130 tracks the recurrence; the older
closed record remains immutable.

The policy now waits up to 50 ms from the first pending luma update, releasing
early when accepted chroma covers its regions. LC0's independent region lists are
preserved. The decoder still applies every accepted update in wire order; no
frame-ID pairing or chroma rejection was added. Paired callbacks protect the
whole bitmap update even outside StartFrame/EndFrame.

The old 41.748/41.782/42.220 trace shows 438 ms between chroma and submission,
but metadata alone cannot explain that interval or prove a pixel/decoder fault.
Added redraw scheduling, defer-reason, visibility and submission-duration logs
to distinguish future cases. Existing flip-flop storage limits are unchanged.

## Review decisions

Successful current-stamp acknowledgement is sufficient to retire a pending
batch. A second wall-clock condition was removed; it added no protection and
made deterministic-clock testing misleading. Active updates and stale stamps
still cannot acknowledge newer pending work.

Bound both stored fragments and input regions before expensive geometric work.
Overflow releases the wait; it does not skip decoded pixel writes.

An unchanged output mapping is not a lifecycle reset. Clearing the policy on
every MapSurface PDU would let repeated mappings restart the wait indefinitely.
Actual mapping/incarnation changes still clear obsolete coverage.

The cross-family consultant was unavailable because its quota was exhausted.
The lead verified Microsoft's protocol documentation and reviewed the worker
changes directly. No independent visual verification is claimed.

## Evidence

All commands used the existing main-clone Cargo target cache, bounded timeouts
and closed stdin. No test connections or installed-client replacements were made.

- `cargo test --locked -p mdrdp --lib gfx::tests::`: 65 passed (also matches the
  `egfx` module). Removing luma coverage from the real callback chain made the
  new decoded-coverage test fail at its deadline assertion; restored and passed.
- `cargo test --locked -p mdrdp --lib window::tests::`: 69 passed. Reversing the
  snapshot gate's stamp comparison made all three changed timing tests fail,
  plus the existing large-canvas copy test; restored and passed.
- `cargo test --locked -p mdrdp --lib surface::tests::`: 73 passed in the lead's
  final run. The worker reports individual red/green fixture mutations for all
  15 new/rewritten policy tests, including expiry/rearm and repeated mappings.
- `./scripts/test-vendored.sh`: all vendored suites passed, including 48 EGFX,
  219 graphics and 372 PDU tests. The worker also observed the new callback-order
  test failing with deliberately corrupted metadata, then restored it.
- `./scripts/check-windows.sh --locked`: passed for the application and host
  crate. Existing warnings concern unused Windows presenter dimensions and
  unavailable icon-embedding tooling; neither is introduced by this change.
- `cargo clippy --locked -p mdrdp --lib -- -D warnings`: passed.
- Root formatting and diff whitespace checks passed. An additional standalone
  EGFX formatting check reports existing drift in untouched client/server code;
  checking the origin client source confirms the same pre-existing formatting
  differences. The new callback/test blocks introduce no formatter differences.

These tests establish scheduling, coverage and callback behaviour, not the
subjective flicker result. A release-profile client on the affected terminal is
still needed for that judgement. Chroma later than 50 ms can still produce a
visible refinement; the latency bound deliberately wins in that case.
