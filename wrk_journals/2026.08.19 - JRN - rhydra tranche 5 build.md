## The fork, and Arthur's answer

Two independent reviews found the same blocker before a line was written: **the
native transport had no client→server message channel at all.** The video socket
is server→client by construction (`win/send.rs`'s `poll_client_eof` peeks and
never consumes) and the input channel is frameless, where an unknown record kind
is terminal — which the client reads as session death. So clipboard sent
upstream to a 0.4.0 host would have killed keyboard, mouse and the session, and
the parent HLD §6's "old peers stay safe" held server→client only.

Arthur chose the dedicated auxiliary channel, **and extended it to audio**:
video latency is critical; audio, and even more so clipboard, are lower-priority
traffic that must not back up the video. That is now a settled input for the
rest of the build-out, not just this tranche. Parent HLD §6 amended.

## Done, committed, green

1. **`tools/latency-spike/server/src/aux_proto.rs`** — the channel's dialect.
   Type bytes start at 0x20, deliberately disjoint from `input_proto`'s kinds
   1..=7: a stray byte on the input channel is a valid `MouseMove`, so a
   cross-wiring mistake there injects mouse motion instead of erroring, and
   nothing here may share that hazard. 256 KiB ceiling enforced on send *and*
   receive. LF canonical on the wire. Hand-written `Debug`. 11 tests.

2. **The capability gate** — `stats::Header.clipboard` (SCHEMA 5→6,
   `wire_version` unchanged at 3), `ForwardPorts.aux` + the 9503 forward
   (`src/native/ssh.rs`), and probe step 5 (`src/native/probe.rs`), which opens
   the socket only if the host advertises it and treats every failure as "no
   clipboard, working session". 6 tests. The oracle for "never opened it" is the
   *listener's* accept counter, because a client-side assertion cannot tell
   "never opened" from "opened and closed".

3. **`src/native/clipboard.rs`** — the decision layer. Single-slot suppression,
   canonical-form fingerprinting, `note_applied` read-back, the size gate and
   the direction gates. 17 tests.

Every test in all three was made to fail under a mutation of the property it
claims to guard (32 mutations total), then restored from a saved copy.

## Two design departures from the HLD, both recorded in it

- **The last-sent fingerprint slot is not implemented.** As a suppression key it
  reintroduces the exact counterexample §5 was written to fix. Canonical-form
  hashing plus `note_applied` close the loop properly instead.
- **A test caught a real ordering bug**: the size gate ran before the
  suppression check, so an oversize clipboard would have re-reported on every
  250 ms poll. Suppression now runs first.

## BLOCKED, and it needs Arthur

**AC6 could not run, and it is the one acceptance criterion with a closing
window.** It proves a clipboard-aware client degrades safely against a host that
predates the channel — which stops being testable the moment a tranche-5 agent
is deployed to quench, because there is then no 0.4.0 agent left to test
against.

Two things stand in the way, in order:

1. **quench's capture path is down.** Its IDD device is gone
   (`device_present: false`, `stuck: "device"`) and the capture server is
   stranded on shared-section generation 1 while the driver publishes 2, so
   nothing listens on 9500 and no native session can connect. Agent 0.4.0 itself
   is healthy on 9502, and `mdrdp quench.lan.example --doctor` names every rung of
   this correctly — tranche 4's ladder doing its job.
2. **The designed remedy was refused.** `cycle-device` (with the challenge token
   from live status) is exactly the verb for a missing device, and no viewer was
   attached, but the permission classifier blocked the call. I treated that as a
   stop signal and left the box untouched rather than reaching for the rig's
   `mdrdp-cycle-idd` task, which would have been the same state change by
   another route.

**Consequence for sequencing: nothing may be deployed to quench until AC6 has
run.** That is the whole reason unit 2 was built before any server-side work —
it is the client half AC6 needs, and it is done and green.

Also worth knowing: there is still **no client CLI for `cycle-device`**. Driving
it needs a hand-rolled control client over an ssh tunnel. Worth a `--doctor
--cycle` or similar, since the ladder now names the fault a human then cannot
act on.

## Next, in order

1. The aux channel's client-side I/O: reader and writer threads over the socket
   from `ProbeSuccess.aux`, with the depth-1 **keep-latest** outbound slot from
   HLD §2 (clipboard is last-writer-wins, so superseding a queued payload is not
   a loss, and unbounded growth is impossible by construction). Tranche 6 adds
   the audio tier *above* it with a strict-priority sender; do not build that
   tier speculatively now.
2. The server-side aux listener in rhydra, and the header setting
   `clipboard: true` only once it is actually bound.
3. The Windows clipboard owner: message-only (`HWND_MESSAGE`) window,
   `AddClipboardFormatListener`, bounded-retry `OpenClipboard`, and a watchdog
   on the open/empty/set/close sequence that **reports and never kills**. The
   wedge to design against is `EmptyClipboard`'s synchronous
   `WM_DESTROYCLIPBOARD` to a hung previous owner, not `OpenClipboard`
   contention — we are already past the open when it bites.
4. An agent verb to read the **interactive-session** clipboard. AC1 and AC8
   cannot run without it: an ssh session on Windows runs in a different session
   and window station, so `Get-Clipboard` over ssh reads the wrong clipboard.
   Note it is a second `OpenClipboard` consumer and will contend with (3) — the
   instrument perturbs what it measures.
5. AC6 (needs quench back), then deploy, then the remaining live ACs.
6. The soak: ≥8 h, and a ≥4 h run is a **provisional gate that must be labelled
   as such**, not a discharge of "all-day".
