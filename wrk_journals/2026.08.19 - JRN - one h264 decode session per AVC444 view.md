# 2026-08-19 — one H.264 decode session per AVC444 view

Running under the lean end-to-end process Arthur specified: understand → design →
adversarial review → external (cross-family) review → self-approved checkpoint →
implement → code review → validate.

## Where this came from

Tail end of the MDR-BUG-FLUX-00008 investigation. Fixing the ResetGraphics decoder
teardown (landed 0.1.79) turned a permanent black desktop into a recoverable burst, but
`-12909` failures remained. The structural cause left standing: both AVC444 views decode
through one `h264_decoder`, so each view's P-frames are predicted against the other
view's last frame.

## Decisions taken before design, with Arthur

- **Not per-surface decoders.** I initially proposed a map keyed by `(surface_id,
  sub_stream)`. Arthur asked why there would ever be two surfaces for one desktop — and he
  was right. A surface's size is fixed at `CreateSurface`, so a resolution change
  *replaces* it; there is only ever one live surface (`+2 -1` healthy, `+4 -3` after a
  maximize), and multi-monitor is out of scope. The map was machinery for an impossible
  case. Corrected an over-claim of mine in the process: I had said surfaces also exist for
  composition and caching, which is generic EGFX capability, not what our server does.
- **Not async/parallel decode.** Arthur's hypothesis was two hardware decoders, one per
  stream. Checked the device tree: this M5 Max has **one** decode engine (`avd0`) and
  **two** encode engines (`ave0`, `ave1`) — the encoders confirm the numbering reflects
  real instances, so `avd0` alone is a positive finding. Two sessions multiplex onto one
  engine, so parallel submission buys pipelining crumbs while costing a memory-ownership
  rework: `h264::decode_with_session` is deliberately synchronous because the decode
  callback writes through raw pointers into the caller's stack frame. Arthur's call:
  "if there's only one decoder then async just adds hassle - better to keep sync".
- **Two decoders is a CORRECTNESS change, not a performance one.** Reference frames are
  not a warm cache; a P-frame is undecodable without them. Client decode measures ~1.3 ms
  against a ~30 ms typing round trip that lives on the server, so no speedup is claimed.

## FreeRDP comparison (Arthur: "we can't be the first to hit this")

We are not. [FreeRDP #4371](https://github.com/FreeRDP/FreeRDP/issues/4371), "black screen
with gfx and suppress output", reproduces by switching workspaces away and back — our
scenario. Reading their source settled three things:

- `gdi_ResetGraphics` does not reset the decoder the gfx path actually uses. It resets
  `codecs->h264` (shared) while AVC420/AVC444 decode with `surface->h264` (per surface).
  Our 0.1.79 fix matches upstream.
- FreeRDP suppresses output only on **minimise** (`UnmapNotify` / minimized
  `PropertyNotify`), never on occlusion. We suppress on occlusion, which for a fullscreen
  macOS session fires on every Space switch. Established clients avoid this bug by rarely
  entering the suppressed state, not by handling resume better. Arthur has **parked**
  moving us to minimise-only for now.
- FreeRDP sends **no** Refresh Rect on resume — our FLUX-00006 fix already does more than
  upstream, so the repaint request was never the weak link.
- But FreeRDP feeds **both AVC444 sub-streams through one decoder instance**. So this
  change goes beyond upstream rather than catching up to it. Flagged as read from a
  summarising fetch on a subtle point — verify before relying on it.

## The trap this design exists to avoid

Under LC=2 the chroma frame travels in **stream1**, not stream2. Routing decoders by wire
slot would feed the aux view's frames to the main decoder and rebuild the exact defect.
Decoders must follow the **view**. The existing `yuv_scratch.0`/`.1` split already encodes
that correctly, so decoder choice mirrors scratch choice.

## Outcome

Arthur settled it in one line: he has eyeballed AVC444v2 output on 0.1.79 and later and it
is correct. That is the August HLD's own acceptance criterion being met.

The point I had missed is *what* that validates. Re-reading the guard: when the ABAB
condition fires it returns `Err` and **preserves the existing session** — so the frame is
skipped and counted, and the working decoder survives. So correct output validates the
single decoder **and** the guard as a system, not the narrower claim that the views never
diverge. The one guard firing on kiln is therefore the guard working, not a defect: the
views diverged once, it absorbed the divergence for the price of one frame, and the picture
stayed right.

That removes the entire case for splitting. It also inverts the risk: this design's
acceptance criterion 6 was to delete that guard as dead code, which would have converted
one skipped frame into a double rebuild per frame — the permanent-black failure 0.1.79 was
written to remove, re-entered by another door.

**Delivered instead of the redesign:**

1. `src/h264.rs` — corrected the comment that invited the misreading. It claimed "Windows
   uses one SPS for both, so in practice this guard never fires"; that is false (measured
   on kiln 2026-08-19) and it is what made me read a load-bearing guard as dead code. Now
   records the measured firing, marks the guard load-bearing, and names this rejected
   design so the next reader sees the trap already sprung.
2. This design marked **REJECTED** with the evidence, so the fallback is not re-proposed a
   third time.
3. Task branch retired; no production code was written for the split.

## HALT: the design's premise contradicts a prior evidenced decision

The codec-correctness reviewer found that the load-bearing premise — main and aux are
independent H.264 sequences needing separate decoders — is contradicted by work already
in this repo. Verified both citations directly rather than trusting the reviewer:

`vendor/ironrdp-egfx/src/client.rs:915-917`, the doc comment on the very function this
design changes:

> Both sub-streams go through the SAME decoder sequentially — the Windows encoder
> produces a jointly-encoded, single-decoder-compatible pair (FreeRDP decodes it the
> same way).

`wrk_docs/2026.08.16 - HLD - AVC444v2 decode.md`, decision log item 2:

> One decoder instance, both sub-streams sequentially — FreeRDP-proven against Windows.
> A probe refutation attempt used independently-encoded streams (which do corrupt) but
> that is not what Windows emits; live acceptance 2b is the guard. **Fallback if ever
> needed: stream-index parameter, two sessions.**

So a previous agent considered this exact question, ran a refutation probe, concluded one
decoder was correct for what Windows actually emits, and named "two sessions" as the
fallback. That HLD carried external review. This design is that fallback, proposed
without re-establishing the trigger.

**Evidence on the new side is thin:** the `oscillating SPS/PPS` guard fired exactly once,
on kiln, 2026-08-19. That firing is genuinely hard to reconcile with "Windows uses one
SPS for both" (`src/h264.rs:713-714`) — the guard cannot fire unless the two views
presented divergent parameter sets. But n=1, and the `-12909` failures I cited alongside
it are attributed by MDR-BUG-FLUX-00008's own STILL OPEN section to a different mechanism
(reference loss across suppress/resume), which afflicts a single-view session just as
much and would be untouched by this change.

**Settleable with data, not argument.** `examples/avcreplay.rs` exists to replay captured
AVC444 payloads through the production pipeline, and `--capture-failures <dir>` collects
them from a live session. Capturing from kiln and checking whether the two views ever
carry divergent SPS/PPS decides it either way.

## Survivors worth folding regardless of that decision

- **Reverse the guard deletion.** The guard's *mechanism* is general anti-thrash (refuse a
  rebuild returning to the previous parameter set); only its *comment* attributes it to
  sub-streams. It has fired in production. Deleting it risks continuous mid-GOP rebuilds,
  which our own measurement says fail every frame until the next IDR — the permanent-black
  symptom 0.1.79 removed, re-entered by another door.
- **`examples/avcreplay.rs` feeds both sub-streams through one decoder.** Any split must
  update it or it silently stops mirroring production, while being the tool used for
  chroma-artifact investigation.
- **`advertised_capabilities` (`client.rs:1231`, `:1288-1291`)** takes one
  `Option<&dyn H264Decoder>` and would not compile against a pair; whose
  `supports_yuv420()` governs is unspecified.
- **`H264Decoder::reset()` is called nowhere in production today** — reset-on-surface-
  delete is net-new behaviour, not a mirrored precedent, and needs its own test.
- **Acceptance criterion 8 was not falsifiable**: FLUX-00008's second mechanism produces
  the identical `-12909`, and deleting the guard removes the one string that discriminates.
- **Factual error in my own doc:** the "Why" section put the guard in `client.rs`; it is
  `src/h264.rs:727`. The file-impact table had it right.
- `tools/latency-spike/viewer` is not a workspace member, so `cargo test` would not catch
  a break there — singular `hardware_decoder()` must stay.
- `src/main.rs:1632` is the native/rhydra path (single-stream RGBA `decode()`), correctly
  out of scope; my file-impact table should not have named it unqualified.
