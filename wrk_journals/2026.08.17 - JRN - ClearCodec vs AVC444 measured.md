# 2026.08.17 — ClearCodec vs AVC444, measured on temper with the new --no-avc flag

Question (Arthur): shouldn't ClearCodec be better, since it only sends the parts
of the screen that change? Answer: it sends fewer BYTES and vastly LATER frames.

First surprise: **temper now sends AVC444v2 by default** — the "temper sends
ClearCodec + RFX Progressive, not H.264" fact from the 2026.08.14 spike is stale
(the host's H.264 policy has since been enabled). CLAUDE.md updated. To measure
the non-AVC path at all, the client needed a way to withhold its AVC capability:
`--no-avc` (new flag, this branch). Verified live — with it, temper falls back to
ClearCodec + RFX Progressive and the bitmap cache goes from idle to 100% hit rate.

## The 2×2 on temper (same host, same scripts, same day, mdrdp 0.1.43 branch)

| workload | AVC444v2 | ClearCodec/RFX (--no-avc) |
|---|---|---|
| typing RTT p50 / p95 | 47.8 / 478 ms | **416 / 994 ms** |
| typing bytes in | 5.8 MB | **0.9 MB** |
| drag RTT p50 / p95 | 23.6 / **56.6** ms | 23.2 / 199 ms |
| drag bytes in | 7.8 MB | 6.7 MB |
| client decode p50 | ~2.5 ms | 0.1–0.8 ms |

Typing under ClearCodec shows frame gaps bursting at ~3 ms then stalling ~1 s
(p75 345 ms, p90 998 ms): the modern Windows non-AVC pipeline coalesces small
updates aggressively. The codec itself is fine — client decode is cheaper than
H.264 and the cache works — but the server starves the path of frames, so typed
characters appear ~9x later at the median. Drag medians tie, but the non-AVC
tail is 3.5x worse.

## Conclusions

1. The "only sends changes" intuition holds for H.264 too: skip-blocks + region
   maps mean an AVC typing frame costs ~KB. What ClearCodec wins is bytes (6x on
   typing) — relevant on constrained links, not this LAN.
2. Latency-wise AVC444 is the right default everywhere Windows offers it;
   `--no-avc` is a diagnostic lever (codec A/B, AVC-bug triage), not a mode to
   recommend.
3. temper is generally laggier than quench under AVC (typing p50 47.8 vs ~33 ms,
   p95 478 vs 87) — different hardware/encoder; temper also still has the default
   30 fps cap where quench now runs DWMFRAMEINTERVAL=15.

Caveats: one 75 s run per cell; temper on default frame cap; RTT is the client's
input→paint proxy. The typing delta (47.8 vs 416 ms) is far beyond run noise.
