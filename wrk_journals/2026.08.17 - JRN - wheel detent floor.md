# Wheel: slow-scroll fix, second attempt — the detent floor

Arthur reported the slow-wheel bug still live after 0.1.48's `WheelAccumulator`
(60e843b): scrolling the wheel slowly still moved nothing on the terminal server.

## Why accumulation alone was not the fix

The accumulator was correct arithmetic on the wrong model. macOS's scroll
acceleration reports a slowly-turned wheel click as ~0.1 of a *line*
(`MouseScrollDelta::LineDelta`), so pure accumulation charged ten physical
clicks per remote notch. The travel was no longer *dropped* — 0.1.48 fixed
that — but the exchange rate made slow scrolling read as dead. On a native
Windows box every click scrolls, however slowly the wheel turns; that is the
behaviour the hand expects.

## The fix (bb02e6e, 0.1.53)

`input::detent_floor` promotes a sub-line `LineDelta` axis to one whole line,
keeping its direction. Rationale:

- winit emits `LineDelta` only for non-precise devices, so each such event is a
  physical detent click — the user is owed a notch for it.
- Values ≥ 1 line pass through untouched: a fast spin keeps the acceleration
  curve, and its fractional part still accumulates in the `WheelAccumulator`.
- Precise pixel streams (trackpad, Magic Mouse) are unchanged: no click to
  honour, so sub-notch jitter still stays off the wire and slow drags still
  accumulate.
- Precedent: iTerm2 and Chromium apply the same one-line floor to non-precise
  scroll events, for the same macOS acceleration reason.

Accepted trade-off, documented on the function: a driver that splits one detent
into several sub-line events (some high-resolution wheels) will over-scroll.
That shape has not been seen from macOS, and a dead slow scroll is the worse
failure.

## Verification

524 tests green, clippy `-D warnings` clean, `check-windows.sh` clean. New
tests pin the floor (each 0.1-line click → exactly one notch, both axes and
directions) and pin that ≥1-line values are not floored; both were watched
failing under a mutated `detent_floor`. The accumulation/reversal/cap tests
moved to the pixel path, where accumulation still lives.

**Open:** live slow-wheel feel needs Arthur's hand on the real mouse against
the terminal server — unit tests cannot observe the macOS acceleration curve
itself. If slow scroll is *still* dead after this, the next hypothesis to test
is that his device delivers slow scroll as `PixelDelta` (Magic Mouse /
Logitech smooth-scroll driver), where the fix would instead be a lower
`PIXELS_PER_NOTCH` or a floor on the first event of a discrete gesture.

## A process burn worth remembering

While mutation-testing the fix I reverted the mutation with
`git checkout -- src/input.rs` *before* committing — which restored HEAD and
wiped the entire uncommitted fix along with the mutation. Re-applied from
context, no loss, but: commit first, mutate second, revert the mutation by
inverse edit.
