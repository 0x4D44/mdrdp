# 2026.08.18 — quench "DWM wedge" post-mortem, reboot, disconnect-message verification

## The verdict first

The afternoon's "DWM stopped composing the IDD virtual display" was **not a host
fault**. It was three rig errors stacked on top of each other, each of which produced
the same symptom — zero frame records — and each of which was misread as capture
death. Quench was rebooted anyway (Arthur's call, and it bought real findings), and
the full IDD+diff capture path is verified working: 60/60 posted keystrokes captured,
keystroke→capture p50 18.0 ms.

## The three rig errors

1. **A viewer-less spike-server records nothing, by design.** The capture loop parks
   in 50 ms sleeps until a client connects
   (`tools/latency-spike/server/src/win/pipeline.rs:609`). Every "smoke" that ran the
   server task and counted frame records without connecting a client measured the
   design, not the host. This is what made a healthy host look dead all afternoon.
   A headless drain is enough to arm it: `ssh -L 9500:… ` plus `nc -d 127.0.0.1 9500
   > /dev/null` (the `-d` matters — nc closes the socket on stdin EOF without it,
   and the server disarms the moment the client drops).
2. **Scheduled tasks cannot take foreground.** `SetForegroundWindow` from a schtasks
   context is refused by the foreground lock, so `type-stamped.ps1`'s SendKeys went
   to whatever had focus — never the console parked on the virtual display. The
   display stayed static, and a static display legitimately produces no frames. The
   script now posts `WM_CHAR` straight to the recorded hwnd (`PostMessage` needs no
   focus); the prep script's window-park still works because `SetWindowPos` is not
   focus-gated.
3. **`schtasks /end` orphans the server.** It kills the task's `cmd` wrapper, not the
   `spike-server-inc3.exe` child, which keeps ports 9500/9501 and poisons the next
   run with `os error 10048`. Stop the server with
   `taskkill /im spike-server-inc3.exe /f`.

Contributing confusion: my frame count grepped `"record":"frame"` only, so a run
whose updates all went down the Increment 3 rect path (`"record":"rects"`) counted
as zero.

## The real product finding: the IDD device is not boot-persistent

The device exists only while `mdrdp-idd-create.exe --wait` runs. A reboot kills the
creator and the device vanishes — `pnputil` shows no trace, and everything downstream
(display attach, section, capture) is gone. Quench now has an elevated task
`mdrdp-idd-create` that recreates it; `mdrdp deploy` in the ownership HLD must
install this as a boot/logon task, and the health ladder's "cycle device" step should
check the creator process first.

Also learnt while recovering: after a reboot nobody is logged on, and the
interactive-session rig needs ano at the console. The working recovery is: RDP in
with mdrdp (creates the session), then an elevated `tscon <id> /dest:console` moves
it to the console and the rig is back. The tscon kick arrives at the client as
ERRINFO "Another user connected …" — a second live datapoint for the epilogue
dialog.

## Disconnect-message verification (the reason for the reboot order)

With an mdrdp session attached, the reboot exercised the recently-fixed ERRINFO path
end-to-end against a real host for the first time:

```
server ended the session: [Protocol independent error] The remote server is busy rebooting
session ended: ServerEnded(ServerFarewell { headline: "is restarting",
  detail: "The host is rebooting. It will take connections again once it is back." })
```

Quench really does send ERRINFO 0x1A on reboot — the code that used to fail the
whole PDU decode — and it now flows to the right dialog text. The `tscon` kick also
proved the fallback arm ("Another user connected…", shown verbatim). One cosmetic
niggle for the scratchpad: the fallback arm's detail leads with the raw
"[Protocol independent error]" prefix, which reads rough in a user-facing dialog.

## First lean-app host-floor datapoint (preliminary)

The recovery smoke doubled as the conhost floor run: 60 `WM_CHAR` posts at 180 ms
gaps into a classic console parked on the IDD display at 240 Hz (min present gap
4.2 ms confirms the mode), server capturing with a drain client attached.

- **keystroke→first capture event: n=60, min 6.6, p50 18.0, p90 25.3, p95 25.9,
  max 26.7 ms, zero misses.**
- Reference: Windows 11 Notepad measured 25.8 ms p50 (SendInput injection, earlier
  runs).

So the host floor does *not* collapse for a lean app: conhost saves ~8 ms of
Notepad's XAML pipeline but still pays ~18 ms median, with a 6.6–26.7 spread that
looks like uniform phase against a ~60 fps repaint throttle (conhost's renderer),
not against DWM (which composes 240 Hz here). Caveats: single run, n=60,
`PostMessage` injection bypasses the input queue (~1–2 ms flattering vs SendInput),
and the observation point is capture-side acquire, not DWM present. A tighter
decomposition needs an app that presents immediately on input — a custom D3D pad —
which is a later experiment. For now the working conclusion shifts: the ~26 ms
Notepad floor is roughly (app repaint cadence ~18 ms) + (XAML pipeline ~8 ms), and
no server-side work of ours can touch either term.
