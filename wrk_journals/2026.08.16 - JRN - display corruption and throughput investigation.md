# 2026.08.16 — JRN — display corruption and throughput investigation

Task: reproduce the display corruption Arthur reported (resolution changes and window
open/close leave fragments), find the cause, fix it. Follow-ups queued behind it:
rendering-performance review and an audio/video (YouTube) exercise.

All live work against quench (`ano`/`ano` throwaway account), scripted with osascript
drivers and full-screen `screencapture` verification. Release builds only.

## Reproduction

Trivially reproducible, as promised. A scripted session (connect 1920x1080 windowed →
open/close Explorer → Ctrl+Alt+Enter to 5120x2880 → back) produced:

- Mis-scaled stale fragments after each resolution change: 1x-scale windows floating in
  the 5K frame; 2x-scale window chrome, giant text and misplaced wallpaper chunks in the
  1080p frame after returning. The session's own `--screenshot` buffer holds them, so it
  is composition, not presentation.
- The session ran at ~0.6–2 fps with input-to-paint latency 1.2–3.6 s on a 3.3 ms LAN,
  and repaints froze partway (the corruption then persisted indefinitely).
- Zero decode errors, zero surface errors, zero undecoded regions, 100% cache hits —
  the counters said healthy while the screen said broken.

## Diagnosis

Instrument first: `MDRDP_LOG=<filter>` now installs a global stderr tracing subscriber
(main.rs), making the vendored EGFX client's frame-level tracing visible. That produced
a timestamped frame timeline correlated against a timestamped keystroke driver.

**Finding 1 — the server was throttling us.** Server frame ids SKIPPED (10→12, 18→24,
56→61…) and after every burst the server went silent for 13–33 s, leaving repaints
incomplete. Every received frame was acked instantly, so it wasn't ack latency.
`ironrdp_session=debug` showed the real cause: quench sends **Bandwidth Measure
Start/Stop probes continuously — 140 pairs in a 40 s session** — and ironrdp-session
0.11 logs each one "not yet implemented" and drops it. A Windows server that never
receives Bandwidth Measure Results keeps re-probing and throttles/skips EGFX frames.
This is also a direct mechanism for product requirement 3 ("latency degrades the longer
a session runs") and 5 (performance).

Fix: vendored `ironrdp-session` and implemented the responses, mirroring FreeRDP
(`autodetect.c` + the byte counting in `rdp_recv_tpkt_pdu`): Start arms a timer and
counts every inbound frame's bytes (ActiveStage::process feeds each frame length in,
covering fast-path); Stop answers with elapsed ms + byte count (response type 0x0003
for a 0x002B connect-time stop, 0x000B otherwise); a Stop with no Start answers zeros.
Unit tests in the vendored crate, each proven-red first. Live effect: the post-resize
repaint went from stopping at 3 frames + 33 s of silence to running to completion
(18 frames, sub-second), and responses carry real numbers (44 555 bytes / 7 ms).

**Finding 2 — codec state dies with the surface, never with the reset.** With pacing
fixed the fragments persisted in one run, still with zero errors. The reference:
sdl-freerdp 3.27.1 with /dynamic-resolution against the same host stays clean across
resizes, so the divergence is ours. First hypothesis — mirror FreeRDP's
`freerdp_client_codecs_reset` and restart both decoders at ResetGraphics — was **half
wrong, and the live A/B caught it**: the very next repaint after a reset failed 74
ClearCodec decodes with "V-bar cache miss on hit" (black holes on screen). Windows
keeps referencing V-bars cached before the reset, so the decoder must keep them.

What survived the experiment: `on_surface_deleted` drops that surface's progressive
tile state (FreeRDP: `progressive_delete_surface_context`), closing the same-id
same-dimensions recreate hole (dimension changes already rebuild the grid inside the
decoder). Surfaces, the EGFX bitmap cache, and the ClearCodec caches all persist
across a reset. Vendored ironrdp-graphics gained a `context_count()` test accessor;
all new tests proven-red first.

With both fixes the full choreography (open/close Explorer, 1080p → 5K → back) ends
with zero decode/surface errors and a fragment-free final session buffer, matching
FreeRDP. Honest caveat on attribution: run-to-run variance was real during diagnosis;
the clean result was confirmed on a repeat run, but the fragment mechanism is best
described as "stalled repaints (finding 1) leaving the DPI-transition's mixed-scale
intermediate on screen, plus stale progressive state on same-dims surface recreates" —
not a single smoking gun.

## Environment notes for future scripted GUI runs

- The Mac's display sleeps during long unattended runs; a slept display (or a different
  active Space — another agent runs a fullscreen RDP session on this machine) silently
  eats osascript keystrokes. Hold the display awake (`caffeinate -dimsu`) and verify
  `frontmost of process "mdrdp"` before every keystroke; abort on focus failure.
- `deltic timeout` swallows stdin — invoke the binary directly for `--password-stdin`.
