# 2026.08.17 — Frame cadence measured; Windows App transport ruled out

Follow-up to the 2026.08.16 profiling journal. Two questions were open: what
sets the server's ~15 fps-while-typing cadence, and whether the reference
client's latency rides RDP-UDP.

## Transport: Windows App uses plain TCP here

Checked live against Arthur's Windows App 11.3.8 session to temper
(192.0.2.171): `lsof` shows exactly one established TCP connection to
:3389 and **no UDP sockets at all**, re-verified minutes apart. Any latency
advantage the reference client has on this LAN is pacing/ack/decode
behaviour, not transport. (Caveat: observed against temper; quench could in
principle differ, but both are default-firewall Windows hosts.)

## Cadence: a ~60 Hz encoder tick sustaining only ~30 fps

New `frame_gap` metric (inter-paint wall gap, raw 512-sample window now
exported in the metrics JSON) against quench, 1920x1080 AVC444v2:

- **Typing**: gaps quantize at multiples of ~16 ms (modes at 8–16, 24–32,
  40–56, 80–88, 96–104 ms). No fixed 66 ms cadence — frames follow
  keystrokes on a ~16 ms tick grid. RTT p50 33.0 ms, consistent with
  yesterday.
- **Continuous drag**: p50 gap **31.8 ms** (p25–p75: 30.7–32.7) with a
  secondary 8–16 ms burst mode. Sustained rate ~30 fps; the tick itself is
  ~60 Hz capable.

Reading: the classic remote-session frame-rate cap (~30 fps), not an
encode-speed limit. The host knob to test is
`HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\DWMFRAMEINTERVAL`
(DWORD 15 → ~60 fps ceiling; applies to NEW connections). Needs admin on
quench. Prediction if applied: drag p50 gap halves to ~16 ms; typing RTT
improves modestly (tick alignment), several ms not tens.

Experiment protocol when access is available: one knob at a time, reconnect,
same `interactive.script`/`heavypaint.script`, compare `frame_gap`
distribution and RTT p50/p95 before/after.
