# 2026.08.16 — Fullscreen, dynamic resolution, default user, title diagnostics

Seven feature requests from Arthur, built in one task branch. Decisions and surprises.

## What landed

1. **Full-window drag** (`src/connect.rs`): IronRDP's `PerformanceFlags::default()` sets
   `DISABLE_FULLWINDOWDRAG`, so remote window drags showed outlines. We now send an
   explicit set: drag contents on, menu animations off, font smoothing on.
2. **Default account** (`src/favourites.rs`, `src/main.rs`): a `[defaults]` table in
   `favourites.toml` supplies the username for `mdrdp <host>`. Precedence: `--user` flag >
   favourite > default.
3. **Fullscreen hotkey** (`src/window.rs`): Ctrl+Alt+Enter, echoing mstsc's
   Ctrl+Alt+Break (no Break key on Mac keyboards). Claimed locally, never forwarded.
4. **Fullscreen memory** (`src/state.rs`): `state.toml` next to `favourites.toml`, keyed
   `host:port`. Remembered state beats the favourite's window mode; `--size` forces
   windowed; new `--fullscreen` flag forces the opposite. Written from the window's exit
   hook because the Cmd+Q path never returns from `run_app`.
5. **Title diagnostics** (`src/window.rs::title_line`): resolution, latency p50 with
   drift, fps, inbound Mb/s, cache hit rate, STALE count. Refreshed at most 1/s, driven
   by damage, so an idle session's title (correctly) freezes.
6. **Dynamic resolution on fullscreen** (`src/session.rs`, `src/connect.rs`):
   - Display Control DVC (MS-RDPEDISP) joined via the `ironrdp` meta-crate's
     `displaycontrol` feature — no new dependency line; it was already in the lock file.
   - The window sends `SessionCommand::Resize` on user-initiated fullscreen transitions
     (hotkey, startup restore, OS green button). Entering fullscreen requests the
     monitor's native pixels plus its scale factor; leaving requests the windowed size at
     100%.
   - The session finally handles `ActiveStageOutput::DeactivateAll`: the vendored
     connector exposes `ConnectionResult::activation_factory`, and
     `drive_reactivation` runs the Deactivation-Reactivation sequence by hand
     (`read_by_hint`/`step`, 15 s deadline), then swaps in a fresh fast-path processor
     (share ID can change; channel IDs cannot; bulk compression is never negotiated so
     `bulk_decompressor: None` is faithful) and rebuilds the `DecodedImage`.
   - A resize request retries every pump slice until the DVC opens, and gives up after
     10 s on servers that never open it — graceful degradation is the old letterboxing.
7. **Rendering-glitch review**: code inspection found no smoking gun — every drop path
   in `gfx.rs`/`surface.rs` is counted, overlapping same-surface copies are extract-first,
   NSCodec subcodec is now implemented in the vendored graphics crate. The remaining
   documented gap (progressive decoder ignores `ProgressiveRegion.rects`) over-paints
   whole tiles but with fully reconstructed content, so it should not by itself leave
   fragments. Diagnosis needs a live repro with the counters watched — procedure below.

## Design notes

- The geometry policy is deliberately starved while fullscreen: fullscreen geometry
  belongs to the OS, and feeding the policy monitor-sized `Resized` events would teach it
  the wrong "desired" size. The windowed desired size survives fullscreen untouched.
- CLAUDE.md's "dynamic resize is opt-in and only fires on a user-initiated resize" is
  honoured: the *only* trigger for a resolution renegotiation is a fullscreen transition
  the user caused. Display-configuration changes still never touch the session.
- `Channels.display_control` defaults to false so probe paths keep measuring the channel
  set they always measured; only the interactive client sets it.

## Live validation (quench, Windows 11, user `ano`; plus one windowed run on temper)

The first fullscreen run failed usefully: the monitor layout went out immediately after
the channel opened and the session stayed at 1920x1080. **Windows silently drops a
DISPLAYCONTROL_MONITOR_LAYOUT sent before the server's capabilities PDU** — channel-open
and capabilities-received are different states, and `ActiveStage::encode_resize` only
checks the former. Gating on `DisplayControlClient::ready()` (as upstream does; their
`display_control_ready()` helper is newer than our pinned ironrdp-session) fixed it.

With the gate in place, all screenshot-verified against quench (5K Studio-class display):

- `--fullscreen`: session renegotiated to **5120x2880** (scale 200 advertised), zero
  decode/surface errors, graceful close. The resize completed via **EGFX ResetGraphics +
  new surface**, not DeactivateAll — so the reactivation path is written and unit-shaped
  but remains live-unexercised; servers may choose either per MS-RDPEDISP.
- Plain `mdrdp quench` afterwards: opened fullscreen from the remembered state and
  auto-negotiated 5K — the restore path works end to end.
- `--size 1920x1080`: stayed windowed at the stated resolution (flags win), and the
  state file flipped to `fullscreen = false` on close.
- Windowed run against temper: unchanged behaviour, graceful, zero errors.

## Open

- **Glitch repro procedure** (needs a human driving the desktop): run
  `mdrdp quench --capture-failures <dir>`, open/close the start menu until fragments
  appear, then read the exit stats — `decode failures by reason`, `undecoded regions`,
  `surface failures by reason`, and the bitmap-cache line. Every stale-pixel path in this
  client is counted, so whichever counter moves names the faulty path; if none moves, the
  staleness is server-side damage reporting and needs a FreeRDP comparison capture.
  The `ano`/quench test account makes iterating on this cheap now.
- **Interactive hotkey toggle** (Ctrl+Alt+Enter both directions, green-button path) is
  unit-tested but not yet exercised by a human hand.
- **Windows cross-check is broken on this machine** (pre-existing): `cargo check --target
  x86_64-pc-windows-msvc` now fails compiling `ring`/`libz-sys` C sources — `cc` can no
  longer cross-compile for the msvc target. Trunk fails identically, so it is
  environmental, not this branch. The 2026-08-14 "verified clean" note no longer
  reproduces.
