## Design decisions at build start

- **Derive from Microsoft IddSampleDriver** (MIT,
  microsoft/Windows-driver-samples@717778a2), per the HLD. The sample is 809
  lines and structurally complete: WDF plumbing, IddCx adapter/monitor
  lifecycle, and a swapchain processor thread.
- **One EDID-less monitor.** The sample fully supports EDID-less monitors via
  `MonitorGetDefaultModes` + `QueryTargetModes` — both driver-controlled — so
  240 Hz needs no EDID authoring at all. Modes: 1920x1080@240 (preferred),
  @120, @60; target modes add 2560x1440@{120,60}.
- **IddCx 1.6 headers, minimum-required 1.4** (the sample's own pairing);
  UMDF 2.25; `UmdfExtensions = IddCx0102` (the extension contract id, not a
  header version).
- **WPP tracing stripped**; instead a per-600-frames cadence line via
  `OutputDebugStringW` — enough to verify 240 Hz swapchain delivery with
  DebugView and nothing else.
- **Swapchain loop stays the sample's acquire-and-release null consumer.**
  DDA measures against the virtual display for stage 2; the IddCx
  swapchain-as-capture-path comparison is a later increment on this base.
- **Cross-build from macOS** rather than provisioning MSVC+WDK on quench:
  Apple clang's `--driver-mode=cl -target x86_64-pc-windows-msvc` emits valid
  amd64 COFF (verified), rustup's `rust-lld -flavor link` is lld-link, the
  repo's xwin splat provides CRT+SDK 10.0.26100, and the WDK arrives as a
  plain NuGet zip (Microsoft.Windows.WDK.x64 10.0.26100.6584, ~110 MB,
  splatted to `~/.xwin/wdk`) — it even contains `Inf2Cat.exe` for the
  quench-side packaging step. Zero toolchain installs on either machine.
- Driver derivation + build-script grind delegated to an Opus worker against
  a fixed contract; lead owns review, the deploy runbook decisions, and the
  quench deployment (parked until attended).

## Evening session: deployment and first measurements (2026-08-17, ~18:00-20:30)

Everything from driver install to the stage-2 numbers ran over SSH from this
Mac. What happened, in order, with the surprises called out:

- **OpenSSH enabled on quench** (Arthur, elevated). Windows `sudo` was in
  Force-New-Window mode and cannot run PowerShell cmdlets directly
  (`sudo Add-WindowsCapability` → "Command not found"; wrap in
  `sudo powershell -Command "..."`); the capability install also does not
  create a working firewall rule on this box — the service ran but port 22
  stayed closed until an explicit `New-NetFirewallRule` allow for 22/tcp.
  SSH sessions as ano arrive **fully elevated** (High integrity,
  BUILTIN\Administrators enabled) because Windows sshd does not UAC-filter
  admin tokens — so the whole deployment needed no console access.
- **Secure Boot blocks `bcdedit /set testsigning on`** — `deploy.ps1 -Phase
  pre` failed. It turned out not to matter: a UMDF driver package installs on
  **cert trust alone** (self-signed cert in machine Root + TrustedPublisher,
  Inf2Cat → signtool → pnputil). Installed as oem171.inf, no testsigning, no
  reboot, Secure Boot untouched. `install-notest.ps1` (the -Phase install
  steps minus the testsigning gate) is the actual runbook now.
- signtool is NOT in the WDK NuGet — it ships in
  `Microsoft.Windows.SDK.BuildTools` (10.0.26100.4948 used), fetched the same
  NuGet-unzip way.
- **The driver works exactly as designed**: device `SWD\mdrdp_idd\mdrdp_idd`
  started, EDID-less monitor arrived, mode list offers 1920x1080 at
  60/120/240 Hz, and `ChangeDisplaySettingsEx` to 240 Hz succeeded
  (verified via Win32_VideoController). Windows initially picks 60 Hz, not
  the driver's preferred mode — the mode set has to be explicit.
- **Session plumbing is the real deployment lesson.** SSH lands in a
  non-interactive session where user32 display APIs see nothing and DXGI
  duplication cannot run. The working pattern: `tscon 3 /dest:console` to
  put ano's disconnected session on the physical console (unlocked), then
  run every display-facing process via a **scheduled task with
  LogonType Interactive** so it executes inside that console session.
  Also: PowerShell `$null` marshals wrongly as the first argument of
  `EnumDisplayDevices` — `[NullString]::Value` is required, or the API
  returns nothing.
- **spike-server's first-ever Windows execution worked**: Quick Sync async
  hardware MFT selected, both listeners up, DXGI enumeration of both
  outputs (0 = physical DISPLAY1, 1 = virtual DISPLAY5), full pipeline
  streamed to the Mac viewer on the second attempt. The first attempt
  failed instructively: an `nc -z` port probe had counted as the first
  video client, consumed the opening IDR, and the real viewer then joined
  mid-GOP undecodable (`sequence_header_available:false` — Quick Sync
  exposes no out-of-band sequence header, so a mid-GOP joiner cannot be
  rescued). **Fix queued: force an IDR on every new video client connect.**
  Until then: never port-probe the video listener; restart the server per
  client session.
- Windows 11 Notepad re-launches itself, so `Start-Process notepad
  -PassThru` returns a pid that never owns a window — find the notepad
  process with `MainWindowHandle -ne 0` instead.
- **macOS side gotcha**: SCK enumerates ZERO displays (silently, preflight
  passing) when the external display is asleep — looks exactly like a TCC
  denial. `caffeinate -u` before runs; the probe's own wakelock only covers
  the run itself.

### Decomposition (stage 2, `tools/latency-spike/analysis/decompose.py`)

p50 medians, all 100 trials, stages sum ~56 vs measured 54.3:
input+render+composite residual **31.7** | present→acquire **7.5** |
convert 0.2 | encode **5.3** | send 0.1 | decode **5.9** | present **5.4** |
detect quantization -0.2.

Reading: 58% of the latency is the pre-pixel floor (input delivery + target
app render + DWM) common to every remote-display architecture — which is why
the spike and full RDP tie at ~55 ms p50. The pipeline we own costs ~24 ms.
The differentiator is the tail: 240 Hz IDD gave p95 70 / max 81 / zero
timeouts.
