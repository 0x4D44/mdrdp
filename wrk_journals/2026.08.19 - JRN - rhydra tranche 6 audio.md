# 2026.08.19 — JRN — rhydra tranche 6 (audio)

Parked in the understand phase, before any HLD, on a host fact.

## What happened

The tranche's first question was the cheap decisive one: can rhydra capture what
quench is playing? WASAPI loopback attaches to the default **render** endpoint, and
a headless box may not have one.

quench does not. Six render endpoints, all not-present or unplugged, zero active,
`GetDefaultAudioEndpoint` returning `0x80070490`. Full detail and the four options
in `wrk_docs/2026.08.19 - PARK - tranche 6 audio needs a render endpoint on the
host.md`.

## Why it is worth a document rather than a line

Every cheap check said the host was fine. `Win32_SoundDevice` reports the Realtek
adapter with `Status: OK`; `Audiosrv` and `AudioEndpointBuilder` are both Running.
The registry's `MMDevices\Audio\Render` states were the first hint something was
wrong, and even those needed decoding — `0x20000004` and `0x8` are not-present and
unplugged, not variations on "present". Only WASAPI answers the question directly.

Had I taken the WMI answer, the tranche would have been designed, built and
half-validated before the silence turned up, and the natural reading of silence in
an audio feature is a bug in the code you just wrote.

## The judgement call

I did not build the portable half — the priority sender, the wire message, the Mac
playback path — even though it compiles and tests without a host. Two reasons.
Half a feature that cannot be validated end to end is a checkpoint, not a delivery.
And the capture side's real behaviour (mix format, buffer period, how it reports
silence) is exactly what should shape the wire format and the jitter policy; deriving
those from an assumption I cannot test is how a wire format ends up needing a break.

The design work is not lost — the four banked decisions (PCM16 over Opus, the FIFO
that must not reuse `Slot`, the ssh-tunnel caveat on priority separation, clock
drift as the soak risk) are written down in the park document.

## One thing the park document changes regardless of Arthur's answer

Whatever provides the endpoint, the health ladder should report its absence. Audio
that is silently unavailable is requirement 4 (no visibility) in miniature: the user
cannot tell a missing endpoint from a broken feature. That rung is worth adding even
under the descope option.

## Unparked the same night, and built

Arthur's call: build sound first, then the overnight run. The park stands on its
facts — neither host has a render endpoint — but the transport above the capture
stage does not depend on that, so it was built.

### What the reviews changed

Two adversarial reviewers, and they converged independently on the two worst
faults, which is the strongest signal a review can give:

1. **No timing reference on the wire.** With rate and channels only, and silence
   elided, the client cannot tell a 30 ppm clock from 800 ms of elided silence
   from dropped frames — all three present as a change in ring depth, which is
   what both correction mechanisms key off. Added `capture_pos`, a u64 that
   advances across elided silence. Eight bytes now instead of a wire break later.
2. **Strict priority starves the clipboard.** Audio is continuous, so under the
   back-pressure the FIFO exists to survive, audio is always pending and the
   clipboard is never selected — in exactly the window where the user is working.
   Requirement 1 is that the clipboard never wedges. Replaced with a bounded
   drain: audio first, at most 8 frames (80 ms) before a waiting clipboard goes.

They also found two flat factual errors in revision 1 of the HLD, both of which I
verified against the code before acting: "almost free" (the native path calls
`ring.disable()`, which latches, so every push was discarded) and "the missing
half is over-fill" (over-fill was already handled; the real gap is a high-water
mark below the 400 ms ceiling).

And they found that my acceptance criteria were largely theatre: AC1, AC4 and AC5
all passed with the WASAPI capture path entirely absent. I wrote three tests that
could not fail.

### The two-tone probe

The design specified a 440 Hz sine. That is close to useless: a rate error turns a
pure sine into a slightly different pure sine, and a channel swap turns it into
itself. It is now **440 Hz left, 660 Hz right**, which falsifies channel swap,
mono-downmix, one-channel dropout and gross rate error in one measurement — and
there is a test that swaps the ears and confirms the check itself fails.

### What the live run found

AC1 passed first time on the signal and failed on the timing:

```
native: audio frames 1882  underruns 1588      <- correct audio, wrong pacing
native: audio tone left 440 Hz  right 660 Hz
```

The host generated a block and then slept a whole block, so every period was 10 ms
**plus** generation time: the source ran permanently slower than real time and the
ring could never fill. 1588 underrun episodes in 19 s on a link dropping nothing.
Paced against a deadline instead:

```
native: audio frames 2502  underruns 16
native: audio tone left 440 Hz  right 660 Hz
```

99% fewer underruns, same signal, 100.1 frames/sec. **This is the argument for
live validation in one screenful:** every unit test passed before and after, and
none of them could see it.

### Mutation passes, and three vacuous tests

Every new test made to fail once — 36 mutations across four units, all red. The
pass caught three tests that were green and proved nothing:

- `putting_audio_after_close` — the close path clears the queue anyway, so it
  passed whether or not the guard existed.
- `silence_has_no_peak_frequency` — exact zeros score zero in every bin, so a
  second guard caught it and the energy guard was never exercised. Real silence is
  never exactly zero.
- an existing reader test used `framing::encode(0x21, …)` as its "unknown type"
  fixture. 0x21 is `MSG_AUDIO` now, so it would have kept passing against an
  entirely different property.

### Incidental, and reassuring

The host log shows the **old** server meeting the new `MSG_AUDIO_CONTROL` and
logging `unknown-type 1` while carrying on normally. The framing skips an unknown
type safely in both directions, which is exactly what the tranche-5 amendment set
out to guarantee and had not until now been demonstrated against a real older peer.

### Deployment gotcha worth recording

`mdrdp deploy` refuses without the IDD artifacts, which are not built in this
worktree, so the binaries went over by hand — and the first copy went to
`C:\mdrdp\` while the agent actually runs from `C:\mdrdp\v0.5.0\`. Twenty minutes
were spent reading a `server.log` last written the previous day. **Check the log's
timestamp before believing it**, and check `Get-Process | Select Path` before
believing a deployment landed.
