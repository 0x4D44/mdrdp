## The review pass changed the design, and that is the story so far

Three adversarial reviewers ran against the first draft. The draft was wrong in
its central decision, and the correction is worth stating plainly because
everything else follows from it.

The draft claimed only the **client** could see the wedge — "the agent cannot
see the client's input channel and, with no viewer, has nothing to measure".
Both halves are false against the driver source, and I verified the citations
myself rather than taking them on trust:

- `idd_section.rs:65` — `SECTION_NAME` is a fixed well-known name any process
  may open read-only.
- `idd_section.rs:137` — the header carries `generation`, and
  `SharedPool.cpp:223,249` (`AdvertiseNoPool`) writes 0 on teardown.
- `idd_section.rs:184` — slots carry `frame_seq`, **the driver's** presented-
  frame counter, advanced as the compositor presents, with no viewer and no
  capture server needed.

So the agent can answer "is there a pool, and are pixels moving on it?" every
tick for one mapped read. Detection moved agent-side; the client corroborates
and triggers nothing. That single change dissolved the multi-client problem,
the "escalate once" enforcement problem, and `--doctor`'s "untested" answer.

The draft's one automatic remediation is also gone. Traced through the code: a
running server at generation 0 loops on timeout forever, and a *fresh* one
refuses generation 0 and dies after 30 s into backoff — so restarting the
server would have converted a silent wedge into a crash loop **and** killed the
session that detected it (the server is single-viewer,
`win/send.rs:89-92`, verified). Remediation is now cause-specific, and nothing
above rung 4 acts automatically, which is what the parent HLD specified anyway.

Two ACs were replaced outright as traps: the lock/unlock test had no proven
unlock (`tscon` is evidenced for a *disconnected* session, not a locked attached
one, and every fallback is forbidden or triggers the other incident), and the
stranding test had a needlessly destructive inducer. A reviewer found the
cheaper one: **`mdrdp-cycle-idd` alone**, which destroys the section while the
running server holds its old attachment — the stranded-server observable in one
step, no RDP logon, no console kick.

**§4's root-cause claim was withdrawn.** The draft asserted why
`device_replaced` did not fire in Incident A; the record contradicts it (the
display *was* renumbered, which is exactly what that guard keys on). The
post-mortem is recorded as open and the design deliberately does not depend on
it — the `pool` rung detects the condition however it arose.

### What unit 1 deliberately did NOT do

`stuck` is **not** yet derived from the rungs. The pool rung reports `Unknown`
until its sampler lands, and `Unknown` is not-ok for a bring-up rung — routing
that through the derivation today would make every host read as stuck on a rung
this build cannot sample, and `stuck` gates the native connect. The derivation
is written and tested; it gets wired when every bring-up rung has a real
sampler.

`CycleDevice` verifies its challenge and then refuses with "not implemented in
this build". Refusing loudly beats pretending: a caller must never be told a
destructive op succeeded when nothing happened.

### Three test flaws the make-it-fail discipline caught

Worth recording, because two of these tests would have shipped proving nothing:

- The ladder-**order** test passed against an implementation that simply trusted
  the order the agent sent, because its fixture was already in ladder order and
  therefore agreed with both. Now the fixture is built deliberately out of
  order.
- The bring-up-**coverage** test derived its expectation from `Rung::ALL`, the
  constant under test. Dropping a rung from `ALL` left it green — it just
  stopped checking that rung. Now it asserts against a longhand list.
- `stuck_from_rungs` treated a **missing** bring-up rung as ok, so a partial
  report manufactured health — the exact failure class this tranche exists to
  stop. Absence now counts as not-ok, with its own test.

### The one design question the plan did not anticipate

Wiring `stuck` to the rungs looked mechanical and was not. `stuck` feeds `green`,
`green` gates the client's connect — so the obvious derivation ("first rung that
is not Ok") would make an `Unknown` rung refuse a session. A section merely
mid-write on the tick a client probes would turn away a host that works.

The rule I had been applying all tranche is "ignorance must not read as health".
The flip side needed stating too: **in a gate, ignorance must not read as
failure either**. Both errors cost real sessions, in opposite directions. Hence
two functions: `stuck_from_rungs` keys on `Fail` alone and answers "may a client
connect?"; `first_unsatisfied_rung` counts Unknown and absent, and answers "what
should a human look at?".

### What the live runs settled

The `liveness` rung never reports `Fail`, and quench is why: its idle desktop
leaves `frame_seq` static for minutes, so any check calling that a fault would
fire constantly on a healthy host. The wedge is named by `pool`, which has a
structural fact to point at. That is not timidity — it is the difference between
a diagnostic people trust and one they learn to ignore.

AC2 is the tranche justifying itself: the exact failure that cost hours by hand
yesterday was detected, correctly diagnosed, and **recovered automatically in
~16 seconds**, using an inducer (`mdrdp-cycle-idd` alone) that a reviewer found
and that costs the rig nothing.

### Five tests the make-it-fail pass caught proving nothing

Worth recording as a rate, not a list of one-offs. Across this tranche:

1. Ladder-order — fixture already in ladder order, so it agreed with both a
   correct implementation and one that trusted input order.
2. Bring-up coverage — derived its expectation from `Rung::ALL`, the constant
   under test; dropping a rung left it green because it stopped checking it.
3. Pool debounce — loop count derived from `POOL_FAULT_TICKS`, so shrinking the
   constant to 1 made the loop run zero times and the test vacuous.
4. Cycle idempotence — exercised the device-gone path, where restarting the
   clock changes nothing observable.
5. Liveness "only while" — name claimed a direction the test never checked;
   renamed rather than padded.

All five looked reasonable on the page. The common shape is a test whose oracle
is derived from, or coincides with, the thing under test.
