# 2026.08.18 — JRN — Black screen on reveal: suppress resume needs Refresh Rect

## The report

Arthur: mdrdp connected to kiln shows a permanently black screen; connection is up;
`mdrdp -S` shows 1 error. Never seen before the idle-suppression feature (v0.1.65,
MDR-BUG-FLUX-00005) landed.

## The diagnosis trail

- `mdrdp -S`: kiln 80 frames / 3.2 MB in 31 minutes vs crucible's 8,362. Input RTT
  healthy at 30 ms. So the transport was fine and the server was simply not sending
  graphics.
- Session log: first display line after connect is "window hidden; asked the server to
  suppress updates" — the window connected occluded (launched from the favourites
  launcher while Arthur worked on another Space). Nine hidden/visible cycles follow,
  each reveal sending the resume PDU.
- Live experiment on the running session: brought the window forward, held it revealed
  12 s — resume PDU sent, **zero** new frames arrived. Meanwhile temper and crucible
  (same binary, same code) streamed thousands of frames when revealed — their desktops
  change constantly (fleet agents), kiln's is static.
- The "1 error" was a red herring: one isolated AVC decode failure, incidental.

## The root cause

MS-RDPBCGR 2.2.11.3's AllowDisplayUpdates does **not** make Windows repaint under the
EGFX pipeline — the server resumes forwarding only *future* changes. Everything that
changed while suppressed is simply never sent. Kiln's session connected during logon
(the 80 frames were the logon black screen), was suppressed before the desktop
appeared, and the desktop then sat still — so the client's stored image stayed black
forever, faithfully presented at every reveal. The fix commit's assumption that the
desktop rect "doubles as a full-repaint request" was wrong against real Windows.

## The fix

`session::visibility_pdus`: the reveal now sends an explicit Refresh Rect PDU
(MS-RDPBCGR 2.2.11.2) for the full inclusive desktop immediately after the allow.
Hiding still sends the bare suppress. Commit f47e3fa; bug MDR-BUG-FLUX-00006.

## Validation

Live against quench (AVC444v2, EGFX): the validation session itself connected
occluded (suppress at 9 frames), and on reveal the new path produced a 17-frame
repaint burst on an idle desktop within a second. The pre-fix binary on kiln produced
0 frames over a 12 s reveal. The quench session was then ended server-side ("user
logging off his or her session") ~40 s in — quench rig behaviour, unrelated.

## Loose ends

  The favourite's default account (user@example.com) connects fine, so the
  host and RDP stack are healthy — the `ano` credential or account is broken since the
  evening spike-rig work. Posted to the fleet board.
- Arthur's live kiln session (v0.1.65) still shows black until restarted with the

  changes; reconnecting is the answer.
